## 1. 项目目标

模拟城市物流配送场景，以**有向带权图**构建配送网络，实现订单分配、路径规划、动态调度，并通过 Qt 图形界面可视化网络与路径。

系统需满足题目全部基本要求与扩展要求，并在验收时可应对现场变更需求。

## 3. 功能需求

### 3.1 基础功能（必须）

- **B1 图数据结构**：有向带权图，邻接表存储。节点总数 ≥ 30（≥2 仓库、≥15 配送点、≥3 中转站），边 ≥ 50。
- **B2 配置初始化**：从 INI 文件读取节点、边、车辆、订单。
- **B3 图表示输出**：邻接表 / 邻接矩阵文本表示。
- **B4 网络可视化**：GUI 展示节点位置、路径方向、权重标签。
- **B5 动态增删节点/边**：模拟新客户或道路封闭。
- **B6 单车辆路径规划**：从仓库出发，遍历所有待配送点后返回仓库。
- **B7 双策略**：最短距离（距离权重）/ 最低成本（成本权重），均基于 Dijkstra。

### 3.2 扩展功能（必须）

- **E1 路况变化响应**：当前路径上的边耗时增加 ≥ 20% 时自动触发重规划，更新路径高亮。
- **E2 时间窗口**：送达超时即标记 `isLate` 并记录 penalty（口径见 D13）。
- **E3 动态订单插入**：配送过程中新增紧急订单，调整现有路径，优先满足紧急订单。
- **E4 载重约束**：单车辆载重上限硬约束（口径见 D14）。

### 3.3 辅助功能

- **A1 Debug 模式**：开启后所有 GUI 触发操作变为自动模拟。
- **A2 路线信息面板**：路线序列、总距离、总耗时、总成本、到达时间、penalty。
- **A3 日志输出**：重规划、订单插入、超时、路况变化等关键事件。

## 4. 领域模型与不变量

本节定义**概念模型与必须遵守的语义规则**，不规定具体存储实现。

### 4.1 节点

- 属性：唯一 ID、类型（仓库 / 配送点 / 中转站）、坐标 (x, y)、名称、子网络编号。
- 不变量：ID 全局唯一；类型决定节点在 GUI 中的角色与颜色。

### 4.2 边

- 属性：起点 ID、终点 ID、距离 (km)、耗时 (min)、成本 (元)、**基础耗时 `baseTimeMin`**（用于判断「是否增加 ≥20%」与还原）、拥堵标记。
- 不变量：有向；起点终点必须存在；同一对 (from, to) 至多一条边。

### 4.3 时间模型（统一口径）

**时间轴**：所有时间统一表示为「**相对当日 00:00 的分钟数**」（整数）。配置中的 `HH:MM` 一律按此换算。

**发车时刻**：`t0 = vehicles[].depart_time`（默认 `08:00` → 480 分钟）。仓库不计等待、不计服务时间。

**推进递归**（停靠点 `v` 的前驱为 `u`，起点为仓库故 `u` 的 departure 即发车时刻或上一站离开时刻）：

```
rawArrival(v) = departure(u) + travel_time(u, v)
wait(v)       = max(0, windowStart(v) - rawArrival(v))     // 早到则等待至窗口开启
arrival(v)    = rawArrival(v) + wait(v)
isLate(v)     = arrival(v) > windowEnd(v)
penalty(v)    = isLate(v) ? arrival(v) - windowEnd(v) : 0  // 单位：分钟
departure(v)  = arrival(v) + service_time(v)
```

- **D13 统一口径**：`isLate` / `penalty` 仅由「送达时刻 `arrival` 与该点窗口的关系」决定，**与发生在规划阶段还是执行阶段无关**。规划、重规划、动态插单都调用这同一个推进函数，保证口径一致。
- 早到等待计入总耗时，不计 penalty。
- `service_time` 默认 5 分钟，配置文件可调。
- `windowStart(v)` / `windowEnd(v)` 由该配送点关联的全部订单合并得出（见 §4.4）。

**汇总**：总耗时 = 返回仓库后的 `departure` − `depart_time`；总 penalty = 各停靠点 penalty 之和（回仓库不计窗口）。

### 4.4 订单与停靠点

- 订单属性：ID、配送点 ID、货物量 (kg)、窗口起、窗口止、是否紧急、是否已配送。
- 不变量：窗口起 < 窗口止；配送点 ID 必须存在。
- **停靠点合并规则**：**同一配送点上的多个订单合并为一次停靠**——需求量求和，窗口取各订单窗口的并集区间 `[min(windowStart), max(windowEnd)]`。一个停靠点对应一个节点。
- 无任何未服务订单的配送点不作为停靠点。

### 4.5 车辆

- 属性：ID、起始仓库 ID、载重上限 (kg)、发车时刻 `depart_time`。
- 第一版单车辆，接口预留多车辆扩展。

### 4.6 路线结果

- 每个停靠点记录：节点 ID、`rawArrival`、等待时间、`arrival`、离开时间、`isLate`、`penalty`、离开时剩余载重。
- 路线汇总记录：节点序列（含起止仓库）、总距离、总耗时、总成本、总 penalty、规划阶段是否可行、不可行原因。

## 5. 核心算法语义

### 5.1 Dijkstra（手写）

- 输入：图、源节点 ID、目标节点 ID、权重类型（距离 / 耗时 / 成本）。
- 输出：路径节点序列 + 总权重；不可达时返回明确标记。
- **必须手写最小堆与松弛逻辑**，不得调用 `std::priority_queue` 或任何 `<algorithm>` 算法。
- 存储容器（如 `std::vector`）可用，见 §10.1。

### 5.2 贪心串联

- 从仓库出发，依次选择「当前点到候选点的最短路权重最小」的候选点作为下一站。
- 候选集合为**未服务订单对应的停靠点**。
- **紧急订单优先**：若存在未服务的紧急订单，仅在紧急订单中选择下一站；否则在所有未服务订单中选择。该逻辑必须**内嵌在贪心选择内部**，不得靠事后排序实现。
- 时间窗口按 §4.3 推进：超时点标记 `isLate` 并记录 penalty，**但仍加入路线**（D13：执行阶段同样是软约束，只记不弃）。
- 最后返回仓库。
- 载重按 D14 在规划前一次性判定；不可达点或超载时返回不可行并给出原因。

### 5.3 动态订单插入

- 将新订单加入订单集合，标记为紧急；若与既有订单落在同一配送点，按 §4.4 合并停靠点。
- 以车辆当前位置为起点、当前时间为初始时间、当前剩余载重为初始载重，对剩余未服务订单重新执行贪心串联。
- 已服务停靠点从待规划集合移除。
- 重算后按 §4.3 重新求值，penalty 以新路线为准。
- 若新订单窗口与现有订单冲突，输出提示。

### 5.4 路况模拟与重规划

- 随机选取一定比例的边（默认 10%，可配置），耗时增加 20%~50% 随机值，标记为拥堵；**直接修改图中边的耗时**（`baseTimeMin` 保留不变）。
- **触发条件**：仅当受影响边位于当前规划路径上，且耗时增加 ≥ 20% 时触发重规划。
- **第一版重规划**：从车辆当前位置出发，对剩余未服务订单全量重算。
- 增量式更新作为扩展点预留接口，不要求实现。

### 5.5 载重约束（D14）

- 单趟在仓库一次性装载全部待配送货物 → 约束等价于 `Σdemand ≤ capacity`，规划前一次性判定。
- 超载：返回不可行并给出明确原因，不生成路线。
- 路线中每站记录**剩余载重**（发车总量逐站递减）。
- 第一版不实现多趟配送；多趟列为扩展点。

## 6. 模块边界

核心层与 GUI 层严格分离。核心层不得 `#include` 任何 Qt 头文件，必须能用 g++ 独立编译并跑单元测试。

- **core**：图、节点、边、手写堆、Dijkstra、路径规划、约束检查。
- **io**：INI 解析、配置加载、图表示输出。
- **gui**：主窗口、画布、图元、权重标签、侧栏。
- **tests**：核心层单元测试（不依赖 Qt）。

核心层对外接口应满足 GUI 的只读查询需求（获取节点列表、边列表、当前路线）；GUI 通过调用核心层业务方法（规划、重规划、插入订单、增删节点边）触发计算，再根据结果重建或更新图元。

## 7. GUI 语义要求

- 中央画布展示网络：节点按类型着色，边带方向箭头与权重标签。
- 权重标签可在距离 / 耗时 / 成本之间切换（仅更新文本，不重算）。
- 路径高亮：当前规划路线加粗高亮，重规划后更新。
- 工具栏：策略切换、权重标签切换、模拟路况、插入紧急订单、增删节点/边、重新规划、Debug 模式开关。
- 侧栏：订单列表、车辆信息、超时订单、路线信息、日志。
- Debug 模式开启后，原本需要 GUI 触发的操作变为定时自动模拟（路况变化、紧急订单生成、自动重规划），且**必须可随时关闭**。

## 8. 配置文件契约

采用手写 INI 解析器，零第三方依赖。

### 8.1 节与字段

- `[general]`：`service_time_min`、`traffic_change_interval_sec`、`traffic_change_ratio`、`traffic_time_increase_min`、`traffic_time_increase_max`、`urgent_order_interval_sec`
- `[nodes]`：每行 `ID, type, x, y, name, sub_network_id`
- `[edges]`：每行 `from, to, distance_km, time_min, cost_yuan`
- `[vehicles]`：每行 `ID, start_node, capacity_kg, depart_time` ← **新增 `depart_time`（HH:MM）**
- `[orders]`：每行 `ID, node_id, demand_kg, window_start, window_end, is_urgent`

### 8.2 示例

```ini
[general]
service_time_min = 5
traffic_change_interval_sec = 30
traffic_change_ratio = 0.1
traffic_time_increase_min = 0.2
traffic_time_increase_max = 0.5
urgent_order_interval_sec = 60

[nodes]
# ID, type, x, y, name, sub_network_id
N01, warehouse, 100, 200, 中央仓库, 0
N02, delivery,  300, 150, 客户A, 0
N03, transit,   250, 300, 中转站B, 1

[edges]
# from, to, distance_km, time_min, cost_yuan
N01, N02, 5.2, 12, 8.0

[vehicles]
# ID, start_node, capacity_kg, depart_time
V01, N01, 800, 08:00

[orders]
# ID, node_id, demand_kg, window_start, window_end, is_urgent
O01, N02, 30, 09:00, 11:00, 0
O03, N05, 20, 10:00, 12:00, 1
```

### 8.3 解析规则

- `#` 开头为注释；`[section]` 分节；逗号分隔字段；空行忽略。
- 时间 `HH:MM` 转为「相对当日 00:00 的分钟数」。
- 解析错误（缺节、字段数不符、类型错误）需给出**带行号的明确报错**，不得静默忽略。

### 8.4 规模约束（`default.ini` 必须满足）

- 节点 ≥ 30：仓库 ≥ 2、配送点 ≥ 15、中转站 ≥ 3
- 边 ≥ 50
- **总订单需求 ≤ 车辆载重**（D14，保证 B6 在默认配置下可行）
- 车辆 `depart_time` 必须早于或等于各订单窗口起点，避免默认全超时

## 9. 测试要求

测试用例必须覆盖三类：

- **正确运行用例**：默认配置加载、双策略规划、动态增删。
- **导致程序错误的用例**：配置文件缺失、节点 ID 重复、边指向不存在节点、字段数不符/类型错误、载重超限。
- **边界数据用例**：节点数 = 30、边数 = 50、载重刚好等于总需求、送达时刻恰好等于窗口止（`arrival == windowEnd` 不算超时）、及早到等待、空订单列表、不可达点。

核心层测试不依赖 Qt，可用 g++ 直接编译运行。测试数据放 `data/test_cases/`，每份一个 INI 文件。

## 10. 约束与禁止事项

**必须：**

- 核心算法与核心数据结构手写。
- 核心层不依赖 Qt。
- 配置文件驱动初始化。
- GUI 可视化网络与路径高亮。
- 全程 Git 提交（GitHub），commit message 清晰。
- 设计留扩展点以应对验收现场改需求。

### 10.1 STL 使用边界（D4 落地细则）

| 范围 | 是否可用 STL | 说明 |
|---|---|---|
| 核心**算法逻辑** | ❌ **严格禁用** | Dijkstra 松弛、最小堆、贪心选择、图遍历的判定逻辑必须手写 |
| 核心**数据结构** | ⚠️ 手写 | `MinHeap` 必须自实现（**不得用 `std::priority_queue`**）；邻接表的遍历/查找逻辑手写，边表**存储**可用 `std::vector` |
| 核心**存储容器** | ✅ 可用 | `std::vector` / `std::string` / `std::map` 等容器可用 |
| `io` / `tests` / `gui` / 日志 / 字符串格式化 | ✅ 积极使用 | 辅助功能不受限，GUI 可用全部 Qt |

**核心层禁止的 STL 算法**（`<algorithm>` / `<numeric>` / `<queue>` 中的算法与优先队列）：`std::sort`、`std::partial_sort`、`std::nth_element`、`std::min_element`、`std::max_element`、`std::lower_bound`、`std::upper_bound`、`std::priority_queue` 等。核心层需要的 `min` / `max` / `swap` 自行内联实现。

**禁止：**

- 核心算法调用 STL 算法（见上表）。
- 核心层 `#include` 或链接任何 Qt 头文件/库。
- 使用第三方 JSON/INI 解析库。
- 同学间抄袭。

## 11. 扩展点预留

以下能力第一版不实现，但接口设计需留出空间：

- 多车辆（`RoutePlanner` 接口预留车辆列表参数）
- 跨仓库调拨（预留仓库选择接口）
- 增量式重规划（预留 `replanIncremental` 接口）
- 多趟配送（载重不足时回仓库补货）
- 中转站嵌套子网络（多级图，节点已带 `subNetworkId` 字段）
- 更多权重策略（权重类型枚举可扩展）

**建议**：核心层业务方法的参数尽量用「集合 + 配置」形式，避免硬编码单一车辆、单一策略，便于现场改需求时最小改动。

## 14. 测试与开发流程约定

### 14.1 期望值必须先由预言机计算（强制）

**规则：TDD 测试中的期望值不得由人工手工推算。**

起因：实现 `Dijkstra` / `RoutePlanner` 期间，人工推算期望值**连续出错三次**（返回段绕经中转站、`W→D2` 最短路非直达、图与测试用错单位），每次都是"测试红了但实现是对的"。这类算术属于高频易错，必须脚本化。

**工具**：`tools/oracle.py`

```bash
python3 tools/oracle.py            # 打印各测试夹具的全部期望值，供抄入 C++ 测试
python3 tools/oracle.py --check    # 自检；已接入 ctest（oracle_selfcheck）
```

**必须方法独立**（否则构成 `tdd-zh` 明令禁止的**同义反复**——期望值由与代码相同的方式重算，凭构造必然通过，永远无法与代码产生分歧）：

| 计算内容 | 被测实现 | 预言机的独立方法 |
|---|---|---|
| 最短路 | C++ Dijkstra + 手写堆 | **穷举所有简单路径取最小**（暴力法） |
| 时间模型 | `RoutePlanner` 代码 | 直接按 §4.3 定义转写 |

预言机只用于**离线生成测试字面量**：不参与构建、不被交付程序引用。C++ 测试中仍是硬编码字面量，运行时保持独立。

### 14.2 测试数据必须由脚本生成并自检（强制）

**规则：交付用的测试数据（`config/default.ini`）不得手工维护，必须由生成器产出且通过自检。**

起因：`default.ini` 原本出自一个写在 `/tmp` 的一次性脚本，脚本未入库。后果是这份数据**无法复现、无法审计、无法参数化重生成**——这正是两个真实数据缺陷（巡游 28 小时、成本与距离线性相关）得以产生的土壤。

**工具**：`tools/generate_dataset.py`

```bash
python3 tools/generate_dataset.py           # 重生成并与已提交文件逐字节比对 + 自检
python3 tools/generate_dataset.py --write   # 自检通过后写回
python3 tools/generate_dataset.py --check   # 只对已提交文件做自检
```

三条保证：

1. **产物可证明**：默认模式下重生成并与 `config/default.ini` **逐字节比对**。数据被手工改动过、或生成参数已变更，都会立刻失败并打印 diff。
2. **生成即自检**：规模（≥30 节点 / ≥2 仓 / ≥15 配送点 / ≥3 中转站 / ≥50 边）、端点存在性、**往返可达性**（有向图"能去"不等于"能回"）、总需求 ≤ 载重、**cost/dist 比值不得恒定**（双策略恒等价的必要条件）。
3. **接入 ctest**：`dataset_selfcheck`。

> 生成器自检是**必要预警**而非充分证明（例如它无法验证"单车辆一天跑得完"）。充分验证在 `integration_tests.cpp` 的数据质量不变量中。

### 14.3 数据质量不变量：用断言取代"人眼看输出"

**规则：对真实数据，除结构断言外还必须断言其"有效性"，尤其是上面两个缺陷的对应性质。**

起因（关键教训）：两个数据缺陷**单元测试全绿**、一路漏到集成阶段，最后是靠**人眼看 `printf` 输出**发现的。也就是说——同样的缺陷重来一遍，测试依然会全绿通过。这是流程缺陷，不是运气问题。

`integration_tests.cpp::checkDataQualityInvariants` 现在守着：

| # | 不变量 | 挡住什么 |
|---|---|---|
| ① | 两种策略必须给出**不同**结果 | 成本与距离线性相关（B7 名存实亡） |
| ② | 各策略在自身目标上不得劣于对方 | "最优"被破坏 |
| ③ | 总耗时 ≤ 12 小时工作日 | 巡游过长、全部订单必然超时 |
| ④ | 超时必须是少数，且只出现在**窗口跨度 ≤ 4 小时**的停靠点上（按跨度判定，不硬编码 ID） | 系统性超时 |
| ⑤ | 两条策略的总距离/总成本**黄金基准** | 非预期漂移 |

**⑤ 的性质必须诚实标注**：黄金值是从**当前行为捕获**的（贪心顺序来自被测实现，oracle 无法独立复现），因此**不用于证明正确性**，只用于检测漂移。有意调整数据/算法时须连同更新。

> **变异验证**：把两个原始缺陷重新注入 `default.ini`，①③④⑤ 均如期失败；恢复后全绿。这条比"测试通过"更能证明断言有效。

### 14.4 独立性的边界（易误用）

| 对象 | 要求 | 理由 |
|---|---|---|
| **算法** | **必须独立** | 否则构成同义反复——期望值由与代码相同的方式重算，凭构造必然通过 |
| **数据** | 应**单一真值源** | 两份定义必然漂移 |

> 已知遗留：单元测试小图目前仍在 C++ 与 `tools/oracle.py` 中各写一遍（双份定义）。风险可控——夹具漂移会让测试**变红**而非静默通过，只是诊断信息不够直观。后续可将小图外置为共享数据文件，两边同源读取。

### 14.5 GUI 的验证方式（离屏渲染 + 目视）

GUI 层不适用前几层的验证手段：渲染错误（箭头画反、标签遮挡、坐标错位）单元测试根本抓不到，
而 Qt widget 点击级自动化（QTest）对课设性价比极低。约定如下：

| 层次 | 方式 |
|---|---|
| 纯逻辑（如「某条边是否在规划路径上」） | 单元测试（已抽出 `isEdgeOnRoute`，被 GUI 高亮与 `needsReplan` 共用） |
| 渲染层 | **`--render` 离屏渲染成 PNG，由 agent 读图目视确认** |
| widget 点击级自动化 | 不做 |

```bash
QT_QPA_PLATFORM=offscreen ./build/app --render out.png --plan distance
QT_QPA_PLATFORM=offscreen ./build/app --render out.png --labels all --weight cost
```

CLI：`--config` / `--weight distance|time|cost` / `--plan distance|cost` / `--labels all|route` /
`--render PATH` / `--width` / `--height`。

> **实际收益**：首版箭头几何直接照搬 Qt `diagramscene` 的 `atan2` 式写法，渲染后发现
> **箭头被画到节点内部而完全看不见** —— 那段几何在该示例里是配合「线段 p1 为终点」的相反
> 约定使用的。已改为「tip + base + 垂直向量」的自证构造。**这个问题只有看图才能发现。**

### 14.6 测试分层

| 层 | 目标 | 依赖 |
|---|---|---|
| `core_tests` / `minheap_tests` / `dijkstra_tests` / `routeplanner_tests` | 用人工小图钉住**行为语义** | 仅 `core` |
| `config_tests` | 配置解析、规模校验、错误输入、边界 | `io` |
| `integration_tests` | 用**真实 `default.ini`** 跑通「配置 → 规划」全链路 | `io` |
| `oracle_selfcheck` | 预言机自身正确性 | python3 |

> 集成层不可省略：`RoutePlanner` 完成后，单元测试全绿，但集成测试一跑就查出**两个真实数据缺陷**（尺度导致 28 小时巡游、成本与距离线性相关导致双策略恒等价）。详见 §15 变更记录中的"默认数据修正"行。
