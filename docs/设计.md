## 1. 项目目标

模拟城市物流配送场景，以**有向带权图**构建配送网络，实现订单分配、路径规划、动态调度，并通过 Qt 图形界面可视化网络与路径。

系统需满足题目全部基本要求与扩展要求，并在验收时可应对现场变更需求。

## 3. 功能需求

### 3.1 基础功能（必须）

- **B1 图数据结构**：有向带权图，邻接表存储。节点总数 ≥ 30（≥2 仓库、≥15 配送点、≥3 中转站），边 ≥ 50。
- **B2 配置初始化**：从 INI 文件读取节点、边、车辆、订单。
- **B3 图表示输出**：邻接表 / 邻接矩阵文本表示。
- **B4 网络可视化**：GUI 展示节点位置、路径方向、权重标签。
- **B5 动态增删节点/边**：模拟新客户或道路封闭。
- **B6 单车辆路径规划**：从仓库出发，遍历所有待配送点后返回仓库。
- **B7 双策略**：最短距离（距离权重）/ 最低成本（成本权重），均基于 Dijkstra。

### 3.2 扩展功能（必须）

- **E1 路况变化响应**：当前路径上的边耗时增加 ≥ 20% 时自动触发重规划，更新路径高亮。
- **E2 时间窗口**：送达超时即标记 `isLate` 并记录 penalty（口径见 D13）。
- **E3 动态订单插入**：配送过程中新增紧急订单，调整现有路径，优先满足紧急订单。
- **E4 载重约束**：单车辆载重上限硬约束（口径见 D14）。

### 3.3 辅助功能

- **A1 模拟模式**：「按站模拟 / 按时间模拟」两种模式（互斥），开启后按固定节奏自动推进并结算软件内时间事件；**必须可随时关闭**。见 §7 与 D24。（原称「Debug 模式」，2026-09-26 更名。）
- **A2 路线信息面板**：路线序列、总距离、总耗时、总成本、到达时间、penalty。
- **A3 日志输出**：重规划、订单插入、超时、路况变化等关键事件。

## 4. 领域模型与不变量

本节定义**概念模型与必须遵守的语义规则**，不规定具体存储实现。

### 4.1 节点

- 属性：唯一 ID、类型（仓库 / 配送点 / 中转站）、坐标 (x, y)、名称、子网络编号。
- 不变量：ID 全局唯一；类型决定节点在 GUI 中的角色与颜色。
- **三类节点的语义（D16，2026-11-24 按规格一改正）**：
  | 类型 | 语义 |
  | --- | --- |
  | **仓库** | **基地，不是货源**：车辆**空载**从这里发车、服务完回到这里；车在基地**不装任何货**——一件货都只能从它的**取货点 A** 装上车 |
  | **配送点** | **既可能是取货点 A、也可能是送达点 B**（每张订单都带一对 A→B，A≠B）。只有 B 带时间窗与 penalty；A 无窗口、不计 penalty、停靠零耗时 |
  | **中转站** | **降载暂存点**：装不下时把**整张普通订单**卸在这里、事后由**同一辆车**取回继续送。只存**实际卸下的货**（不存在匿名缓冲库存），容量不限，**计划结束时必须为 0**，全局**至多一堆、锁站**（§4.6） |
  > **口径变更记录（保留历史）**：本条原写「仓库 = 货物初始存放地、满载往返的补给点；中转站 = 货物集散点，可暂存供后续趟二次配发」。该语义先后由 §16 P25/P30（中转站退出排线）与规格一（**仓库不供货**、**趟退役**）取代。上表是**现行**口径；历史原文见 §16 P8–P13。
- **子网络（D17）**：中转站可**嵌套子配送网络**（如「中转站 A 下属 3 个社区配送点」），
  由 `sub_network_id` 标识：同一编号的节点构成一个子网络，编号 `0` 表示不隶属任何子网络。
  子网络用于**界面分组标识**（「中转站 / 集散」面板列出每站的下属配送点数）与**新客户的归属继承**（手动「模拟新客户」建出的节点继承最近邻的 `sub_network_id`；最近邻是仓库时回落到最近的编号非 0 配送点/中转站）。**不是**多级图，也**不再是**多趟时的簇划分依据（簇划分随 §5.6 多趟一起退役）。

### 4.2 边

- 属性：起点 ID、终点 ID、距离 (km)、耗时 (min)、成本 (元)、**基础耗时 `baseTimeMin`**（用于判断「是否增加 ≥20%」与还原）、拥堵标记。
- 不变量：有向；起点终点必须存在；同一对 (from, to) 至多一条边。
- **有向性必须真正体现（D18）**：数据集须包含**单向边**（单行道），
  不能全是双向对。若全部双向，则"有向图"与"无向图"在行为上无从区分，
  与 §5.1「有向带权边」不符，也无法展示 Dijkstra 的有向性。
- **道路计数口径（D19）**：`路径总数 ≥ 50` 按**无向道路对数**与**有向边数**两个口径
  同时满足（见 §8.4），避免验收时因口径解释不同而不达标。

### 4.3 时间模型（统一口径）

**时间轴**：所有时间统一表示为「**相对当日 00:00 的分钟数**」（整数）。配置中的 `HH:MM` 一律按此换算。

**发车时刻**：`t0 = vehicles[].depart_time`（默认 `08:00` → 480 分钟）。仓库不计等待、不计服务时间。

**推进递归（2026-11-24 按规格一改正：停靠零耗时 + 逐单窗口）**（停靠点 `s` 的前驱为 `u`，起点为基地故 `u` 的 departure 即发车时刻或上一站离开时刻）：

```
raw(s)      = departure(u) + travel_time(u, s)                       // 沿最短路走完整个 leg
wait(s)     = s.deliveries 为空 ? 0
            : max(0, max{ ws_i : i ∈ s.deliveries } − raw(s))        // 等到本停靠全部送达单都开窗
arr(s)      = raw(s) + wait(s)
penalty_i   = max(0, arr(s) − we_i)      // **逐单**：每张送达单按自己的 we
late_i      = arr(s) > we_i              // **逐单**；arr == we 不算迟到
departure(s)= arr(s)                     // **停靠零耗时**：装卸不耗时、无 service_time
```

- **D13 统一口径**：`isLate` / `penalty` 仅由「送达时刻 `arr(s)` 与该**订单自己的** `[ws, we]` 的关系」决定，**与发生在规划阶段还是执行阶段无关**。规划、重规划、动态插单都调用同一个重放函数（`RoutePlanner.cpp` 匿名命名空间的 `replay`），保证口径一致。
- 早到等待计入总耗时，不计 penalty。
- **停靠零耗时**：`departure == arrival`。配置里**没有** `service_time_min` 这个键——它是**退役键**，出现即带行号报错（§8.1）。
- **窗口只属于送达点 B，且逐单**：`ws_i` / `we_i` 是订单 `i` 自己的窗口；`服务点 A` 没有窗口、不计 penalty；停靠**没有「合并窗口」**（见 §4.4）。
- 汇总口径：总耗时 = `返回基地的时刻 − 发车时刻`（**含等待**）；总 penalty = 各送达单 `penalty_i` 之和（回基地不计窗口）。

**汇总**：总耗时 = 返回仓库后的 `departure` − `depart_time`；总 penalty = 各停靠点 penalty 之和（回仓库不计窗口）。

### 4.4 订单与停靠点（2026-11-24 按规格一改写：**逐单窗口**，不再是并集窗口）

- **契约属性（`[orders]` 七列，顺序固定）**：`ID, pickup, delivery, demand_kg, window_start, window_end, is_urgent`。
  - **全部订单统一 A→B 取送式**（ADR 0002）：`pickup`（取货点 A）**必填**、`delivery`（送达点 B）必填、`A ≠ B`；窗口只属于 **B**。
  - 「普通单的货默认在仓库」的旧语义已退役：**仓库不供货**，任何一件货都得先从 A 装上车（§4.1）。
- **运行时字段（不在七列契约内）**：`source`（来源）与 `picked`/`served`（已取/已送）。来源五取值 + 保留一值：
  | 来源 | ID 前缀 | 产生方式 | 占事件额度？ |
  | --- | --- | --- | --- |
  | `initial` | `O` | `[orders]` 静态加载 | 否（额度只数事件来源） |
  | `event_normal` | `N` | 事件刻刷普通单 | 是（普通 ≤ 6） |
  | `event_urgent` | `U` | 事件刻刷紧急单 | 是（紧急 ≤ 2） |
  | `manual_customer` | `C` | 工具栏「模拟新客户」 | 否（手动单不占额度） |
  | `manual_urgent` | `U` | 工具栏「插入紧急订单」 | 否（手动单不占额度） |
  | `manual_normal` | `M` | **预留**（规格二「插入普通取送单」） | — |
- 不变量：`ws < we`；A、B 必须存在且 `A ≠ B`；`0 < demand_kg ≤ 载重上限`（单笔超载才是不可行，见 §5.5）。
- **停靠 = 动作集**（一个节点一次停靠，动作记在停靠上）：
  | 字段 | 语义 |
  | --- | --- |
  | `deliveries[]` | 送达动作：`orderId` + **该单自己的** `late`/`penaltyMin`（逐单，见 §4.3） |
  | `pickups[]` | 取货动作：在 A 把该单货物装车 |
  | `offloads[]` | 降载动作：把该单整张卸入本中转站暂存（§4.6） |
  | `reclaims[]` | 取回动作：从本中转站取回该单暂存货 |
  | `phase` | `Urgent` / `Normal`——硬优先的阶段划分（§5.6） |
- **停靠内执行顺序恒为「先全部卸、再全部装」**：`deliveries + offloads` 先做，`pickups + reclaims` 后做；因此停靠内的载重峰值取「卸后 / 装后」较大者。
- **同一节点上的多张订单合并为一次停靠，但窗口不合并**：停靠只有一个到达时刻；每张送达单按**自己的** `[ws, we]` 判迟到、计 penalty。旧的「窗口取并集 `[min(ws), max(we)]`」口径**已作废**——它会把紧窗单的迟到吞进宽窗单里（#18 Q14=A 的动机）。
- 无任何动作的配送点不作为停靠点。

> **为什么逐单窗口必须精确到「停靠」这一层**：一个停靠只有一个到达时刻，但同节点多单的窗口并不相同；若继续用并集窗口，`integration_tests` 里「迟到只出现在窗口跨度 ≤4h 的停靠点」这类断言就会把**紧窗单**的迟到误判成**宽窗停靠点**的迟到（MC-G02 要求改逐单）。

### 4.5 车辆（六字段；单车辆 = 规格一，异构 = 规格二）

- **契约字段（`[vehicles]` 六列，顺序固定）**：`ID, start_node, capacity_kg, depart_time, time_factor, cost_factor`。
- **两因子的语义（只缩放两样东西）**：
  | 量 | 是否乘因子 | 说明 |
  | --- | --- | --- |
  | 当前耗时（行驶） | ✅ `× time_factor` | 规划的时间推进、`needsReplan` 的 20% 判定、oracle 复算都按**该车缩放后**的耗时 |
  | 成本 | ✅ `× cost_factor` | 同一条 leg 的成本按该车系数计 |
  | 距离 / 等待 / penalty | ❌ 不乘 | 距离是几何量；等待与 penalty 是**分钟**口径，属服务承诺，不随车变 |
  - 图表示（邻接表 / 邻接矩阵 / 权重标签）**仍显示基础边权**，不显示缩放后的值——避免同一张图因车而异。
- **现行车队（规格二 #39，`config/default.ini` 三行，行序即摘要与页签行序）**：
  | 车辆 | 起始仓库 | 载重上限 | 发车 | 耗时倍率 | 成本倍率 |
  | --- | --- | --- | --- | --- | --- |
  | V01 | W01 | 400 kg | 08:00 | 1.00 | 1.50 |
  | V02 | W01 | 160 kg | 08:00 | 1.25 | 0.80 |
  | V03 | W01 | 160 kg | 08:00 | 1.25 | 0.80 |
  - **V02 与 V03 五个参数完全相同**（容量 / 两因子 / 基地 / 发车）：整条路线互换后**车队级 13 字段一个都不变**，只有「每车 7 字段 + 每车路线序列」能守住「谁跑哪些单」——这是 ADR 0008 与 §7.2 的由来。
- **两因子作用于「当前耗时 / 当前成本」**：路况改过 `timeMin` 之后，该车看到的行驶耗时 = **当前边耗时 × time_factor**；成本 = 当前边成本 × cost_factor。距离、等待、penalty **不乘**（等待与 penalty 是服务承诺的分钟口径）。图表示仍显示**基础边权**。
- **阶段划分**：规格一 = 单车辆（历史基线，接口按集合设计）；规格二 = 上述异构三车 + 类型感知分配（§5.8），每车一条**连续路线**（自己的 `start_node` / `depart_time` 空载出发、回同一基地）。
- **载重约束**：约束的是**单条连续路线上任一时刻的在车货量** `0 ≤ 在车 ≤ 该车 capacity`（前缀载重，见 §5.5），**不是**总需求、也不是「单趟」。总需求超载不构成不可行；**逐车**峰值利用率 = 平均在车 ÷ **该车** capacity。

### 4.6 路线结果（2026-11-24 按规格一改写：`stops` 为真源，`Trip`/多趟已删除）

**路线 = 一条连续路线**：`基地 →（紧急段）→（普通段）→ 基地`。没有趟、没有分批、没有每趟回仓库。

- **`Stop`（一次停靠，动作集为真源）**：
  | 字段 | 语义 |
  | --- | --- |
  | `nodeId` | 停靠节点 |
  | `deliveries[]` / `pickups[]` / `offloads[]` / `reclaims[]` | 动作集（见 §4.4）；四者决定重型状态转移 |
  | `phase` | `Urgent` / `Normal` |
  | `rawArrivalMin` / `waitMin` / `arrivalMin` | 停靠零耗时，故**没有离开时间字段**：`arrival` 就是离开时刻（§4.3） |
  | `late` / `penaltyMin` | **停靠级聚合量** = 各送达单逐单之和，供界面/汇总便捷读；口径本身是逐单 |
  | `remainingLoadKg` | **离开该站时的在车货量** = 到达在车 − 送达 − 降载 + 取货 + 取回（不是「发车量逐站递减」） |
- **`OffloadLeg`（降载 custody 记录）**：`station`/`orderId`/`deliverNodeId`/`kg`/`offloadTimeMin`/`reclaimTimeMin`（-1 = 尚未取回，**计划结束时必须已取回**）。判据：**同一台车卸了又取回 = 降载**，永不记为转运（转运是「卸入车 ≠ 取走车」，规格二 #28）。
- **`StashState`（跨重规划透传）**：`station` + `items[]`（`OnboardItem{nodeId, kg, orderId}`）。重规划时由调用方（GUI）传入，规划器据此在计划里保留「回站取回并继续配送」；不带它，暂存货会在重规划后凭空消失。
- **`RoutePlan` 汇总**：`status`（`Ok` / `OrderExceedsCapacity` / `Unreachable`）+ `reason`、`totalDistanceKm`、`totalTimeMin`、`totalCostYuan`、`totalPenaltyMin`、`returnArrivalMin`、`offloads[]`、`metrics`。
- **`nodes` / `nodeArrivalMin` / `nodeIsStop`（兼容视图，不是真源）**：由 `stops` **一次展平**生成（含途经节点），界面「推进一站」按下标走，`nodeIsStop` 标记哪一次出现是停靠。
- **`RouteMetrics` + `OrderMetric`（摘要与验收口径，§6.1）**：停靠数 S、动作数 A、逐单 `penalty`/准时（含取货准时判据 `t_pick + A→B 最短耗时 ≤ we`）、两率（含紧急·普通分列，分母 0 记 `—`）、时间加权平均在车/利用率/峰值。

> **历史（保留，不再是现行描述）**：本节曾定义「趟（Trip）：节点序列 + 逐节点到达时刻 + 本趟停靠列表 + 本趟在中转站的装卸记录 + 本趟距离/耗时/成本」「路线 = 趟列表」「中转站最终暂存量与峰值暂存量」。`struct Trip`、`RoutePlan::trips`、`nodeTripIndex`、`flatten` 的趟边界已全部删除；`grep -rn 'multiTripPlan\|struct Trip' src` = 0 命中。

### 4.7 实施期口径精确化（**10 条偏离台账**，2026-11-24 现行口径）

> 本节是规格一实施（#32–#37）过程中**偏离规格成稿字面**的十条，逐条给「规格原文 → 实际做法 → 理由 → 证据」。**每条都是现行行为**，不是待修项；规格成稿（`docs/records/specs/spec1-pickup-delivery-foundation.md`）与本节冲突时**以本节 + `src/` 为准**，并已在各票关闭评论里留档。

**① 不变量 ⑦ 的例外判据精确化**
- 规格原文（§4.7-7）：「同阶段同节点至多一次停靠；唯一例外是 **FIFO 强制重访**，且重访停靠只含该单的一个动作」。
- 实际做法：判据改为「**并入首次停靠后 F2/F5/F3 仍成立 ⇒ 必须合并**；否则算强制重访，且重访停靠只含该单的一个动作」。
- 理由：默认数据集自带 A/B **互逆环**（O01 `D08→D01` 与 O09 `D01→D08`）。逐字按「例外仅 FIFO」执行会把默认数据判成**不可行**（结构下限 26 站 > 25 单可服务）。精确化后默认三策略的**非强制重复 = 0**，仍可被 `integration_tests` 逐策略断言。
- 证据：提交 `a2a12da`（落实为默认约束）、`2847540`/`0820251`（断言改回规格字面并对齐 `firstAt` 口径）；守卫 `integration_tests` 逐策略「非强制重复 = 0」、`routeplanner_tests` 不变量 ⑦ 用例。

**② 时间策略的键第二分量**计入早到等待**
- 规格原文（§4.1）：「目标 = 字典序 (Σpenalty, 当前策略权重, 稳定 tieKey)」，未说明「策略权重」是否含等待。
- 实际做法：`WeightType::Time` 的键**加上早到等待**（`key.weight += wait`），距离/成本两维不加。
- 理由：「总耗时」的对外口径是 `返回 − 发车`（**含等待**，§4.3）。若键只累加 leg 行驶耗时，会出现「最短耗时策略」的总耗时反而**更长**——验收 ② 必然不成立。距离/成本两项本身不含等待，故只对 Time 生效。
- 证据：提交 `cc91ef5`（键序回退为规格三键）、`6f38f5f`（键序说明写进代码注释）；守卫 `integration_tests` 三策略 ②（实测 time 378.200 ≤ distance 415.200 / cost 431.600）。

**③ 多起点构造（整批构造跑三版插入序）**
- 规格原文（§4.5）：「普通段：全位置对枚举 → 取 key 最小」——单一 EDD 插入序。
- 实际做法：**仅对「从基地、空车、发车时刻」的整批构造**（`planRoute`）跑三版插入序：① EDD、② 按取货点 A 聚簇、③ 按送达点 B 聚簇；每版都跑满同一条链（pair-insertion + `repair(R≤3)`），可行者**按同一把规格三键取优**。**中途重规划（`replan` 带在车货/非发车时刻）仍单起点**。
- 理由：单起点 EDD 下成本策略会被距离策略反超（实测单起点时 cost 168.5 元 vs distance 145.3 元 ⇒ ② 的成本项失败）。中途重规划不启用多起点，是因为那条路径上构造次数多（时间预算）且起点已被已执行前缀约束。
- 证据：`src/core/RoutePlanner.cpp` 的 `insertionStarts`/`buildAll`；提交 `cc91ef5`；守卫 `integration_tests` 三策略 ②、`--plan-summary` 黄金值。

**④ 新增 `OrderSource::ManualUrgent`（第 5 个运行时来源，前缀仍 `U`）**
- 规格原文（#24 R5）：来源四类 `initial`/`event_normal`/`event_urgent`/`manual_customer`，前缀 `O/N/U/C`。
- 实际做法：新增 `manual_urgent`（工具栏「插入紧急订单」生成的手动紧急单，前缀仍 `U`），**不占 R6 的待处理额度**（额度只数事件来源的单）。
- 理由：若复用 `event_urgent`，手动插的紧急单会被算进「事件来源」，额度提前耗尽；若复用 `initial`，订单表就分不清它是配置静态单还是用户刚点的。**仅此一处新增，别再加来源**。
- 证据：`src/core/Order.h::OrderSource`；提交 `9425543`；守卫 `--self-check-actions` 第 7 段（额度/来源）、`config_tests`（静态单恒 `Initial`）。

**⑤ `onAdvanceStop` 的结算时机改为「到达前逐刻、在各自时刻结算」**
- 规格原文（D24 纪律）：「事件结算必须挂在**软件时间前进**上」，未规定 `onAdvanceStop` 内部的结算时刻。
- 实际做法：`onAdvanceStop` 在**移动到下一节点之前**，把区间内的每个事件刻**逐个结算**（车仍显示在所在路段起点），而不是「到达后一次性批量结算」。
- 理由：这是 A1–A7 等价性（一次推进一刻 == 逐个推进到同一时刻）成立的前提。按到达时刻批量结算时，两条路径在同一刻的 (位置, 时钟) 必然不同——实测路径 A 第 15 行即分叉，终态 23:35 vs 18:51。
- 代价（如实记录）：事件密集的长跑，**终点会保守后移**（实测 18:51 → 23:35）；`--plan-summary`（无事件）不受影响。
- 证据：提交 `9425543`；守卫 `--self-check-actions` 第 8 段 A1–A7（A1 事件日志 62 行逐字相同；实测 `A6 位置 W01 @ 23:35`、`A7 下一个事件刻 23:45`）。

**⑥ oracle 的最短路用递归穷举（刻意与 C++ Dijkstra 方法独立）**
- 规格原文（§6.4 L3）：「用 app 输出的路线节点序列独立复算**纯算术项**」。
- 实际做法：`tools/oracle.py` 的最短路用**递归穷举简单路径**，不复用 Dijkstra 的松弛/堆写法；`cli_plan_summary` 现在约 **20s**（本机 2026-11-24 实测 20.88s）。
- 理由：§14.4 要求「算法必须独立」——若 oracle 也用 Dijkstra，等于拿同一套逻辑再算一遍，构成同义反复，测不到东西。代价是慢，但只在 L3 对拍与 `oracle_selfcheck` 里付。
- 证据：`tools/oracle.py`；ctest 目标 `cli_plan_summary`（162 项）/ `oracle_selfcheck`。

**⑦ `cli_action_self_check` 36.6s（#34 的等价性双跑）**
- 规格原文：未规定自检耗时。
- 实际做法：A1–A7 等价性要「重新加载配置 + 构造两个独立 `MainWindow` + 各推进到路线终点（63 刻 / 56 站）」并逐字比对，耗时由 8.1s 涨到 **36.6s**（本机 2026-11-24 实测 35.86s）。
- 理由：等价性只能靠**真的跑两条路径再比对**来证明（§14.4）；不做周期性全量重算、不减少步数，否则等于弱化守卫。
- 证据：`tests/../src/main.cpp:runActionSelfCheck` 第 8 段；提交 `9425543`；ctest 目标 `cli_action_self_check`。

**⑧ `--dump-plan` 的 stdout 首行带「已加载 …」日志**
- 规格原文（#35 交接）：「L3 需要一个只供开发用的计划转储」。
- 实际做法：`--dump-plan <kind>` 输出停靠级转储（停靠、动作、到达时刻、逐单 penalty），**首行是 `已加载 <路径>：节点 N，边 M，订单 K` 的运行日志**（与所有 CLI 路径一致，不单独静默）。
- 理由：把日志压掉会让「配置到底加载了哪份文件」不可见；oracle 侧已容忍首行（跳过非数据行）。
- 证据：`src/main.cpp`（`--dump-plan`）；`tools/oracle.py --plan`；ctest `cli_plan_summary` 的 L3 段。

**⑨ 退役键白名单要字面串 ⇒ grep 口径调整**
- 规格原文（DoD）：「`grep -rn 'service_time_min' src config` 保持 0 命中」「`event_weight_` 0 命中」。
- 实际做法：`src/io/ConfigLoader.cpp::retiredGeneralKeyHint` 的白名单表里**必须**出现这几个字面键（否则旧配置会静默变默认值，而不是带行号报错）。故 DoD 收紧为「**白名单表之外 0 命中**」。
- 理由：退役键的处置方式是**报错 + 迁移提示**，不是「假装没这个键」；把字面串删掉等于把「旧配置被静默接受」这个 bug 放回来。
- 证据：`grep -n 'service_time_min\|event_weight_' src/io/ConfigLoader.cpp` 只命中该函数体；`config` 目录 0 命中；`config_tests` 退役键 6 类报错断言。

**⑩ 规格一 §6.8 的 8/7 列被裁定的 9/8 列取代**
- 规格原文（§6.8）：停靠明细 **8 列**、超时订单 **7 列**。

## 5. 核心算法语义

### 5.1 Dijkstra（手写）

- 输入：图、源节点 ID、目标节点 ID、权重类型（距离 / 耗时 / 成本）。
- 输出：路径节点序列 + 总权重；不可达时返回明确标记。
- **必须手写最小堆与松弛逻辑**，不得调用 `std::priority_queue` 或任何 `<algorithm>` 算法。
- 存储容器（如 `std::vector`）可用，见 §10.1。

### 5.2 主构造：penalty 先的 cheapest pair-insertion（+ EDD + 有界 relocate）

> **2026-11-24（规格一）**：本节原写「贪心串联：从仓库出发依次选当前点最短路权重最小的候选点」。#18 的选型把构造器改为**插入式**——不再「最近邻选下一站」，而是「把整张订单的取送**对**插到最省的位置」。最近邻只保留为基线/叙事，不再是实现。

**排序（先定插入顺序，再谈插入位置）**：
- 紧急单：**订单级 FIFO** 键 =（到达事件刻, 插入序）——先到先服务，后插的排在后面。
- 普通单：**EDD**（窗口止升序，同窗止按订单 ID 升序）——最紧的先插，避免后面无处可插。

**插入（普通段）**：
- 对当前这张单，枚举普通段内的**全部位置对** `(i, j)`：取货动作 A 落在第 `i` 个停靠之前、送达动作 B 落在第 `j` 个停靠之前（`j ≥ i`）。
- 每个候选位置都要**重放整条路线**（`replay`：时间/等待/逐单 penalty/前缀载重/可行性 F1–F7），取键最小者。
- **同节点并入既有停靠**（并集窗口已退役，窗口仍逐单，见 §4.4）。

**目标函数：字典序三键**：

| 键 | 内容 | 说明 |
| --- | --- | --- |
| 第 1 键 | `Σ` 逐单 penalty | **penalty 一票否决**：penalty 多一点，后面两项再小也不选 |
| 第 2 键 | 当前策略权重（距离 / 耗时 / 成本） | 耗时维**含早到等待**（见 §4.7-②） |
| 第 3 键 | 稳定 tieKey | 停靠序列的 (节点 ID, 排序后的动作订单 ID) 逐位比较，再按长度收尾 ⇒ 同输入必得同一路线 |

> 载重峰值**不进键**：它是报告指标（`RouteMetrics::peakLoadKg`），不是决策依据。

**失败后的三级兜底**（顺序固定，越往后越贵）：

1. **有界 relocate**（`repairRoute`，`R ≤ 3` 轮）：只动**普通段**，把普通单按 EDD 序逐个摘下、重插到更优位置；某一轮无改进即停。紧急段对 relocate 恒等（FIFO 不可重排）。
2. **全量兜底**：把「插不进去的那张单」提到普通序最前，从当前位置/时刻/在车货**整体重跑**一次构造；两版按同一把三键取优。
3. **降载**（最后手段，§4.6）：仍不行才卸整张普通单到中转站腾空间。
4. **拒绝并报原因**：绝不通过违反容量或「先送后取」来凑一个解。

- 时间窗口按 §4.3 推进：迟到单标记并计 penalty，**但仍加入路线**（D13：只记不弃）。
- 最后返回**基地**（不是「仓库先装货再出发」——车空载出发，见 §4.1）。
- 不可行只在：A/B 不可达、单笔 `demand > capacity`、`demand ≤ 0`、`A == B`、降载后仍无解。

**复杂度（目标规模内不裁剪）**：单请求插入 = `O(n²)` 位置对 × `O(n)` 重放 = **`O(n³)`**；m 张单 ⇒ `O(m·n³)`；修复 `O(R·m_n·n³)`。目标规模 m ≤ 50 / n ≤ 100（§4.8 规格一），n > 100 才谈 top-k 裁剪——本轮不做。

### 5.3 动态订单插入（**通用插单**：紧急 FIFO 硬优先 + 普通 pair-insertion）

> **2026-11-24（规格一）**：本节原写「**新订单一律标记为紧急取送单**」「紧急取送单独立成趟、最先执行」。通用插单（#24 / MC-B04）把 `insertUrgentOrder` 换成了 `insertOrder`：**走哪条链由订单自己的 `urgent` 标记决定**，不再复制两个函数、也不再强制把所有新单当紧急单。

**入口**：`RoutePlanner::insertOrder(graph, vehicle, remainingOrders, newOrder, currentPosition, currentTimeMin, weight, onboard, stash)`。

- **每张单都携带 A→B**（A≠B），完成以**到达 B 卸货**为准；A 无窗口、不计 penalty、停靠零耗时；只有 B 有送达窗口。
- **`urgent == true` → 紧急段尾插**（订单级 FIFO，后来的紧急单排后面）；**合并停靠内先送达前一张、再取货后一张**（不然会违反 F5）。
- **`urgent == false` → 普通段 pair-insertion 链**：全位置对 → `repair(R≤3)` → 全量兜底 → 降载 → 拒绝（§5.2 同一套，不另写一份）。
- **窗口基准**：事件刻刷出的单以**事件刻** `t` 为基准（普通 `[t, 24:00]`、紧急 `[t, min(t+60, 1440)]`）；手动「插入紧急订单」以**当前软件时刻**为基准 `[now, now+60]`。
- **装不下时降载（最后手段）**：若「载重上限 − 当前在车货」放不下这张单，先把车上若干**整张普通订单**卸到中转站（选站按完整绕行增量、全局至多一堆锁站），再 A 取、B 送；暂存队列在普通段**先于该单送达**取回，继续普通配送。**同一台车卸、同一台车取回 ⇒ 记降载，不记转运**。
- **顺路交货**：A/B 本身若也是在车普通货的目的地，取/送时顺路一并交付（仅限此刻已在车上的货）；**只在不增加该停靠等待时并入**；降载选货绝不卸 A/B 目的地的货。
- **重规划基准**：以车辆当前位置、当前时刻、当前在车货为起点，对剩余未服务订单重算；已服务停靠从待规划集合移除，penalty 以新路线为准（`onboard` 与 `StashState` 必须一并传入，否则暂存货会凭空消失）。
- **拒绝插入**：A/B 不可达、`A == B`、单笔货量超载重或 `≤ 0` ⇒ 拒绝并给出原因；**窗口明显不可达**（最早到达已晚于 `we`）⇒ 在 `warning` 里如实提示，但**仍纳入规划**（D13：超时只记不弃）。

### 5.4 路况模拟与重规划

- 随机选取一定比例的边（默认 10%，可配置），耗时增加 20%~50% 随机值，标记为拥堵；**直接修改图中边的耗时**（`baseTimeMin` 保留不变）。
- **触发时机（D24）**：路况等模拟事件**不由真实时间、也不由"推进了几次"触发**，而由**软件内时钟**决定——每过一个 `event_interval_min`（默认 15min）的事件刻，恰抽 1 个事件（权重见 D24）。事件结算挂在"软件时间前进"上，因此推进粒度（一站 / 一刻）不影响事件串。旧口径「真实每 30 秒自动模拟一次」已废弃，见 §16 P34。
- **触发条件**：仅当受影响边位于当前规划路径上，且耗时增加 ≥ 20% 时触发重规划。
- **第一版重规划**：从车辆当前位置出发，对剩余未服务订单全量重算（带上在车货 `OnboardItem` 与暂存 `StashState`）。
- **增量式更新（2026-11-24 改为「顺序不变版重放」）**：`replanIncremental` 不再按 leg 重算——停靠**顺序完全不变**，只把剩余停靠按**当前边权重**重放一遍；可行则采用并把 `usedIncremental` 置 true，不可行（任一 leg 不可达）则退回全量。见 §5.7 与 §4.7。

### 5.5 载重约束（2026-11-24 按规格一改写：**前缀在车量**）

> **本节先后由 D21 与规格一改写**：D14 把「载重不足」判**不可行**；D21 改成「按载重上限**多趟**往返」；**规格一**再改成「**单条连续路线上的前缀在车量**」——车边走边取边送，载重上限只约束**任一时刻在车上**的货量。

**约束的正确表述**：

- 约束对象是**单条连续路线上任一时刻的在车货量**：`0 ≤ 在车 ≤ capacity`。
- 在车量的变化**只由停靠动作决定**：到 A **+该单货量**（取货）、到 B **−该单货量**（送达）、降载 **−卸下量**、取回 **+取回量**；停靠内**先卸后装**，因此停靠内峰值取「卸后 / 装后」较大者。
- **总需求不再受 capacity 限制，也不触发任何分批**：`Σdemand > capacity` 是**常态**（默认数据 516kg vs 200kg），不是异常。
- 不可行只剩两条：**单笔订单货量 > capacity**（`OrderExceedsCapacity`，无法拆分、降载也救不了）与**存在不可达点**（`Unreachable`）。
- 每站记录**离开该站时的在车货量**（`Stop::remainingLoadKg`），界面「余货(kg)」列即此值。
- 中转站暂存满足 `stock[t] ≥ 0`（只存**实际卸下**的整张普通单），**计划结束时必须为 0**（不留残余库存）。

**口径变更的影响**：原「载重约束」人工关卡期望的「不可行」结论**作废**，
改为期望「**一条连续路线**跑完全部订单 + 逐站余货明细」；「总需求 ≤ 车辆载重」这条**规模约束**（§8.4 原写 `default.ini` 必须满足）随之删除——它与新模型直接矛盾。

### 5.6 单条连续路线构造概述（**本节替代原「多趟分批配送算法」**）

> **2026-11-24（规格一）**：本节原文定义「趟（Trip）」、簇划分、按载重上限分批、每趟回仓库、中转站暂存分支与 6 条不变量。**多趟机制整体退役**——`struct Trip`/`RoutePlan::trips`/`multiTripPlan`/`flatten` 的趟边界已从 `src` 删除（`grep -rn 'multiTripPlan\|struct Trip' src` 0 命中），段末保留一段历史核算结论。

**路线形状（唯一形状）**：

```text
[基地] ─ 空载发车
   → 紧急段（紧急单 A/B 对，订单级 FIFO 整单串接；可含降载卸货停靠、FIFO 强制重访停靠）
   → 普通段（普通单 A/B 对，EDD + pair-insertion；取回停靠是必做停靠）
   → [基地] 收尾（回基地即结束，不计趟、不计窗口）
```

**四步，顺序固定**：

| 步 | 做什么 | 失败时 |
| --- | --- | --- |
| 1 建候选 | 剩余订单的 (A,B) 对 + 暂存**取回**（必做单点）+ 触发时的**降载卸货** | 单笔超载/不可达 ⇒ 直接判不可行 |
| 2 紧急段 | 按 FIFO 逐张**尾插** A→B；装不下先降载；同节点合并时停靠内**先送后取** | 降载也腾不出 ⇒ 不可行并说明 |
| 3 普通段 | 按 EDD 逐张做 **pair-insertion**（全位置对 → 取键最小）；失败走 `repair(R≤3)` → 全量兜底 → 降载 | 三级兜底都失败 ⇒ 拒绝该单并报原因 |
| 4 收尾 | 补取回停靠（**先于**该单送达）→ 从当前位置回基地 | 回不去 ⇒ 不可行（不可达） |

**与原「多趟」的四条差别（读文档的人最容易混）**：

| 维度 | 原多趟（已退役） | 现行单条连续路线 |
| --- | --- | --- |
| 单位 | 趟（Trip），每趟独立核算 | **一条路线**，只有停靠序列 |
| 载重 | 每趟发车量逐站递减 | **前缀在车量**（边取边送，§5.5） |
| 中转站 | 集散/暂存/二次配发 | **只做降载暂存的临时存放**（§4.6） |
| 收尾 | 最后一趟回仓库 | 服务完回基地即结束 |

**必须断言的不变量（12 条，验收直接断言）**：见规格一成稿 §4.7（本设计 §9 与 §14.3 只列「测什么」，逐条守卫落点见 `docs`/迁移清单 MC-B06）。其中与本设计其余小节直接相关的是 F3 前缀载重（§5.5）、逐单 penalty（§4.3/§4.4）、暂存守恒与期末 0（§4.6）。

> **历史核算结论（保留，别拿它推现行行为）**：在单车单仓库模型下，中转站集散**不必然降低总距离**（干线里程下界同为 `⌈D/C⌉ × 2L`），当时的真实价值是「把超载从不可行变可行」——而规格一改掉「超载不可行」这条前提后，该收益本身也消失了。**报告里评价这类机制仍须用「可行性 + 停靠数/动作数 + 总权重」，不得宣称不实里程收益。**

### 5.7 增量式重规划（D22，2026-11-24 改为「顺序不变版重放」）

- **出处**：要求原文【实现提示 2】「触发路径重规划时采用增量式更新（仅调整受影响的路径段）」。
- **现行做法（规格二 §10 裁定 1 / ADR 0007）**：**停靠顺序完全不变**，只把上一版的**剩余停靠序列**按**当前边权重**重放一遍：
  - 时间、等待、逐单 penalty、前缀载重、逐单成本全部按新权重重算；
  - 任一 leg 不可达 ⇒ 该版不可行，退回**全量重规划**（`usedIncremental = false`）。
- **如实说明（裁定原文）**：**不重写 A→B 版的 leg 级增量**。旧 `replanIncremental`（「按停靠点切 leg、只重算受影响的 leg」）在新模型下**恒退全量**——那条链没有实现载体；局部性改由「重放 + §5.2 的有界 relocate」承担。因此 `usedIncremental` 的语义是「本次是否用了**顺序不变版重放**」，不是「是否只重算了受影响的 leg」。
- **强断言（本阶段核心测试）**：

  | # | 断言 | 说明 |
  | --- | --- | --- |
  | 1 | 全部停靠仍被服务，且**顺序与重规划前逐位相同** | 重放不重排 |
  | 2 | 未变的边权重下，**逐位时刻不变** | 重放的确定性 |
  | 3 | 总耗时 ≤ 重规划前（按变化后的耗时计） | 只可能找到更快的绕行 |
  | 4 | 若**没有任何边受影响**，结果与原路线逐位相同 | 幂等 |
  | 5 | 每段仍可达、仍回到基地 | 合法性 |

- **为什么不与全量重算比对相等**：全量重算会重新做 EDD + pair-insertion，**停靠顺序可能变化**，两者本就**不必相等**。把「与全量一致」写成断言是错误的——它会把一个正确的重放结果判为失败。全量只在**重放不可行**时兜底。
- **范围**：不再有「只适用于单趟」这条限制（「趟」已不存在）。重放对**任何**上一版剩余路线都适用；跨版必须带入在车货 `OnboardItem` 与暂存 `StashState`（漏带会让暂存货凭空消失，见 §4.6）。

### 5.8 订单分配（规格二 #30：类型感知三阶段）

> 代码落点：核心 src/core/RoutePlanner.cpp 的 planFleet / planFleetSequentialBaseline / aggregateFleet；界面与 CLI 同走这一处（--dump-plan 的 ALLOC/ASSIGN 是它的可核对视图）。

- **阶段一 · 聚类**：簇(order) = node(order.A).sub_network_id；A、B 跨网 ⇒ 跨簇单，单独成队列（不属任何簇）。sub_network_id == 0 的异常数据也并入跨簇队列并记 allocationLog，**不静默丢单**。手动新客户单必须继承最近邻节点的 sub_network_id（否则会落到「子网络 0」）。
- **阶段二 · 整簇指派 + 全排列枚举**：枚举全部「簇 → 车」排列（默认 3 簇 3 车 = 6 种，手写全排列），每簇订单交给该车跑**规格一的单车构造器**；候选按车队键 (Σpenalty, Σ策略权重, 均衡键, tieKey) 取优。簇数 > 车数时按簇货量降序取前 k 个各占一车，其余并入「货量最接近且仍可行」的车。
- **阶段三 · 有界跨车改派**：单请求 relocate，R ≤ 3 轮，**只动普通段**、EDD 序；两条接受条件**同时**成立才接受：① 车队键**严格变优**；② **完工耗时不得变差**。一轮无改进即停。每条被接受的改派都写 RelocateRecord（改派前后 penalty/权重/均衡/完工耗时），不变量 8 直接读它。
- **均衡度**：峰值利用率(v) = max_t 在车量_v(t) ÷ capacity_v；车队均衡度 = max_v 峰值利用率 − min_v 峰值利用率。分母口径按**全部车**（空车 utilization 记 0 并参与极差，否则「一台干活、两台空转」会被算成最均衡）。地位 = 决策键第三级 + 报告指标，**不作硬约束**。
- **顺序轮转基线**（planFleetSequentialBaseline，对照组不是候选方案）：订单 ID 升序、第 i 单 → 第 (i mod k) 台车、车辆序 = [vehicles] 行序；不跳车、不重分配、不做可行性预判。它的分配只由「订单 ID 升序 + 车队行序」决定，与策略/容量/窗口全部无关（不变量 9）。
- **边际代价 Δkey(order, vehicle)**：key(在该车插入后) − key(该车现状)，三元组按字典序比较；**必须用候选车自己的因子重放**。跨车新单的选车顺序（§6.6）按 Δkey 升序试车、首个可行即接受。
- **失败兜底链**：换车（枚举覆盖）→ 拆簇（仅此级触发并留日志）→ 规格一的降载/全量兜底 → 拒绝该单并报原因（不通过违反容量或先取后送去「凑」解）。
- **九条分配不变量（验收直接断言）**：① 每单恰好一台车（转运版例外：取货车 ≠ 送达车）；② 簇归属完备且互斥；③ 逐车前缀峰值 ≤ 该车 capacity（**禁止**用「总分配 kg ≤ 容量」）；④ 每车从自己的 start_node/发车时刻空载出发、回同一基地；⑤ 确定性，tieKey = 车辆 ID → 节点 ID → 订单 ID 升序；⑥ 时间用该车缩放后的耗时、等待/penalty 不乘；⑦ Σ 可加性与「完工耗时 ≠ 车时合计」；⑧ 第三阶段每条改派「完工耗时不变差」；⑨ 基线分配与策略/容量/窗口无关。
- **已如实记录的代价**：默认整簇不可分 ⇒ 均衡极差劣于轮转基线（三策略 0.54/0.85/0.76 vs 0.18/0.38/0.22）；距离/成本策略只赢了自身 Σ 目标、完工耗时仍劣于基线（429/449.5 vs 383min），只有时间策略在主口径上占优（378.2min）。这不是缺陷，是「整簇不可分」的结构性代价。

### 5.9 跨车转运（规格二 #28：整单 relay）

> 代码落点：Stop 的 transitUnloads / transitPickups、TransitLeg、kTransferMaxDwellMin、applyTransitLayer / buildTransitLedger；只有「已实际执行」的卸入进 GUI 转运账本。

- **它是什么**：任意车可在中转站整单卸下、**另一台车**可取走并送达。与降载的分界是**判据本身**：同一台车卸了又取回 ⇒ 永远算降载（OffloadLeg），不算转运；转运必须 inVehicleId ≠ outVehicleId。
- **TransitLeg（账本最小单位，两端都必填）**：orderId / stationId / kg（= 该单需求，整单不可拆）/ inVehicleId / inTimeMin / outVehicleId / outTimeMin。没有「只卸不取」的合法记录；期末必须为空（有「在站」行就是缺陷）。
- **时刻链与站内等待**：取货(A) ≤ 卸入(S) ≤ 取走(S) ≤ 送达(B)；dwell = outTimeMin − inTimeMin ≤ **60**（代码常量，不加配置键）。站无窗口、停靠零耗时；货在站里等多久不产生耗时/penalty，所以必须用**可行性**而不是指标管住它。
- **守恒三式**：C1 整单不可拆（同一 (站, 订单) 至多一笔未取走记录）；C2 任一站任一时刻 Σ卸入 − Σ取走 ≥ 0；C3 期末 0。C3 由构造保证：只产出「取走车在收工前送达」的方案，留站过夜不是合法计划。
- **绝不更差的可执行判据**：key = (Σ逐单 penalty, Σ策略权重用各车缩放后权重, tieKey)，**严格字典序更小**才启用；**完全并列 ⇒ 保留禁转运版**。本图 84.2% 点对存在精确零绕行站 + 停靠零耗时 ⇒ 转运版常常完全并列；若用「不更差即启用」会把默认数据改成大量零收益转运。
- **三条场景判据（固定顺序）**：① 跨簇订单（A/B 不同子网）；② 容量腾挪（禁转运版里前缀载重将超该车容量，即规格一会走降载/判不可行）；③ 紧急响应（禁转运版里某紧急单 penalty > 0）。「零绕行」按**当前策略权重**判。每类最多 R = 3 轮、每轮至多接受一个 key 最优候选；无更优即停。转运层**不改分配**：谁走哪台车仍归 §5.8。
- **紧急单最后手段通道（双门槛）**：只有「禁转运版里该紧急单 penalty > 0」才构造；接受当且仅当 ① **该单 penalty 严格下降** 且 ② 整计划 key 严格更优。与紧急硬优先共存的精确化：订单级 FIFO 记为「U_k 送达 ≤ U_{k+1} 取货」；「同刻至多一张紧急单在车」扩成「在车**或**在站（已取未送）」；取走车必须在自己的紧急段内完成该单取送。
- **十二条不变量**：转运段两端齐全且 in≠out；整单不可拆；守恒且期末 0；时刻链；dwell ≤ 60；两车各自前缀载重 ≤ 各自容量（停靠内先卸后装）；站停靠无窗口、不计 penalty、零耗时且计入停靠数；penalty 只记在送达车一次；A 停靠索引 < B；最终 key 严格小于禁转运版**或完全等于**（未启用），不存在「更差」；同输入同输出；重规划后无「上一版计划卸入但从未实际执行」的残留。
- **默认数据静态全不触发**（0 跨簇、每簇一批不超容量、初始无紧急单），这是「绝不更差」的最强经验证据；演示必须用「插入普通订单…」造一张跨簇普通单（§7.6）。

### 5.10 动态事件复调度（规格二 #27：单一原语 + 五级链）

> 代码落点：advanceFleetTo / rescheduleFleet / localReplanTwoVersion / chooseVehicleForNewOrder / affectedVehiclesForTraffic / affectedVehiclesForClosure / ExecutedTransitEntry；本层只做**计划**，不碰任何已发生的物理事实。

- **单一车队时钟 + 一个推进原语**：软件内时间只有一条轴；「推进一站」= 全队下一到达时刻的最小值、「推进一刻」= 下一事件刻。事件结算挂在软件时间前进上（§7.4），两种推进粒度必须看到同一串事件（A1–A7）。
- **局部重规划 = 两版比较**：R1 = 停靠顺序完全不变、只按新边权重重放；R2 = 剩余订单重跑规格一构造器。**采用 R2 当且仅当 R2 可行且 key(R2) < key(R1)**（严格并列保留 R1）。R1 不可行 ⇒ 本级失败，进入升级链第 ② 级。
- **五级升级链**：① 局部重排 → ② 跨车再分配 → ③ 全车队重调度 → ④ 降载/转运并列 → ⑤ 拒绝并报原因。每级都复用既有构造器/Δkey/转运层，不新增算法。「失败」= 该级产不出可行解（容量 + 可达 + 先取后送 + 紧急硬优先/FIFO 全成立）；窗口只影响 penalty，不判不可行。
- **受影响车集合**：路况 = 存在被改动边 e 使「e 在该车剩余路线上（有向、相邻两站）」且 e.increaseRatio ≥ thresholdRatio；封路 = 该车剩余路线**用到**被封闭的边（任一方向）。（GUI 的封路按钮显式跳过桥边，所以事件封路**永远**造不出不可达；不可达演示用手工删桥边。）
- **未受影响车的路线逐字不变**：只对被重算的车写回计划；不变量 5 读 rescheduleFleet 的 replanned 集合核对。
- **逐车紧急 FIFO（跨车并行允许）**：不存在「全车队同刻至多一张紧急单在执行」的断言；等价性守卫 A1–A7 比对两条推进路径的**事件日志逐字**与**逐车终态**。
- **已执行卸入是一等输入**：ExecutedTransitEntry{leg, order} 必须被继承，任一可行车可取走，期末 0；计划内**未执行**的卸入在重规划时全部作废，不得跨轮累积。**先降载后转运**（第 ④ 级的固定顺序）。
- **新订单选车**（§6.6）：候选 = 全部车按 Δkey 升序（并列按车辆 ID），逐个试可行插入，首个可行即接受；局部可行即接受，不做「局部 vs 全局两版取优」。
- **十四条复调度不变量**：见规格二 §6.11；现行守卫由 routeplanner_tests 的复调度族 + --self-check-actions 第 8 段 A1–A7 + cli 的 ALLOC 一致性承担。

## 6. 模块边界

核心层与 GUI 层严格分离。核心层不得 `#include` 任何 Qt 头文件，必须能用 g++ 独立编译并跑单元测试。

- **core**：图、节点、边、手写堆、Dijkstra、路径规划、约束检查。
- **io**：INI 解析、配置加载、图表示输出。
- **gui**：主窗口、画布、图元、权重标签、侧栏。
- **tests**：核心层单元测试（不依赖 Qt）。

核心层对外接口应满足 GUI 的只读查询需求（获取节点列表、边列表、当前路线）；GUI 通过调用核心层业务方法（规划、重规划、插入订单、增删节点边）触发计算，再根据结果重建或更新图元。

### 7.3 模拟模式与推进

- **两种模拟模式（并列、互斥，D24）**：`按站模拟`（原「Debug 模式」更名）与 `按时间模拟`（新增）放进**同一个 `QActionGroup`**，勾选其一自动取消另一个。
  - 两者都以固定 **1 秒/步**的节奏自动推进，区别只在「一步」的粒度：

  | 模式 | 一步的粒度 |
  | --- | --- |
  | **按站模拟** | 一站（调 `onAdvanceStop`，与手动「推进一站」同一状态转移点） |
  | **按时间模拟** | 一刻 = `event_interval_min`（调 `onAdvanceMoment`，进到下一个事件刻） |

  - 停止方式沿用「再点一次取消勾选」；**关闭后不再产生任何副作用**。
    ⚠️ 实现注意：两个动作放进 exclusive `QActionGroup` 后，**点已选中的那个不会取消勾选、也不发 `QAction::toggled`**，因此勾选状态必须只在 `QActionGroup::triggered` 一处收口，并在「再点当前模式」时显式 `setChecked(false)` + 停表。
  - **到达路线终点即自动停止**：停掉计时器、清除勾选，并只播报一次（不再空转刷日志）。播报分两种，**不可混同**：
    · 路线真的走完（计划可行且 `nodeIndex_+1 >= plan_.nodes.size()`）→「本次配送已完成，模拟结束」；
    · 计划不可行或为空 →「计划不可行或为空，模拟停止」。
    （`atRouteEnd()` 对两种情形都为真；若统一播成「已完成」，界面会同时写着「规划不可行」与「已完成」= 假成功。）
  - `--demo N` 的语义：执行 N 次「推进一站」；**由于推进本身会结算沿途事件刻，日志里也会出现 `[事件]` 行**——它不再是「纯推进 N 次」。
- **「推进一刻」语义（`onAdvanceMoment`）**：推进到**下一个事件刻** `T = nextEventTimeMin(当前软件内时刻, event_interval_min)`。
  - **必须逐节点重放**：依次走过 `T` 之前到达的每个节点，每个都调同一套 `arriveAt` / 停靠动作执行（取货 / 送达 / 降载 / 取回）；**绝不允许**直接把 `nodeIndex_` 跳到 `nodeIndexAtTime(plan_, T)` 再补一次状态——那会跳过沿途的送达与装卸记账。
  - **半路时车辆显示为所在段的起点**：推进后车辆位置取「最后一个到达时刻 ≤ T 的节点」，即车辆当前所在段（i → i+1）的**起点 i**（例：A→B→C 已过、正驶向 D ⇒ 停在 C）。`nodeIndexAtTime` 仅用于**显示与断言比对**，不用于跳过节点。
  - 每过一个事件刻**恰结算 1 个事件**（等级权重见 §8.1），并**每刻播报一行**（带该刻软件内时刻，如 `08:15`）。

### 7.4 事件结算挂在软件时间前进上（关键纪律）

- `onAdvanceStop` 与 `onAdvanceMoment` 在移动位置之后**都必须**调用 `settleEventsUpTo(now)`：只要软件内时间跨过了事件刻就补结算。这样两条路径看到**同一串事件**，与推进粒度无关。
- **`onAdvanceStop` 的结算时机（2026-11-24 精确化）**：在**移动到下一节点之前**，把本段区间内的每个事件刻**逐个结算**，且每个事件在**它自己的软件时刻**结算（此时车仍显示在所在路段起点）。**不是**「到达后再一次性批量结算」。
  - 理由：这是 A1–A7 等价性（一次推进一刻 == 逐个推进到同一时刻）成立的前提。批量结算会让两条路径在同一刻的 (位置, 时钟) 不同——实测路径 A 第 15 行即分叉、终态 23:35 vs 18:51。
  - 代价（如实记录）：事件密集的长跑**终点会保守后移**；`--plan-summary`（无事件）不受影响。
  - 守卫：`--self-check-actions` 第 8 段 A1–A7（两条路径各自重新加载配置、构造两个独立窗口，推进到路线终点后逐字比对事件日志与 A2–A7 终态）。

## 8. 配置文件契约

采用手写 INI 解析器，零第三方依赖。

### 8.1 节与字段

- `[general]`：
  - **模拟事件（D24，2026-11-24 口径）**：`event_interval_min`（事件刻间隔，默认 `15`，单位=**软件内分钟**）+ 四个**等级**键 `event_level_traffic` / `event_level_urgent` / `event_level_customer` / `event_level_closure`。
    - 等级取值：`extra_low` / `low` / `medium` / `high`（**不区分大小写**，无法识别即**报错**，不猜、不回落）。
    - 等级 → 权重由 `src/core/Config.h::eventLevelWeight` 的**固定表**派生：`extra_low=1 / low=3 / medium=9 / high=27`。**配置文件里不再出现任何权重数字**。
    - 默认值 `high / low / medium / extra_low` ⇒ **27:3:9:1（Σ=40）** ⇒ 概率 67.5% / 7.5% / 22.5% / 2.5%。
    - 缺键 ⇒ 回落到上述默认等级（合法）；写**非法等级** ⇒ 带行号报错。
  - **路况**：`traffic_change_ratio`（默认 `0.1` =「改 10%」）、`traffic_time_increase_min`（`0.2`）、`traffic_time_increase_max`（`0.5`）。
  - **退役键（出现即带行号报错 + 迁移提示）**：`event_weight_traffic|urgent|customer|closure`（→ 改用 `event_level_*`）、`service_time_min`（→ **停靠零耗时，本键不存在**）、`traffic_change_interval_sec`、`urgent_order_interval_sec`。
    - 白名单实现：`src/io/ConfigLoader.cpp::retiredGeneralKeyHint`。**字面串必须留在白名单表里**——删掉它等于让旧配置被**静默**接受成默认值（§4.7-⑨）。
    - 其余**未知键**仍按「忽略」处理（不报错），与「退役键必须报错」是两条不同规则。
- `[nodes]`：每行 `ID, type, x, y, name, sub_network_id`（6 列）。
- `[edges]`：每行 `from, to, distance_km, time_min, cost_yuan`（5 列）。
- `[vehicles]`：每行 `ID, start_node, capacity_kg, depart_time, time_factor, cost_factor`（**6 列**，`depart_time` 为 `HH:MM`）。规格一只有一行（V01）；契约按多行设计，§4.5。
- `[orders]`：每行 `ID, pickup, delivery, demand_kg, window_start, window_end, is_urgent`（**7 列**；`pickup` = 取货点 A **必填**，`delivery` = 送达点 B，`A ≠ B`）。

### 8.2 示例（与 `config/default.ini` 同形，取前几条）

```ini
[general]
traffic_change_ratio = 0.1
traffic_time_increase_min = 0.2
traffic_time_increase_max = 0.5
event_interval_min = 15
event_level_traffic = high
event_level_customer = medium
event_level_urgent = low
event_level_closure = extra_low

[nodes]
# ID, type, x, y, name, sub_network_id
W01, warehouse, 80, 160, 中央仓库A, 0
T01, transit, 380, 200, 中转站甲, 1
D01, delivery, 180, 90, 客户01, 1

[edges]
# from, to, distance_km, time_min, cost_yuan
W01, T01, 4.7, 4.7, 7.5
T01, D01, 3.6, 8.6, 4.3

[vehicles]
# ID, start_node, capacity_kg, depart_time, time_factor, cost_factor
V01, W01, 200, 08:00, 1.00, 1.00

[orders]
# ID, pickup, delivery, demand_kg, window_start, window_end, is_urgent
O01, D08, D01, 20, 08:00, 13:00, 0
O09, D01, D08, 20, 08:15, 14:00, 0
```

> **示例里的两个「坑」都是有意的**：① `[general]` **没有** `service_time_min`——停靠零耗时，写了反而报错；② O01 是 `D08→D01`、O09 是 `D01→D08`，这对**互逆环**正是 §4.7-① 那条「不变量 ⑦ 例外判据精确化」的由来（逐字执行「例外仅 FIFO」会把默认数据判成不可行）。

### 8.3 解析规则

- `#` 开头为注释；`[section]` 分节；逗号分隔字段；空行忽略。
- 时间 `HH:MM` 转为「相对当日 00:00 的分钟数」。
- 解析错误（缺节、字段数不符、类型错误）需给出**带行号的明确报错**，不得静默忽略。

### 8.4 规模约束（`default.ini` 必须满足）

- 节点 ≥ 30：仓库 ≥ 2、配送点 ≥ 15、中转站 ≥ 3
- **路径 ≥ 50，两个口径同时满足（D19）**：
  - **有向边数 ≥ 50**
  - **无向道路对数 ≥ 50**（即“把双向路算作一条”时也不低于 50）
- **必须含单向边（D18）**：至少数条单行道，使有向性可被观察
- **单笔订单货量 < 最小载重上限**：这是**新的**载重约束（`OrderExceedsCapacity` 是唯一与载重相关的不可行）。旧条目「**总订单需求 ≤ 车辆载重**」**已删除**——它与前缀载重模型直接矛盾：规格一的默认数据 516kg 需求 vs 200kg 车是**正常数据**，不是需要规避的场景。
- 每张订单的 `pickup`/`delivery` 都必须存在且不相等（A ≠ B）——数据加载时校验（订单十条校验之一）。
- **每个中转站至少归属 1 个配送点**（`sub_network_id` 非 0 的配送点）。理由只剩界面分组与降载选站的**可达性**：没有下属配送点的中转站永远不会有货被卸到那里，该行会恒显示 0。
- **车辆 `depart_time` 应早于或等于各订单窗口起点**：这是**数据质量建议**，不是解析校验——违反不会加载失败，只会让默认演示大面积超时（§14.3 的「④ 迟到订单必须是少数」会红）。

### 10.1 STL 使用边界（D4 落地细则）

> **口径修订（2026-09-26，用户经任课教师确认）**：原表述是「核心算法逻辑严格禁用 STL，
> `min` / `max` / `swap` 也要自行内联」，**偏严**。现放宽为：
> **只有「把算法主体交给 STL」才禁止**——核心算法内部使用 `std::min` / `std::max` /
> `std::swap` / 迭代器 / 容器这些**不构成算法主体**的设施完全允许。
> 下表与禁止清单已按此更新；`src/core/Random.h`、`Traffic.h` 里"禁止类库"的旧注释理由也一并修正。

**判据一句话：手写「算法」，不手写「轮子」。**

| 范围 | 是否可用 STL | 说明 |
|---|---|---|
| 课程考点的**算法主体** | ❌ **禁止交给 STL** | 排序、堆、二分查找、最短路松弛、贪心选择、图遍历的判定逻辑必须自己写——不得用 `std::sort` 代替自实现的排序，不得用 `std::priority_queue` 代替手写堆 |
| 核心算法**内部**的辅助设施 | ✅ 可用 | `std::min` / `std::max` / `std::swap` / 迭代器 / 容器访问——不构成算法主体 |
| 核心**数据结构** | ⚠️ 手写 | `MinHeap` 必须自实现（**不得用 `std::priority_queue`**）；邻接表的遍历/查找逻辑手写，边表**存储**可用 `std::vector` |
| 核心**存储容器** | ✅ 可用 | `std::vector` / `std::string` / `std::map` 等容器不受限 |
| `io` / `tests` / `gui` / 日志 / 字符串格式化 / 任何辅助功能 | ✅ 积极使用 | 不受限，GUI 可用全部 Qt |

**核心层禁止的 STL 算法**（把算法主体外包出去的那几个）：
`std::sort`、`std::partial_sort`、`std::stable_sort`、`std::nth_element`、
`std::min_element`、`std::max_element`、`std::lower_bound`、`std::upper_bound`、
`std::priority_queue`、`std::make_heap` / `std::push_heap` / `std::pop_heap`。

**明确允许**（不在禁止之列）：`std::min` / `std::max` / `std::swap` / 全部容器与迭代器
（`std::vector`、`std::map`、`std::string`…）。

**禁止：**

- 用 STL 代替课程考点的算法主体（见上表与禁止清单）。
- 核心层 `#include` 或链接任何 Qt 头文件/库。
- 使用第三方 JSON/INI 解析库。
- 同学间抄袭。

## 14. 测试与开发流程约定

### 14.1 期望值必须先由预言机计算（强制）

**规则：TDD 测试中的期望值不得由人工手工推算。**

起因：实现 `Dijkstra` / `RoutePlanner` 期间，人工推算期望值**连续出错三次**（返回段绕经中转站、`W→D2` 最短路非直达、图与测试用错单位），每次都是"测试红了但实现是对的"。这类算术属于高频易错，必须脚本化。

**工具**：`tools/oracle.py`

```bash
python3 tools/oracle.py            # 打印各测试夹具的全部期望值，供抄入 C++ 测试
python3 tools/oracle.py --check    # 自检；已接入 ctest（oracle_selfcheck）
```

**必须方法独立**（否则构成 `tdd-zh` 明令禁止的**同义反复**——期望值由与代码相同的方式重算，凭构造必然通过，永远无法与代码产生分歧）：

| 计算内容 | 被测实现 | 预言机的独立方法 |
|---|---|---|
| 最短路 | C++ Dijkstra + 手写堆 | **穷举所有简单路径取最小**（暴力法） |
| 时间模型 | `RoutePlanner` 代码 | 直接按 §4.3 定义转写 |

预言机只用于**离线生成测试字面量**：不参与构建、不被交付程序引用。C++ 测试中仍是硬编码字面量，运行时保持独立。

### 14.2 测试数据必须由脚本生成并自检（强制）

**规则：交付用的测试数据（`config/default.ini`）不得手工维护，必须由生成器产出且通过自检。**

起因：`default.ini` 原本出自一个写在 `/tmp` 的一次性脚本，脚本未入库。后果是这份数据**无法复现、无法审计、无法参数化重生成**——这正是两个真实数据缺陷（巡游 28 小时、成本与距离线性相关）得以产生的土壤。

**工具**：`tools/generate_dataset.py`

```bash
python3 tools/generate_dataset.py           # 重生成并与已提交文件逐字节比对 + 自检
python3 tools/generate_dataset.py --write   # 自检通过后写回
python3 tools/generate_dataset.py --check   # 只对已提交文件做自检
```

三条保证：

1. **产物可证明**：默认模式下重生成并与 `config/default.ini` **逐字节比对**。数据被手工改动过、或生成参数已变更，都会立刻失败并打印 diff。
2. **生成即自检**：规模（≥30 节点 / ≥2 仓 / ≥15 配送点 / ≥3 中转站 / ≥50 边）、端点存在性、**往返可达性**（有向图「能去」不等于「能回」）、**最大单笔货量 < 最小车辆载重**（规格一 Q1；旧条目「总需求 ≤ 载重」已删除——它与前缀载重模型矛盾）、**cost/dist 比值不得恒定**（三策略分化的必要条件）。
3. **接入 ctest**：`dataset_selfcheck`。

> 生成器自检是**必要预警**而非充分证明（例如它无法验证"单车辆一天跑得完"）。充分验证在 `integration_tests.cpp` 的数据质量不变量中。

### 14.3 数据质量不变量：用断言取代"人眼看输出"

**规则：对真实数据，除结构断言外还必须断言其"有效性"，尤其是上面两个缺陷的对应性质。**

起因（关键教训）：两个数据缺陷**单元测试全绿**、一路漏到集成阶段，最后是靠**人眼看 `printf` 输出**发现的。也就是说——同样的缺陷重来一遍，测试依然会全绿通过。这是流程缺陷，不是运气问题。

### 14.4 独立性的边界（易误用）

| 对象 | 要求 | 理由 |
|---|---|---|
| **算法** | **必须独立** | 否则构成同义反复——期望值由与代码相同的方式重算，凭构造必然通过 |
| **数据** | 应**单一真值源** | 两份定义必然漂移 |

> 已知遗留：单元测试小图目前仍在 C++ 与 `tools/oracle.py` 中各写一遍（双份定义）。风险可控——夹具漂移会让测试**变红**而非静默通过，只是诊断信息不够直观。后续可将小图外置为共享数据文件，两边同源读取。

### 14.5 GUI 的验证方式（离屏渲染 + 目视）

GUI 层不适用前几层的验证手段：渲染错误（箭头画反、标签遮挡、坐标错位）单元测试根本抓不到，
而 Qt widget 点击级自动化（QTest）对课设性价比极低。约定如下：

| 层次 | 方式 |
|---|---|
| 纯逻辑（如「某条边是否在规划路径上」） | 单元测试（已抽出 `isEdgeOnRoute`，被 GUI 高亮与 `needsReplan` 共用） |
| 渲染层 | **`--render` 离屏渲染成 PNG，由 agent 读图目视确认** |
| widget 点击级自动化 | 不做 |

```bash
QT_QPA_PLATFORM=offscreen ./build/app --render out.png --plan distance
QT_QPA_PLATFORM=offscreen ./build/app --render out.png --labels all --weight cost
```

`--render PATH` / `--width` / `--height`。

> **箭头被画到节点内部而完全看不见** —— 那段几何在该示例里是配合「线段 p1 为终点」的相反

### P8 多趟模式下的紧急订单优先（真实回归）

引入多趟后，`insertUrgentOrder` 的"紧急订单优先"失效：算法按**簇**逐个处理，
紧急订单若落在靠后的簇里就会被排到最后，违反 E3「优先满足紧急订单」。

先尝试的修法（让含紧急订单的簇优先处理）**不够**：若两个簇各含紧急单，
它们仍会被各自簇的行程隔开，扁平停靠序列里不连续。

最终修法：**紧急订单单独成趟、最先执行**——先把全部未服务紧急订单按载重分批，
每批一趟直接从仓库送达后返回，再按原逻辑处理其余订单的簇。
这既满足「优先满足紧急订单」，也符合现实（紧急单应立即派车）。

货量从仓库跨到某簇所在区域，是任何方案都躲不掉的干线运输。每跨一次最多带走

**直接送达**恰好达到这个下界；**经中转站**同样是这个下界，却额外产生

### P13 顺路寄存（前置储存点机制）——已实现

用户第 10 轮确认按**安全版**实现：只卸在**回程路径上的站**，且**必须是该站所服务簇的货**。

**关键简化**：寄存发生在规划窗口**之前**，因此不需要在任何行程里记一笔装卸，
直接体现为站里的**期初存货**即可。整个机制因此只有几十行。

`replan` 新增两个可选参数：

- `initialStock`：各站期初存货（前置储存点）
- `onboard`：车辆**此刻已载在车上**的货（`OnboardItem{nodeId, kg}`）

处理顺序（`multiTripPlan`）：

1. **先空跑一版**，得出"本次回仓库**之前**会服务哪些停靠点"；
2. 在途货里**没被这一版送掉**的部分，若其所属簇的中转站满足
   `dist(出发地,站) + dist(站,仓库) <= dist(出发地,仓库)`（即**站在回程路径上**），
   就把它并入期初存货 —— **零绕路**；不满足则原样带回去；
3. 算两版（不许用站 / 允许用站），**取更优者**，用站版 penalty 更差则一票否决。

**必须"先空跑一版"的原因**：把**全部**在途货都寄存是错的——车马上就要送掉的那些
不该卸下来。所以要按"本次回程前是否来得及送"来筛。

实测（`testOnboardSurplusIsBankedEnRoute`，载重 50kg、订单各 20kg、车在 D1 载着 D2 的货）：

```
第1趟: D1 T W                       <- 回仓库路上经过 T，顺路寄存 20kg（零绕路）
第2趟: W T D1 D2 D1 D3 D4 D3 D1 T W
T 峰值 20.0kg  期末 20.0kg          <- 存货留下，供后续使用
```

**触发条件**：不是常规直送——常规直送时车**空车**回仓库，没有可寄存的货。
真正触发的是**途中重规划**：车正在簇内执行某趟、车上载着尚未送达的货，
而新规划要求它先回仓库（例如插入远端紧急订单）。此时那部分货才"来不及送"。

**"积少成多"的回路**：GUI 用 `stationStock_` 保存最近一次规划的期末存货，
下一次重规划时作为 `initialStock` 传回（三处规划出口都会回写）。
这样寄存的货不会凭空消失，会跨重规划累积，直到被某次规划当作前置仓库用掉。

### P16 向导支持"只跑一关"

用户要求：脚本开头能选"跑全部"还是"只跑某一关"，以便对某项做快速回归。

- 交互式：脚本开头提示 `输入 0 = 全部；关卡号 / 关卡名 / 名字片段 = 只跑那一关`

**守卫**（2026-11-17 已随向导退役删除）：`tools/check_wizard_stage_pick.sh`（接入 ctest `wizard_stage_pick`）

关名 -> 对应关；片段唯一匹配 -> 对应关；不存在的名字 -> 无法识别；

- 把 `--only` 校验挪回终端检查之后 -> 报"没有报无法识别（可能被终端检查抢先了）"

### P17 第 13 轮：Debug 下"车在仓库与客户间反复跳跃"

**用户反馈**：Debug 时日志不断出现"→ 上一版为多趟方案，退回全量重算"，
车在仓库与 D01 间反复跳跃。

**已查到并修好的**：

1. **重规划总让车先跑回仓库**：规划器完全不知道车上还载着货，于是每次都按
   "货都在仓库"排线，第一段就变成"回仓库"。已加"**在途货先送掉**"：
   紧急订单 -> 在途货（从**当前位置**直接出发）-> 其余按簇分批。
   实测轨迹从"D01→W01→D01"变成正常前进 D01→D02→D03→…

2. **同一客户被送两次**：新增的"在途货"批次是从**全量 candidates** 里取的，
   而紧急批次可能已经把其中一些客户送掉了，于是出现两趟完全相同的行程
   （车在原地打转）。已改为从**剩余池**取并按节点归并。

3. **中转站补货趟造成的往返**：车一旦停在站里，规划就排出「站 -> 仓库 -> 站」
   的补货趟。结合实测（该路由全面劣于直达：198.2km/13 趟 vs 178.2km/6 趟），
   已**关闭中转站的路由角色**，只保留它的**库存角色**（顺路寄存 + 界面展示）。

4. **单关模式形同虚设**：`stage_wanted` 函数写好了，却**没有任何一关调用它**，

### P19 第 15 轮：重规划必须继承两条"既定事实"

用户的观察很有道理：**重规划会重建整个计划，但有些事在物理上早已确定，
不该被抹掉**。据此实现两条语义继承：

**① 本趟装载：驶离仓库后冻结。**
一旦车离开仓库，这一趟装了多少就是既成事实；重规划把它重算会得到与事实不符的值
（实测重规划后从 190kg 变成 160kg）。现在用 `tripDeparted_` 显式记录"本趟是否已驶离"：

> 不能用"车辆是否停在该趟起点"来判断——重规划后车辆恰好位于新计划的起点，
> 会被误判成"还没出发"。（这正是我第一版写错的地方。）

**② 趟号：用"已完成趟数"做偏移，接着往下编。**
记录 `completedTrips_`（回过几次仓库 = 跑完几趟），显示时
`趟号 = completedTrips_ + 当前计划里的趟号`。
于是跑过 2 趟之后，最上面一行显示「第 3 趟」而不是又回到「第 1 趟」。

实测（纯推进 50 步）：

```
已完成趟=0 首行趟号=第 1     已完成趟=2 首行趟号=第 5
已完成趟=1 首行趟号=第 3     已完成趟=4 首行趟号=第 9
```

**守卫**：
- `--self-check-actions` 新增：驶离 → 触发重规划 → 断言本趟装载未被改写
  （变异：忽略"是否已驶离" → 报"重规划后 160kg，之前 190kg"失败）
- `--ui-probe` 新增：停靠明细的趟号必须沿行**单调不减且 ≥ 1**，
  不允许"已完成的趟又冒出来"或编号倒退

**仍未解决**：`completedTrips_` 在 Debug 里增长很慢，因为车辆受"经过仓库时翻向"
那个未修问题影响、迟迟跑不完一整趟。该问题在 §16 P17 已记录。

### P22 修正：趟号仍未继承已完成趟数（人工测试第二次反馈）

用户反馈：**路线信息的「共 X 趟」和停靠明细的「趟」还是没有继承已完成的趟数。**

实测确认（`--demo`）：

```
TAG 17 已完成趟=0 位置=W01   明细首/末行=第 1/第 5   共 5 趟
```

车**已经回到仓库了**，`已完成趟` 却仍是 0，于是所有趟号永远停在「第 1」。

**根因**：换计划时我用 `completedTrips_ += currentTripIndex()` 合并。但车停在仓库时，
它的 `nodeTripIndex` 指向的正是**它刚跑完的那一趟**（该趟的终点就是仓库），
所以 `curTrip` 读出来还是 0 —— 少记一趟，趟号就再也不前进。

**修法**：新增 `tripsToMergeOnReplan()`——
- 车**在仓库且非初始位置**（`nodeIndex_ > 0`）→ 刚跑完的那一趟已结束，合并 `curTrip + 1`
- 否则（途中）→ 当前这一趟未跑完，只合并 `curTrip`
- 计划尚未开始（`nodeIndex_ == 0`）→ 合并 0

修正后实测（`--demo 20`），三处完全一致：

```
已完成趟=0  明细首/末=第 1/第 6   共 6 趟   车辆 第 1 / 6 趟
已完成趟=2  明细首/末=第 3/第 7   共 7 趟   车辆 第 3 / 7 趟
已完成趟=5  明细首/末=第 6/第 10  共 10 趟  车辆 第 6 / 10 趟
已完成趟=8  明细首/末=第 9/第 13  共 13 趟  车辆 第 9 / 13 趟
```

**守卫**：断言「停靠明细**末行**的趟号 == 已完成趟数 + 计划趟数」。
这条把"明细的偏移"与"共 K 趟的偏移"绑在一起——两者只要有一个漏了偏移就对不上。
反向验证：撤掉明细的偏移 → 报「实际 5，期望 18」失败。

### P23 修正：「本趟装载」被冻结过头，换趟后不刷新

用户反馈：趟号问题仍在，且**「本趟装载」并未真正展示本趟载重**。

### P24 Debug 下趟号仍错：查明是**轨迹本身坏了**，不是显示逻辑

用户反馈：**共 X 趟、第一行趟数在 Debug 模拟中仍错，但手动推进没问题。**

这个"手动对、Debug 错"的对照恰好锁定了根因。我用**真 Debug 定时器**跑（`--demo` 的调用
顺序不同，会掩盖它：`--demo` 是"先推进再重规划"，Debug 是"先重规划再推进"）：

```

tick=12 回仓库=0 已完成=0 明细首行=第 1 | 共 5 趟    <- 相对编号重启，退回去了
```

**但 Debug 的症状没有因此消失，而且查出了更硬的事实**：

> 整整 28 个 tick，**回仓库 = 0** ——车一次都没回过仓库。

而它同时送达了 17 站。**载重 200kg 的车送完 740kg 的货却从不回仓库装货，
这在物理上不可能** —— 说明 Debug 下重规划产出的**轨迹本身是坏的**。

这条正是 §16 P17 记录、我尚未修的那个问题（车经过仓库时翻向 / 在途货状态由计划反推）。
**趟号显示只是它的下游症状**：物理轨迹不回仓库，就没有"完成的趟"可累计。

**结论与下一步**：本轮只交付了"偏移量改用物理事实"这一处正确性改进（手动路径不受影响，
已实测），**没有再去糊显示层**。要真正修好 Debug 下的趟号，必须先修 P17——

让轨迹重新变回"回仓库装货"的正常形态。

### P25 第 17 轮：从数据流上根除「重规划改写物理事实」

用户要求："作为一个要继续维护的项目，从基层将其完全修复，梳理数据流保证其不会再出此问题。"

#### 诊断：一类缺陷，反复出现

本项目在**十几次**反馈里反复栽在同一件事上：**某个物理事实被"从当前计划反推"**，
于是重规划一重建计划，它就变错。已发生过的全部实例：

| 症状 | 被反推的事实 |
| --- | --- |
| 趟号塌成「第 1 趟」 | 车辆进度 ← 计划内游标 |
| 「已送达 N 站」归零、「停靠 N 站」缩水 | 送达计数 ← `plan_.stops.size()` / `stopCursor_` |
| 「总 penalty」往回跳 | 已发生的惩罚 ← `plan_.totalPenaltyMin` |
| 「本趟装载」被重算 | 本趟装载 ← `plan_.trips[t].loadKg` |
| 在途货被反复寄存、库存单调膨胀 | 车上货 ← 从计划的未走完停靠点反推 |
| **车在各簇之间"瞬移"、28 tick 不回仓库** | 同上 |

最后一条是**根因**：因为"车上有什么货"是从计划反推的，车经过仓库那一刻算出"车上没货"，
下一刻新计划又把原计划的货重新分派到另一个簇 —— 于是车永远不回仓库装货，
却送完了 17 站。**载重 200kg 的车送 740kg 的货、中间不装货，物理上不可能。**

#### 修法：一个唯一的物理状态源

新增 `MainWindow::VehicleState`，作为**所有物理事实的唯一权威来源**：

```
atNodeId / atTimeMin          此刻在哪、几点
loadKg / onboard              车上具体是哪些货（**显式列出**，不再反推）
tripNumber / tripLoadKg       正在跑第几趟、本趟出发时装了多少
departed / completedTrips     本趟是否驶离、已跑完几趟
servedStops / incurredPenaltyMin / deliveredLate   累计量
```

**规则写进头文件注释**，供后续维护遵守：

> - 只有车辆**真的做了什么**才能改它 —— 装载 / 到达 / 送达，全部收敛到四个状态转移：
>   `loadForCurrentTrip()` / `arriveAt()` / `deliverAt()`，且只由 `onAdvanceStop()` 触发；
> - 重规划只**读**它，作为输入喂给规划器；`plan_` 只描述"接下来怎么走"，
>   不作为任何**已经发生**的事实的依据。

原来散落的 10 个部分重复的字段（`depotArrivals_` / `completedTrips_` / `servedStopsBase_` /
`currentTripLoadKg_` / `tripDeparted_` / `incurredPenaltyMin_` / `deliveredLate_` /
`bankedNodeIds_` …）全部并入 `state_`。

#### 顺带了结「顺路寄存」

状态显式化之后暴露了一个**根本矛盾**：中转站已经不参与路由（第 13 轮实测更差），
那么"寄存到站里"的货**再也没有路径被取出来用** —— 只会在"车上 ↔ 站里"空转，
站内存货单调膨胀并污染后续规划（实测 870kg）。

因此**寄存机制一并移除**：中转站不再产生任何存货。核心不再寄存，GUI 不再维护站内库存，
测试 `testOnboardSurplusIsBankedEnRoute` 改写为 `testTransitNeverHoldsStock`。

#### 效果（真 Debug 定时器实测）

```
tick=3   已完成趟=0  明细首行=第 1  共 6 趟  第 1/6 趟  本趟装载 190
tick=12  已完成趟=1  位置=W01      明细首行=第 2  共 6 趟  第 2/6 趟  本趟装载 196   <- 回仓库了
tick=27  已完成趟=2  明细首行=第 3  共 6 趟  第 3/6 趟  本趟装载 178   <- 又换趟
tick=39  已完成趟=2  明细首行=第 3  共 3 趟  第 3/3 趟  本趟装载 178
```

**车恢复成"回仓库装货"的正常轨迹**，趟号 / 装载 / 已送达 / 停靠总数全部正常。

#### 守卫（结构性，全部反向验证过）

1. **重规划绝不改写车辆状态**：快照 `state_` → 依次走**三条**重规划路径
   （路况 / 插单 / 工具栏「重新规划」）→ 逐项断言趟次、已完成趟数、已送达、已发生 penalty、
   车上货量都没变。
   - 变异：让 `replan()` 从计划反推已送达 → 报「4 -> 0」失败
   - 第一版只测了路况与插单两条路径，**漏掉了 `replan()` 本身**（正是我这些轮反复漏的地方）
2. **轨迹必须正常**：每 tick 都重规划的情况下，车也必须在若干步内回仓库装货一次
3. 原有守卫（本趟装载不得被改写、趟号三处一致、停靠总数不缩水、站内存货不增长）全部保留

### P26 第 18 轮：车"送它没装在车上的货"——装载与计划脱节

用户反馈 `共 6 趟 -> 共 3 趟`。查下来**不是语义误读，是物理不自洽**：

```
tick=48  已完成趟=2  已送达=25站  已送=740kg  车上=0kg
         已送/(已完成趟×载重上限) = 1.85      <- 2 趟最多送 400kg
```

**追查出三个独立缺陷**：

**① 送达判断与"计划里的停靠下标"失同步**。只看 `nodeIsStop[i] == true`，
于是在下标错位时会拿**另一个停靠点**去卸货 —— 扣错货。已加校验：
下标必须与 `plan_.nodes[nodeIndex_]` **对上**才认作送达。

**② 到仓库后装错了趟**。`nodeIndex_` 在车停在仓库时指向的是**刚刚跑完的那一趟**
（该趟终点就是仓库），拿它去装货等于装上一趟已经送完的货 —— 空车出发。
改为**显式给趟号**：`loadForTrip(justArrived ? cur + 1 : cur)`。
（与之前"车在仓库时趟号读错一趟"是同一个坑，第三次出现了。）

**③ 计划换了，车上的货没跟着对齐**。这里要**区分两类东西**：
- **事实**（本趟出发时装了多少 `tripLoadKg`、已送达、已发生 penalty、跑完几趟）——
  重规划**绝不允许**改写；
- **决策**（车上此刻该有哪些货）—— 必须与计划的当前趟一致才**可执行**，
  否则就会出现"送车上没有的货"。新增 `reconcileOnboardWithPlan()` 在每次换计划后校准。

**效果（真 Debug 定时器实测）**：
- 空车送达 **4 次 -> 0 次**
- 每趟送出的货量 / 载重上限 稳定在 0.5–0.8（此前达 1.85）

**守卫**：
- 「不得送出车上没有的货」——`state_.offloadedWithoutGoods` 计数，断言真实流程（每 tick
  重规划）中为 0。
  **诚实说明**：这条守卫**没能通过变异验证**（把装载改回装错趟，它仍通过）。
  它是一道**回归检查**，不是有牙齿的守卫。
- 「重规划不得改变本趟出发时的装载量」——守的是**事实**（`tripLoadKg`），
  不再守"车上现有货量"（那是决策，允许被校准）。

**遗留（已定位，未修完）**：刻意"**连续推进而不重规划**"的合成路径仍能构造出
1 次空车送达。真实流程（每 tick 重规划）实测为 0。根因是换计划与重新装载之间
仍有一处时序缝隙，尚未完全消除。

### P27 第 19 轮：趟次标签改为"三段式"，消除「共 K 趟」的歧义

用户反馈：Debug 一开始显示"共 6 趟"，跑一会儿变成"共 3 趟"。查明根因是物理不自洽


向导第 3 关同步说明三者口径不同，**别把 K 当成"整趟配送总共几趟"**。

### P28 第 20 轮：撤掉我上一轮引入的 `reconcileOnboardWithPlan`（它自己就是那类缺陷）

用户反馈「本趟载重还是没有随趟数正确更新」。实测真 Debug 定时器：

```

tick=12  趟号=1 已完成=0 车上=196kg | 本趟装载：190 kg    <- 车上 196 > 本趟装载 190
tick=36  趟号=1 已完成=0 车上=0kg   | 本趟装载：190 kg
```

**趟号 42 个 tick 都停在 1**（车没回仓库），`车上` 在乱跳（100→42→196→138）。

**根因是我上一轮（P26）加的 `reconcileOnboardWithPlan()`**：它每次换计划都把

### P29 第 21 轮：趟次三段的口径必须自洽

用户提问：路线信息的趟次是否满足 **已完成 n / 当前 n+1 / 总趟数 >= n+1**？

| 段 | 来源 | 是否满足 |
| --- | --- | --- |
| 已完成 N 趟 | `state_.completedTrips` | n ✓ |
| 当前第 M 趟 | `state_.tripNumber`，代码里即 `completedTrips + 1` | n+1 ✓ |
| ~~本计划共 K 趟~~ | `plan_.trips.size()` —— "**本次规划还要跑几趟**"，与已完成无关 | **可 < n+1 ✗** |

```
趟次：已完成 N 趟 · 当前第 N+1 趟 · 全部完成约需 T 趟      （T = 已完成 + 本计划还需）
```

**守卫**：断言界面文本满足 `当前 == 已完成 + 1` 且 `总趟数 >= 当前`。

> 把第三段改回 `plan_.trips.size()`（也就是把 bug 放回去）**它照样通过**，

### P34 第 26 轮：模拟事件改由**软件内时间**驱动（口径变更 D24）

**现象（用户原话要点）**："模拟路况**未按软件内时间**触发，而是以两种错误方式触发：① 界面无操作时**随系统时间**触发；② Debug 模式中**每次推进就触发**。"

**两种错误触发的根因（对照 §1 的代码证据）**：

| # | 根因 | 位置（当时实测） |
| --- | --- | --- |
| ① | **真实秒级定时器** `trafficTimer_` 按 `traffic_change_interval_sec`（默认 30 **真实秒**）触发 `onSimulateTraffic`：**界面无操作也照跑**，与软件内时间完全脱节——游戏内可能才过去 1 分钟，真实时间已抽了好几轮路况 | `MainWindow.cpp` 的 `trafficTimer_` / `onTrafficTick` |
| ② | `onDebugTick` **每个 tick 无条件**调 `onSimulateTraffic`，紧急单另按 `urgent_order_interval_sec` 节流、封路每 20 tick 一次 | `MainWindow.cpp` 的 `onDebugTick` |

两者的共同后果：**事件密度由"推进按钮被按了多少次 / 真实过了多少秒"决定，而不是由软件内时间决定**——于是"到达密集客户时高频触发、跑长途时长时间不触发"，与需求"跑长途不会长时间不触发"直接冲突。

**新模型（D24，用户拍板）**：一律按**软件内时间**。每 `event_interval_min`（默认 **15min**）一个**事件刻**，每刻**恰抽 1 个**事件；权重
`event_weight_traffic=10 : event_weight_urgent=3 : event_weight_customer=1 : event_weight_closure=1`（合计 15）。
触发由"**软件时间前进**"驱动，**与推进粒度（一站 / 一刻）无关**。到路线终点自动停止模拟。
GUI 侧：「Debug 模式」更名「**按站模拟**」，新增互斥的「**按时间模拟**」（1 秒/步）与「**推进一刻**」。

**纪律：事件结算必须挂在软件时间前进上（等价性断言的前提）**——

- 「推进一刻」与「逐个推进一站到同一时刻」这两条路径，**必须看到同一串事件**；否则一次推进一刻的结果 ≠ 逐个推进的结果。
- 因此**不能**只让「推进一刻」结算事件、而「按站模拟」不结算：那两条路径会抽到不同次数的事件、走不同的重规划（路况事件会触发重规划，进一步改写 `plan_`），等价性断言**必然失败**。
- 正确做法：维护"下一个未结算事件刻" `nextEventMark_`，在 `onAdvanceStop` 与 `onAdvanceMoment` 移动位置之后**都**调 `settleEventsUpTo(now)`（`now = state_.atTimeMin`），只要软件内时间跨过事件刻就补结算。抽签随机源复用窗口既有 `rng_`，且**每次事件恰消耗一次抽签**，两条路径的抽签次数与顺序才一致。
- 一次 `onAdvanceStop` 若跨过多个事件刻（长途 leg），`settleEventsUpTo` 会连抽多次——这是**正确**行为。事件执行可能触发重规划，故推进循环的条件必须每轮**重新读取当前 `plan_`**。

**代价（如实记录，用户明确裁定）**：要求原文【实现提示 2】的「每 **30 秒**修改 **10%** 路径」这一**字面点被主动放弃**：30 秒口径改由软件内 **15min** 事件刻承担；"改 10%"保留为 `traffic_change_ratio = 0.1`。
**要求原文与 `docs/课设要求整理.md` 一律不动**，偏差只记在本节与 `docs/功能实现清单.md` H3。

**本轮落地范围（诚实口径）**：核心层 `src/core/SimEvent.{h,cpp}`（`SimEventKind` / `EventWeights` / `pickEvent` / `nextEventTimeMin`）、`RoutePlanner::nodeIndexAtTime`、`tests/simevent_tests.cpp` 与配置键 `event_interval_min` + 四个权重（`config/default.ini`、`ConfigLoader`）已落地；GUI 侧（删 `trafficTimer_`/旧 `onDebugTick` 触发、更名、新增「推进一刻」「按时间模拟」、事件播报）**本轮待收尾**。`traffic_change_interval_sec` / `urgent_order_interval_sec` **此刻仍在配置与解析器中**，随收尾一并移除——**不要读成已删除**（见 §8.1）。

### P35 第 27 轮：紧急单「缓冲库存就地满足」（D23 修订）

**起因**：用户提出「满载出仓 → 返程顺路寄存 → 紧急单就近取用」。四轮商议（含可复现探针）
逐条否证了原始论证的前提，最后收敛到一个**窄版本**：常规趟不进站、中转站只服务紧急单。

**实测（探针；对 `HEAD = db89d18` 的源码树可复现）**：默认数据下返程盈余恒为 0（三策略 6 趟）；
回程「顺路」只 4/6 趟成立（`time` 权重下第 5 趟绕 **+10.00km**）；读法 2（仓库可发缓冲货）
站内可攒 **434/434/438kg**；站方案对一次紧急单省 **3.0~16.1km**（11 组全为正）；而「从站取货
送**普通**客户」8/25 更差、最多 +10.00km、0 个更好——这正是"常规趟绝不进站"的量化依据。

**实现（T1–T5，四个提交）**：`25fa17e` T1 数据与签名穿透（零行为变化）→ `ae2d7e7` T2 生产者
（满载 + 顺路寄存）→ `698b026` T3 消费者（三链 + 两版取优 + penalty 一票否决）→ `0a4532b` T4
界面与 `VehicleState`（权威库存 + 面板「当前库存」列）。

**本轮踩到并修掉的真实缺陷**（都是"想当然"型，逐条留在这里以免重犯）：

1. **寄存落账判据改了三次**。①按「到达时刻恰好等于计划时刻」：一趟去程回程都经过同一个站，
   且重规划会重建趟结构与下标 ⇒ **几乎不可能命中**（实测跑完全程站内库存恒为 0）；
   ②按「整份计划里最后一次经过该站」：同一个站在**后续趟**里还会再出现 ⇒ 永不成立；
   ③最终「**本趟内**最后一次经过该站」（按 `nodeTripIndex` 限定本趟）+ 已落账键去重，才成立。
2. **仓库处先装载再落账**，会把刚跑完那趟的 `bufferKg` 覆盖成下一趟的量 ⇒ 落账必须排在装载之前。
3. **self-check ④ 原本按固定的「计划节点数」推进**：推进中事件会触发重规划（新计划从当前位置
   重新起算，游标归零），事先算好的步数随即失效。T4 让 GUI 真的把缓冲/库存喂进紧急单路径后，
   插单还可能选中「就地满足」从而改走另一条路线，这个坑立刻显形。改为按「路线是否走完」推进
   并保留显式上界。
4. **规格 §4 的 `d = 紧急单需求` 默认了该配送点只有这一张紧急单**；同点还有普通订单时会与紧急单
   **合并成同一个停靠点**，只按 10kg 去凑就会出现「车上只有 10kg 却把这个停靠点的 70kg 送掉」
   ——正是 P25 那类「车送它没装的货」。改为按**停靠点合并后的需求**。

5. **`replanIncremental`（路况触发的增量重规划）把缓冲整个吞掉了**——它逐趟重建时
   `out = Trip(); out.loadKg = prevTrip.loadKg;` 只复制订单货，`bufferKg`/`bankOps` 全丢，
   返回的 plan 也没带 `transitStock`/`transitOps`；而且它回退全量重算时**连 `initialStock`
   都没往下传**。症状（用户跑模拟时观察到）：**一次路况重规划之后，车回仓库只装订单货就出发**，
   站里再也攒不到货。修法：在这条路径上按与 `multiTripPlanImpl` **完全相同的规则重新推导**
   （只有"从仓库装货出发"的趟才满载；受影响的 leg 可能已重算，顺路关系随之改变，所以是重新
   推导而不是复制），并把库存快照跟着带走。新增守卫「出仓必满载」对 planRoute 与
   replanIncremental **两条路径**都断言。

**守卫（全部做过反向验证：回退修复后必须失败）**：G1 常规趟绝不进站 · G2 寄存零成本（库存不得
影响选路）· G3 库存守恒且每次装卸可追溯到某趟到达时刻 · G4 缓冲不超载 · G5 紧急单优先性 ·
G6 绝不更差（含「站不在路上」的反例夹具：有货就用会 45km vs 现状 40km，取优必须退回现状）·
G7 面板「当前库存」= `VehicleState` 权威值。

**运行日志导出（用户要求，2026-09-26）**：用户在与缺陷修复对话沟通时**对方法复现不出**他
观察到的问题，因此要求一个"把证据带出界面"的出口。做法：工具栏新增「**导出运行日志…**」，
并在同一条代码路径上提供命令行入口 `--export-log PATH`（缺陷修复方一条命令即可拿到同样的文件）。
导出内容：每次**事件触发**（用**它自己的事件刻**做前缀——批量结算时若用记录时刻会写成
「09:00 [事件] 08:15 抽取…」，最容易被误读）、每次**出仓装车**（订单货/缓冲货/合计，并标明
是否满载）、每次**到达配送点时的载重明细**（卸货前记，三项分开）、顺路寄存与紧急单处置方式，

"只在该行出现"的词，避免"到达"这种到处都有的词导致守卫形同虚设）。

**回归**：断言总数 790 → **820**（导出守卫在 app 侧，不增测试二进制）；`ctest` 20/20

### P36 第 28 轮：人工测试反馈——车在途中插紧急单后，「接着送」趟从旧位置起算，仓库发车不满载

**现象（用户导出运行日志 `logs/运行日志-20260926-215508.txt`）**：
```
09:41  接着送车上已有的货（第 2 趟，起点 D10，**非出仓**，不计缓冲）：订单货 20.0 kg ＝ 20.0 kg
09:41  经过 W01（到达 09:41）
09:46  经过 T01（到达 09:46）
```
车**在仓库 W01**（09:41）却装载了一趟"起点 D10"的货，随后 09:46 又驶出——全程没有
「出仓装车」记录，车上仍是 20kg。用户原话："紧急配送仅载着自己紧急订单所需货量的货就出仓了"。

**复现**：`--demo N --export-log` 可复现同类序列（RNG 固定种子）；核心层最小用例见下方守卫
（车在途中 T、车上 30kg 在途货、插入紧急单 U@D1），缺陷版本产出
`[1] T..W  [2] T..W  [3] W..W`——第 2 趟起点 T ≠ 第 1 趟终点 W。

**根因（不是显示层）**：`multiTripPlanImpl` 里"接着送车上已有的货"那一趟，`weave(..., startPos,
..., startPos, ...)` 传的是**原始出发位置 `startPos`**，而不是车的**当前真实位置 `current`**。
紧急批**先执行**且每趟都以仓库收尾（`current = vehicle.startNodeId`），于是：
- 计划排出一趟"起点是车早已离开的客户点"的趟（各趟首尾不接，车凭空从仓库跳回客户点）；
- 该趟起点非仓库 ⇒ `bufferKg = 0`、`loadedFromDepot = false`；
- 界面在车**到达仓库**时 `loadForCurrentTrip()` 装载它 ⇒ 车只带在途那点订单货离开仓库。

**为什么这是漏改**：同段注释（"从**当前位置**直接出发"）、紧急批与簇批用的都是 `current`，
只有这一处写了 `startPos`。判据"`startPos == vehicle.startNodeId` 才算出仓"随之也判错。

**为什么既有守卫没抓到**：`testEveryDepotTripIsFullyLoaded` 按 `nodes.front() == 仓库` 筛"出仓趟"，
而这趟的 `front()` 是客户点，被 `continue` 直接跳过；导出日志侧的守卫又**信任
`loadedFromDepot` 标记**——可标记本身就是错的。两条守卫都绕开了它。

**最小修复**：`startPos` → `current`（`weave` 的起点与装货点两处）+ 出仓判据；同步注释。

**守卫**：新增 `testTripContinuityAfterUrgentInsertWhileEnRoute`（`tests/routeplanner_tests.cpp`），
断言两条不变量：①**各趟首尾相接**（第一趟起点 = 车辆位置；此后每趟起点 = 上一趟终点）；
②任何**从仓库出发**的趟必须满载且 `loadedFromDepot`（判据用起点，不信任标记）。
反向验证（回退 `startPos` 后必须失败）实测：
```
FAIL  各趟必须首尾相接（车不能凭空移动）：第 2 趟起点 T != 第 1 趟终点 W；
      实际 [1] T..W  [2] T..W  [3] W..W
```

**回归**：`ctest` 20/20（目标数不变）；断言总数 827 → **829**（截至本轮；2026-10-19 补 IniFile 行号断言后现为 838）；三策略黄金值**逐位不变**
（该修复只改计划内趟的起点，静态规划无紧急单/无在途货时 `current == startPos`，故无行为变化）。

**顺带纠正一条"看起来像证据"的误导**：`--export-log` 的渲染守卫只检查"出仓装车…未满载"字样，
而本缺陷把违规趟标成了「接着送…非出仓」，因此**能通过日志守卫**。教训与 P32 一致：
守卫若信任另一个可能出错的标记，就测不到东西；结构性不变量（首尾相接）才是上游判据。

### P37 第 29 轮：人工测试反馈——载重出现小数；货量口径统一为整公斤

**现象（用户导出日志 `build/logs/运行日志-20261001-164611.txt`）**：载重明细里出现
`缓冲货 141.9 kg`、`135.2 kg`、`76.4 kg`，汇总里 `期末站内库存 136.4 kg`。

**排查结论（与直觉相反的事实）**：静态数据 `config/default.ini` 的货量列**全是整数**
（实测 orders 的 demand 列小数 **0** 个），**小数只来自动态事件的两个浮点随机生成点**：

- `MainWindow::insertUrgentOrderAction`：`3.0 + rng_.nextRange(0.0, 7.0)`（日志实测 `3.3kg`）
- `MainWindow::addRandomCustomerAction`：`3.0 + rng_.nextRange(0.0, 12.0)`

它们把小数写进 `Order::demandKg`，再传播到 `Trip::loadKg/bufferKg`、`VehicleState::loadKg/
bufferKg`、`stationStock`，于是在各处显示点露出。

**范围裁定（用户 2026-10-01）**：**只改生成端 + 移除显示**，**不**把货量容器改成 `int`
（选项 B 被明确否决）；派生的库存/缓冲**随生成端自然变为整数，不额外加取整代码**。

**最小修复**：两个生成点改为 `std::floor(3.0 + rng_.nextRange(...))`，区间仍是 3–10kg / 3–15kg；
30 处 kg 类显示由 `'f',1` 改为 `'f',0`。

**关键实现陷阱（值得记）**：改用 `rng_.nextInt(3,10)` **不是**等价替换——`nextInt` 取模
（`nextU32() % span`）会**改变后续随机序列**，导致 `--self-check-actions` 里"连续两次插单不丢单"
与"新客户被纳入配送"两条**既有**断言失败（实测 3 项红）。而 `nextRange + floor` 保持随机流形状，
只消除小数。故采用后者，**而不是**去改那两条无关断言。教训：凡是"消除随机源的小数"这类改动，
要先确认随机数**消耗方式**是否相同，否则会连带打破下游对序列的依赖。

**刻意不动的**：距离/耗时/成本的小数显示（178.2km / 378.3min / 244.2 元）是既有正确口径，
必须保留——守卫的正则只匹配"数字紧跟 kg"的形态，故不会误伤它们。

**守卫（`runActionSelfCheck` 第 ⑨ 节，两条）**：
1. **生成端**：40 轮×2 入口 = 79 个样本，断言 `demandKg` 为整数（读**动态事件真的生成出来**的货量，
   不重算公式），外加区间断言（紧急单 3–10kg、新客户 3–15kg）。附前置断言"必须真的生成了订单"。
2. **显示端**：用正则 `([0-9]+\.[0-9]+)\s*kg` 扫 `runLogText()` 的**真实文本**，断言无小数 kg；
   附前置断言"文本里应含以 kg 计的货量字段"（防"把 kg 全删掉也能通过"的空跑）。

**反向验证（两条，均实测）**：
- 回退生成端 → `FAIL 动态事件（紧急单/新客户）生成的货量必须是整数公斤：检查 79 个，其中 79 个带小数（首个：新客户 13.7292kg）`
- 回退显示端（到达载重明细改回 `'f',1`）→ `FAIL 导出运行日志里的货量必须是整数：出现了「190.0 kg」`

**性能纪律**：守卫初版跑 200 轮（每个入口内部都会 replan），使 `cli_action_self_check`
由 0.25s 涨到 **99.41s**。降为 40 轮后 **2.4s**，且反向验证仍为 79/79 带小数（牙齿不丢）。

**回归**：`ctest` 20/20（目标数不变）；8 个单元测试二进制自报断言合计 **829 项（不变，截至本轮；现为 838）**；
`--self-check-actions` 通过且**断言数 74 → 80**（口径 = `… | grep -c '^\[self-check\] OK'`；
另有 1 条 `--` 信息行与 1 行汇总，故总行数 82——**不要把这 82 当成断言数**，
独立 verifier 复核时正是按 82 抓到过这处口径错）；三策略黄金值**逐位不变**
（黄金值走静态规划、不含动态事件，静态数据本无小数，故数字不该变，实测确实未变）。
