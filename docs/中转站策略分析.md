## 一、问题

用户提出两条主张：

1. **「满载驶出仓库」不会更差**，并要求给出反例（若存在）。
2. 车辆**返回仓库前把多余载荷卸在中转站**；下次满载过来先分发一部分客户，
   再回中转站**取上上次留下的载荷 + 车上剩余的载荷**，去满足剩余客户或新出现的紧急订单。

---

## 二、反例：满载确实可能更差（已实测）

**图**：`W(0,0)`；簇 A 的中转站 `TA(0,10)`、客户 `a1(0,11)` 需求 20kg；
簇 B 的中转站 `TB(50,0)`、客户 `b1(50,1)` 需求 100kg。载重 `C = 100kg`。
`TA` 与 `TB` 之间无直连路（只能经 W 绕行 60）。

| 方案 | 路线 | 里程 |
| --- | --- | --- |
| **按目的簇装货** | ① `W→TA→a1→TA→W`（装 20）<br>② `W→TB→b1→TB→W`（装 100） | **124 km**（2 趟） |
| **一律满载 + 余货卸在当前站点** | ① `W→TA→a1→TA→W`，装 100（20 给 a1 + **80 给 b1**），80kg 卸在 TA<br>② `W→TB→b1→TB→W`，装 100<br>③ `TA→W→TB→b1→TB→W`，**去 TA 把那 80kg 取回来送** | **236 km**（3 趟） |

**满载方案多跑 112 km（+90%），多出整整一趟。**
多出来的里程全部来自：**那 80kg 被卸在了错误的中转站**——它的目的地在 TB 那边，
只能再跑一趟把它搬过去。

### 由此得到的第一条结论

> **代价不在「满载」，而在「把不相关的货卸在了某个站」。**

我们的计费模型是**逐边累加里程/耗时/成本，与载重无关**，
所以车上多带 100kg 走一段路本身**不花钱**。真正花钱的是：
你把货卸在了一个「它不该去的地方」，于是它多走了一段冤枉路。

因此「满载出库」要成立，有一个**必要前提**：
**余货必须属于你卸货那个站所服务的簇**。
用户描述的场景（同一个簇的后续客户）满足这个前提；
但「一律装满」这种无差别规则不满足，上面就是它的代价。

## 三、「满载 + 正确站点留货」能不能省里程？——不能

货量必须从仓库跨越到簇所在区域，这是任何方案都躲不掉的干线运输。
每跨一次最多带走一个载重上限 `C`，所以**干线跨越次数存在下界**：

```
每簇跨越次数 >= ceil(簇货量 / C)

当前数据（C = 200kg）：
  簇1 262kg -> 下界 2 次
  簇2 220kg -> 下界 2 次
  簇3 258kg -> 下界 2 次
```

- **按需装载**（每次带 `min(剩余, C)`）：跨越次数 **= 下界**，且没有多余装卸。
- **一律满载**（每次带 `C`）：跨越次数**同样是下界**，却每次都产生
  `C − 本批需求` 的余货要卸进站里 —— 次数不变，只多出装卸。

**结论：两种装法的干线跨越次数相同，因此总里程相同。**
「预先把货囤到中转站」**不减少跨越次数**，它只是改变了货物移动的**时机**。

（一个容易混淆的点：把余货先卸在站里，看着像"省了下一趟回仓库"，
但那批货的跨越本身已经发生过了，下一趟省下的是**别的**货的跨越——
总体次数仍由下界决定。）

---

## 四、那它到底在哪一点上有价值？——**紧急订单的响应时间**

这是唯一站得住、且**可测量**的收益点。它成立的前提是：
**车辆此刻已经在某个中转站附近，而站里有库存。**

实测场景（同上一张图，车辆已完成一轮配送、**空车停在 TB**）：

| 情形 | 路线 | 耗时 |
| --- | --- | --- |
| 站内无库存 | 空车回仓库取货：`TB→W→TB→b1` | **101 min** |
| 站内留了 5kg | 就近取货直达：`TB→b1` | **1 min** |

差 **100 分钟**。在「1 小时内送达」的窗口下，前者**必然超时并记 penalty**，
后者轻松达标。

这与本项目的 E3（动态紧急订单）**直接相关**：penalty 是要求里明确要记的量，
所以「留库存压低紧急单的 penalty」是**可量化**的收益，不是感觉上的效率。

## 五、若要把这个机制做进去，需要改什么

当前实现（`multiTripPlan`）的行为是：**需要多少装多少**，
每轮配送把它取走的货全部送完，因此**每轮结束后站内库存恰好为 0**。
于是紧急订单一来，规划器只能让它从仓库出发取货。

要支持用户描述的机制，需要两项改动：

1. **把「站内库存」变成规划的一等输入**
   现在 `TransitStock` 只是**规划的产物**（replan 时从 0 重新算）。
   要实现"取用现存库存"，它必须成为**车辆状态的延续**：
   replan 时接收"当前各站库存"，规划结束后回写新的库存，并保持守恒
   （卸入 + 取用 ≤ 库存，终值非负）。

2. **给出"该囤多少"的规则**，并且**只在同一个簇内囤**
   —— 第三节已经证明：囤**本簇**的货不省里程（次数不变），
   但能让站内长期保有库存，从而压低紧急单的响应时间；
   囤**别簇**的货 = 上面那个 +90% 的反例。
   最小的规则：每次从仓库出发去某簇时，装 `min(本簇剩余, C)` 之外**再额外多装一份备用**，
   但额外量必须 ≤ `C` 且仍属于本簇。

**代价与风险**：多了一个跨重规划的**状态维度**（库存），
必须配套守恒断言；且这个机制**只在紧急订单出现时才有收益**，
没有紧急单时它纯粹是"多带了货"——里程不变，但装卸记录更复杂。

## 六、结论摘要

| 主张 | 核查结论 |
| --- | --- |
| 满载驶出仓库一定不会更差 | **不成立**。若余货被卸在错误的中转站，实测 +90% 里程、多一趟 |
| 「满载」本身是问题 | **不是**。逐边计费与载重无关，多带不花钱；花钱的是**卸错地方** |
| 预先把货囤到中转站能省里程 | **不成立**。干线跨越次数下界 = `ceil(簇货量/C)`，两种装法都一样 |
| 中转站留库存能压低紧急订单 penalty | **成立且可测量**。实测差 100 分钟，直接影响 E2 的 penalty |
| 用户描述的"取回上次留的货 + 车上剩余" | **等价于**已实现的"站内库存 + 反复就近配发"；差别只在库存是否跨重规划延续 |
