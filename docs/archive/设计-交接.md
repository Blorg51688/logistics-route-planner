## 4. 构建与运行

### 4.1 核心层独立构建（不依赖 Qt，当前可立即使用）

建议用 CMake 拆分目标：`core` 静态库 + `tests` 可执行文件。示例：

```cmake
cmake_minimum_required(VERSION 3.20)
project(logistics CXX)

set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

add_library(core STATIC
    src/core/...
    src/io/...
)
target_include_directories(core PUBLIC src)

add_executable(core_tests tests/...)
target_link_libraries(core_tests PRIVATE core)

# GUI 目标在 Qt 可用后再启用
# find_package(Qt6 REQUIRED COMPONENTS Widgets)
# add_executable(app src/main.cpp src/gui/...)
# target_link_libraries(app PRIVATE core Qt6::Widgets)
```

### 4.2 核心层测试

```bash
cmake -S . -B build
cmake --build build
./build/core_tests
```

### 4.3 GUI 构建（Qt 就绪后）

```bash
cmake -S . -B build -DBUILD_GUI=ON
```

## 5. 建议的推进顺序

按依赖关系排列，每步都应产出可编译、可测试的增量：

1. **项目骨架**：CMakeLists、目录结构、.gitignore、首次 commit。
2. **核心数据结构**：Node、Edge、LogisticsGraph（邻接表）。先不写算法，只写增删查。
3. **手写最小堆**：`MinHeap`，独立测试 siftUp / siftDown。
4. **Dijkstra**：基于邻接表 + 手写堆，单源最短路。测试单点最短路正确性。
5. **INI 解析器**：手写 section/key/value 解析，独立测试。
6. **ConfigLoader**：把 INI 转成图、车辆、订单。写一份满足规模的 `default.ini`。
7. **RoutePlanner**：贪心串联 + 时间窗口推进 + 载重检查 + 紧急订单优先。
8. **图表示输出**：邻接表 / 邻接矩阵文本输出，便于调试。
9. **核心层单元测试**：覆盖正确 / 错误 / 边界三类。
10. **GUI 层**（Qt 就绪后）：GraphScene、NodeItem、EdgeItem、WeightLabel、MainWindow、SidePanel。
11. **扩展功能**：路况模拟与重规划、动态订单插入、Debug 模式定时器。
12. **报告素材**：流程图、UML 图、测试用例表。

**前 8 步完全不依赖 Qt，可在当前环境立即开始。**

## 6. 核心接口契约

以下接口为 GUI 与测试所依赖的最小集合，命名可调整，但语义必须保留。

### 6.1 LogisticsGraph

必须提供：

- 节点增删：`addNode` / `removeNode`
- 边增删：`addEdge` / `removeEdge`
- 只读查询：获取全部节点、全部边、某节点的出边、按 ID 找节点、按 (from, to) 找边
- 图表示输出：邻接表字符串、邻接矩阵字符串

**不变量**：
- 删除节点时，必须同步删除所有出边与入边。
- 同一对 `(from, to)` 至多一条边。

### 6.2 Dijkstra

- 输入：图、源 ID、目标 ID、权重类型（距离 / 耗时 / 成本）
- 输出：路径节点序列 + 总权重；不可达时返回明确标记
- 必须手写最小堆与松弛，不得用 `std::priority_queue`

### 6.3 RoutePlanner

必须提供：

- `planRoute(...)`：从起点出发，对给定订单集合贪心串联，返回 `RouteResult`
- `replan(...)`：从当前位置出发，对剩余未服务订单重算
- `insertUrgentOrder(...)`：加入紧急订单后重算

**语义要点**：
- 紧急订单在贪心选择中优先。
- 规划阶段时间窗口硬约束检查：预计超时标记 `isLate` 并记录 penalty，但仍加入路线。
- 载重超限时返回不可行并给出原因。
- 不可达点返回不可行并给出原因。

### 6.4 RouteResult

每个停靠点至少包含：节点 ID、到达时间、等待时间、离开时间、是否超时、penalty、离开时累计载重。
路线汇总至少包含：节点序列、总距离、总耗时、总成本、总 penalty、是否可行。

### 6.5 核心层与 GUI 的边界

- 核心层不感知 Qt。
- GUI 通过只读接口拿数据画图，通过业务方法触发计算。
- 计算完成后 GUI 重建或更新图元，不直接改核心层内部状态。

## 7. 配置契约

`config/default.ini` 必须满足规模要求：节点 ≥30（≥2 仓库、≥15 配送点、≥3 中转站），边 ≥50。

格式：

```ini
[general]
service_time_min = 5
traffic_change_interval_sec = 30
traffic_change_ratio = 0.1
traffic_time_increase_min = 0.2
traffic_time_increase_max = 0.5
urgent_order_interval_sec = 60

[nodes]
# ID, type, x, y, name, sub_network_id
N01, warehouse, 100, 200, 中央仓库, 0
N02, delivery,  300, 150, 客户A, 0
N03, transit,   250, 300, 中转站B, 1
...

[edges]
# from, to, distance_km, time_min, cost_yuan
N01, N02, 5.2, 12, 8.0
...

[vehicles]
# ID, start_node, capacity_kg
V01, N01, 500

[orders]
# ID, node_id, demand_kg, window_start, window_end, is_urgent
O01, N02, 30, 09:00, 11:00, 0
O02, N03, 45, 14:00, 16:00, 0
O03, N05, 20, 10:00, 12:00, 1
...
```

解析规则：
- `#` 开头为注释
- `[section]` 分节
- 逗号分隔字段
- 空行忽略
- 时间 `HH:MM` 转为相对分钟

**建议先手写一份满足规模的 `default.ini`**，作为开发与测试的基础数据。

## 8. 测试策略

核心层测试不依赖 Qt，直接用 g++ 编译运行。必须覆盖三类：

**正确运行用例**
- 默认配置加载成功
- 双策略规划输出合理路线
- 动态增删节点与边后图状态正确

**导致程序错误的用例**
- 配置文件缺失
- 节点 ID 重复
- 边指向不存在节点
- 载重超限

**边界数据用例**
- 节点数 = 30、边数 = 50
- 载重刚好等于总需求
- 时间窗口卡点（到达 = 窗口开启）
- 空订单列表
- 不可达配送点

建议把测试数据放在 `data/test_cases/`，每份一个 INI 文件，测试程序逐份加载并断言结果。

验收时老师会**现场改需求并现场改代码**。设计上需留出以下扩展点，但第一版不实现：

- 多车辆：`RoutePlanner` 接口预留车辆列表参数
- 跨仓库调拨：预留仓库选择接口
- 增量式重规划：预留 `replanIncremental` 接口
- 中转站嵌套子网络：节点已带 `subNetworkId` 字段
- 更多权重策略：权重类型枚举可扩展

**建议**：核心层业务方法的参数尽量用“集合 + 配置”形式，避免硬编码单一车辆、单一策略，便于现场改需求时最小改动。

## 10. 常见陷阱

- **不要把 Qt 引入核心层**。一旦核心层 `#include <QString>`，核心层测试就无法脱离 Qt 编译，开发会被阻塞。
- **不要用 STL 算法替代 Dijkstra 或堆**。容器可以用，算法不行。
- **删除节点后必须重建节点下标映射**。邻接表用下标索引，删除节点会打乱下标。
- **路况更新要保留初始耗时**。边结构需存 `baseTimeMin`，否则无法判断“是否增加 ≥20%”。
- **时间窗口判断要区分规划与执行**。规划阶段标记 `isLate` 但仍加入路线；执行阶段因路况变化迟到才计 penalty。
- **紧急订单优先逻辑要放在贪心选择内部**，而不是排序后处理，否则可能破坏串联顺序。
- **Debug 模式的自动模拟要可关闭**，否则调试时定时器会干扰手动测试。
