## 0. 全文统一的前提（不写清前提的复杂度等于没写）

**n** = 节点数（当前数据 **30**）、**m** = 有向边数（**106**）、**deg** = 某节点的出度、
**m_task** = 订单数（**25**）、**S** = 停靠数（默认三策略 28–30）、**A** = 动作数（50）、
**s** = 堆内条目数、**count** = 一次路况改动的边数（默认 **11**）、**L** = 配置文本总行数、**r** = 某节的记录行数。

当前数据口径（`config/default.ini`，已提交基线 `cdc98e2`）：2 仓库 + 3 中转站 + 25 配送点 = 30 节点；106 有向边 = 50 个双向道路对（100 条）+ **6 条单向边**；25 张订单（全部 A→B 取送，A≠B），总需求 516kg；车 V01 200kg·08:00·1.00·1.00。

**事实来源**：`src/`（分支 `spec/pdp-fleet`，规格一 #32–#37 已落地）+ 现有文档。文中一律用「`文件:符号名`」，不用行号（行号会漂）。

```text

   ▼
IniFile::parse ──────► IniSection / IniRecord（每条自带 lineNo，报错才能指到行）
   │                     ▲ 退役键（service_time_min / event_weight_*）在此拦下：带行号报错
   ▼
ConfigLoader::load ──► Config{ graph, vehicles(6 列), orders(7 列), general(事件等级) }
   │                                    │
   │ Config.graph                       │ Config.orders
   ▼                                    ▼
LogisticsGraph{ nodes_ 顺序表 + out_ 邻接表 }        Order[] ─► Request{orderId, A, B, kg, [ws,we], urgent}
   │ adjacency() 只读                                            │  （makeCtx：可达性/单笔超载 一次判死）
   ▼                                                            │
Dijkstra::shortestPath（dist[] + previous[] + MinHeap）          │
   │ PathResult{nodes, totalWeight}                              │
   ▼                                                            ▼
CostMatrix（V×V×3：距离/耗时/成本，全源最短路预计算）◄─────────────┘
   │ 该车缩放：耗时 × timeFactor、成本 × costFactor（**距离不乘**）
   ▼
buildAll（整批构造；中途重规划单起点）
   ├─ 起点版本：EDD ／ 按取货点 A 聚簇 ／ 按送达点 B 聚簇（insertionStarts，仅整批构造）
   ├─ 紧急段 appendUrgentAll：订单级 FIFO 尾插、同节点合并、降载兜底
   ├─ 普通段 insertNormalAll：pair-insertion（tryInsertPair，全位置对）
   │     └─ 失败 → repairRoute（有界 relocate，R ≤ 3）→ 全量兜底 → 降载 → 拒绝并报原因
   ├─ 每次评价 replay(StopSpec[])：时间/等待/逐单 penalty/前缀载重/F1–F7
   └─ 取优 compareRoutes：字典序 (Σpenalty, 策略权重, tieKey)
   ▼
RoutePlan{ stops[] = **真源**；offloads[]；metrics }
   │      ├─► Stop{ nodeId, deliveries[]/pickups[]/offloads[]/reclaims[], phase, 时刻, remainingLoadKg }
   │      ├─► OffloadLeg（降载 custody：站 / 单 / kg / 卸下 / 取回）
   │      └─► RouteMetrics + OrderMetric（S / A / 逐单 penalty 与准时 / 两率 / 在车统计）
   │ finalize：**一次展平** → nodes / nodeArrivalMin / nodeIsStop（GUI 按下标推进）
   ▼
MainWindow 推进：onAdvanceStop（**到达前逐刻结算**）/ onAdvanceMoment
   │ settleEventsUpTo(now) —— 事件结算挂在「软件时间前进」上
   ▼
SimEvent::nextEventTimeMin（每 15min 一个刻，严格前进）+ pickEvent(权重由 event_level_* 派生 27:3:9:1)
   │ 抽中的那一类
   ├─ Traffic::simulateTrafficChange ──► TrafficReport ──► needsReplan？
   │        └── 就地改 Edge::timeMin（**baseTimeMin 永不动**）
   ├─ RoutePlanner::insertOrder（紧急 → FIFO 尾插；普通 → pair-insertion；A→B 取送）
   └─ GraphEdit::addRandomCustomer / closeRandomRoad（改图；封路前先 BFS，不封桥）
   │
   ▼
replanIncremental（**顺序不变版重放**：停靠顺序不变，按新权重重放；不可行则退回全量 replan）
   │ 回退时带入 OnboardItem（在车货）与 StashState（暂存），否则暂存货凭空消失
   └──► 回写 RoutePlan（新一版 stops）──► 回到上面的 finalize
   │
   ▼
GraphScene::syncScene（路径高亮 isEdgeOnRoute / 拥堵标记 / 车辆位置）
```

## 2. 表 1 · 存储与配置层（结构本体 + 承载它的记录）

| 结构 | 是什么 | 为什么是它（排除谁 / 依据） | 特点与复杂度（前提） | 没有它得自己写什么 | 连接：谁喂它 → 它 → 谁消费 | 代价与坑 |
|---|---|---|---|---|---|---|
| `IniFile`·`IniSection`·`IniRecord` | INI 文本 → 带行号的记录序列（节 → 记录） | 解析错误必须报行号 ⇒ 记录自带 `lineNo`，而且 `findValue` 返回**记录本体**而非值（报错时才带得上行号）；节数与记录数都很小（`[general]` 8 行）⇒ 顺序 `vector` 足够，不必建键索引 | `parse` O(L)；`findSection` O(节数)；`findValue` O(r) | 逐行扫描 + 手维护一张「值 → 行号」旁表 | `config/default.ini` → `IniFile::parse` → `IniSection`/`IniRecord` → `ConfigLoader::load` | 只认 `#` 注释；重复节名直接失败；不做语义校验（语义都在 `ConfigLoader`） |
| `Config` | 一次加载的完整结果：图 + 车辆列表 + 订单 + 全局参数（含**四个事件等级**） | 把「文件里的四类数据」收成一个值对象，规划器与界面只依赖它、不依赖 INI 形状；事件**权重不落配置**，只落等级，权重由 `Config.h::eventLevelWeight` 的固定表派生 ⇒ 改配置不改代码、也不会出现两份权重表 | O(n + m + 订单数) 空间；纯数据、无方法 | `ConfigLoader` 要回传 4 个出参，或每个调用点自己再解析一遍 | `ConfigLoader::load` → `Config` → `replan`（GUI 入口）/ `planRoute`（CLI `--plan-summary`、测试入口）/ `MainWindow` 按值持有 | 事件参数只剩 `event_interval_min` + 四个 `event_level_*`；`Config::graph` 是**值**，不是引用；`vehicles` 是**列表**（规格一只有 1 台） |
| `LogisticsGraph` | 有向带权图：`nodes_` 顺序表 + `out_` 邻接表，两者下标严格对齐 | 图是稀疏的（30 节点 / 106 有向边）⇒ 邻接矩阵 900 格绝大多数为空、而每格还要塞 3 个权重；下标对齐让「节点 i 的出边」是 O(1) | n、m、deg：`indexOf` **O(n)**（线性扫）；`findEdge` O(deg)；`addNode` O(n)；`removeNode` **O(n+m)**（入边散落在别人的出边表里）；空间 O(n+m) | Dijkstra 每轮自己从边表里筛边（每次 O(m)），或另建一份邻接结构 | `ConfigLoader` 装配 → `Dijkstra` 只读 `adjacency()`、io 输出邻接表/矩阵 → `Traffic`/`GraphEdit` 就地改 → GUI 只读遍历 | 没有反向邻接表 ⇒ 删点 O(n+m)；`indexOf` 是 O(n)（节点数小，不为它引入索引）；**不提供可写 `Edge*`**，防调用方改坏 `fromId` 等不变量 |
| `Node`·`Edge`（记录） | 图的两条记录类型；`Edge` 携带三权重 + `baseTimeMin` + `congested` | 三权重并存才能「同一张图、三套策略」；`baseTimeMin` 单列，是因为路况判定要「相对基准的增幅」，而 `timeMin` 会被就地改写 | 定长 O(1)；`findEdge(from,to)` O(deg) | 想把耗时还原成「畅通」就得另存一张初始耗时表并永久同步 | `ConfigLoader` 构造 → `out_` → `Dijkstra` 松弛 / `Traffic` 改 `timeMin` / GUI 画箭头 | `updateEdgeTime` 只改 `timeMin`，`congested` 由「是否高于 `baseTimeMin`」自动维护；`Node::x/y` 只供 GUI 布局 |

## 3. 表 2 · 手写算法层（「手写算法、不手写轮子」的落点）

| 结构 | 是什么 | 为什么是它（排除谁 / 依据） | 特点与复杂度（前提） | 没有它得自己写什么 | 连接：谁喂它 → 它 → 谁消费 | 代价与坑 |
|---|---|---|---|---|---|---|
| `MinHeap` | 手写二叉最小堆，元素固定 `Entry{key:double, value:int}`（底层 `std::vector`） | 课程硬性要求堆自写（禁 `std::priority_queue`·`make_heap`）；**不做成模板**，因为全项目只有 Dijkstra 一处用、元素类型固定 | `push`/`popMin` 各 O(log s)；`siftUp`/`siftDown`/`swapEntries` 全自写；空堆 `popMin` 返回 false 且不改出参 | Dijkstra 每轮取最小扫一遍 `dist[]`（O(n)）——n=30 时同阶，所以收益是**考点**不是提速 | `Dijkstra::shortestPath` → `push`/`popMin` | **没有 decrease-key** ⇒ 同节点留下过期条目（≤ m），靠 `currentDist > dist[current]` 惰性删除 |
| `Dijkstra::shortestPath` + `dist[]`·`previous[]` | 单源单目标最短路：距离数组 + 前驱数组 + 惰性删除堆 | 三种策略**共用这一份实现**，只在 `pickWeight(Distance/Time/Cost)` 换权重来源；用前驱数组复原路径，而不是让堆条目携带整条路径 | `dist`/`previous` 各 O(n)；时间 **O(m·n + m·log m)**（松弛内层 `graph.indexOf` 是 O(n)）；路径复原 O(路径节点数) | 把前驱数组换成「堆里带路径」会让每次松弛多 O(n)；三套策略要写三遍 | `adjacency()` → `shortestPath` → `PathResult` → `CostMatrix::build` | 不可达时 `found=false` 且 `nodes` 为空；`kInfinity` 只是哨兵；**无 decrease-key 是设计，不是缺陷** |
| `CostMatrix`（+`scaledWeight`） | **全源最短路预计算**：V×V×3 三张表（按距离/耗时/成本各自最优路径的三项指标） | pair-insertion 每次评价要查大量 (站→站) leg，逐个调 Dijkstra 会让「一个候选 = 一次最短路」变成主开销 ⇒ 一次建表、之后 O(1) 查；同时把**车辆因子**收在一处（耗时×timeFactor、成本×costFactor） | 建表 = V×3 次 Dijkstra ≈ **O(V·(m·n + m log m))**；查询 `legAll` O(1)；空间 V²×3 | 每个候选位置对都现算最短路（数量级 ×n² 次），或缓存一份自己维护的旁表 | `Ctx.matrix.build(graph)` → `tryInsertPair`/`replay`/`repairRoute`/`insertReclaimStop` 的每次 leg 查询 | 表按**基础图**建、因子在查询处乘——所以路况改边后必须**重建**（`makeCtx` 每次规划都重建）；`reachable` 用「距离维 ≥ 0」判可达 |
| **pair-insertion**（`tryInsertPair` + `replay` + `compareRoutes`） | 把一张订单的 (A,B) **对**插到普通段的最省位置：枚举全部位置对、逐个重放评价、取键最小 | 规格一 #18 的构造器：**penalty 先**的 cheapest insertion，取代「贪心选最近邻」（最近邻会在紧窗单上迟到——测试 `testPairInsertionBeatsNearestNeighbourOnTightWindow` 直接钉住这一点）；同节点并入既有停靠，减少停靠数 | 单请求 = O(n²) 位置对 × O(n) 重放 = **O(n³)**；m_task 张单 ⇒ O(m_task·n³)；`replay` 里同时判 F1–F7（不可行立即剪掉） | 自己写「每个位置合不合法、代价多少」的评价器；写时间/载重/penalty 的推进 | `Request` + `StopSpec[]` → `tryInsertPair` → `replay`/Eval → `compareRoutes`（三键）→ 采用或进入兜底 | 键序是 (Σpenalty, 策略权重, tieKey)，**载重峰值不进键**；耗时维的权重**含早到等待**（否则「最短耗时」策略会输出更长总耗时，设计 §4.7-②） |
| `repairRoute`（有界 relocate） | 普通段**局部重排**：按 EDD 序把普通单逐个摘下、重插到更优位置，某轮无改进即停，轮数 ≤ 3 | 位置对枚举是「先来先占位」的，前一张单可能挡住了后一张更优的位置；有界 relocate 补这个局部性，又不用整批重算（全量兜底太贵） | O(R·m_task·n³)，R ≤ 3；实测默认数据下多数轮次第 1 轮即无改进 | 全量重跑构造（O(m_task·n³) × 次数），或接受次优 | `insertNormalAll` 失败时 → `repairRoute` → 成功则继续、失败进兜底 | **只动普通段**：紧急段受 FIFO 约束，relocate 恒等；取回停靠也作为单点请求参与 relocate（先于暂存单送达是硬约束） |
| `buildAll`（多起点 + 两级兜底 + 降载） | 构造总调度：起点版本枚举 → 全量兜底 → 降载 → 拒绝 | 单一 EDD 起点会让某个策略在 ② 上被反超（单起点时成本策略 168.5 元 > 距离策略 145.3 元）；多起点把「插入序」这一维也纳入搜索，仍用**同一把三键**取优 | 3 个起点版本 ×（构造 + repair）≈ 3 × O(m_task·n³)；多起点**只在整批构造**（基地 / 空车 / 发车时刻）启用 | 自己写「哪个起点更好」的判断、失败后的重排、降载触发 | `insertionStarts` → `buildAll` → `Outcome{route, reason}` → `finalize` | 中途重规划（`replan` 带在车货/非发车时刻）**单起点**：构造次数多、时间预算不允许；`--self-check-actions` 36s 量级正是这条链的代价 |
| `GraphEdit`（`addRandomCustomer`·`closeRandomRoad`·`makeSyntheticEdge`） | 动态增删：随机位置插新客户、随机封一条路（双向删边）、手工加边的权重估算 | 坐标 → 权重的换算**从图自身既有边推算**平均比值（`estimateScale`），不硬编码尺度；封路前用 BFS 检查连通性，**不封桥**；新节点**继承最近邻的 `sub_network_id`**（#30 缺陷修复） | `estimateScale` O(m)；`reachesSkipping` 手写 BFS，队列 `vector` + 游标、`seen` 线性查找 ⇒ O(n·(n+m))；`addRandomCustomer` 找最近点 O(n) | 自己写「最近点 + 双向连边 + 权重估算 + 连通性检查 + 归属继承」 | 事件分派 / 手动动作 → `GraphEdit` → `addNode`/`addEdge`/`removeEdge` → 新图上的后续规划 | `seen` 是线性查找不是 `set`（节点量小）；封路是**双向**删边；最近邻是仓库时 `sub_network_id` 回落到最近的编号非 0 配送点/中转站 |
| `SimEvent`（`nextEventTimeMin`·`pickEvent`·`pickDistinctPair`·`EventWeights`）+ `Rng` | 软件内时间的事件模型：每 `intervalMin` 一个事件刻、每刻恰抽 1 个事件；四类权重由**等级**派生（默认 27:3:9:1） | **两个独立理由**：① 用软件内时钟而非真实定时器/推进计数，是为了「推进粒度不影响事件串」（D24）；② 手写 `xorshift32` 是**可复现性**选择（同种子必得同序列），**不是**因为 STL 被禁 | `pickEvent` 单次 O(4) 前缀扫描；`nextEventTimeMin` O(1) 且严格大于 now；`pickDistinctPair` 固定消耗 2 次随机数（等价性前提）；`Rng` 每步 3 次移位异或 O(1) | 自己写加权抽签、全零兜底、事件刻对齐、条件均匀的 A/B 抽签 | `GeneralConfig.eventLevel*` → `eventLevelWeight` 派生权重 → `pickEvent`/`pickDistinctPair` → GUI 事件分派 → `Traffic`/`insertOrder`/`GraphEdit` | 权重 ≤ 0 的种类**永不被抽中**；全零保底 `Traffic` 且**仍消耗一次随机数**；`intervalMin <= 0` 返回 `nowMin + 1`；**改枚举顺序会改固定种子下的整条随机串**（等价性断言会红） |
| `simulateTrafficChange`·`TrafficChange`·`TrafficReport`·`needsReplan` | 一次路况变化中被改动的边清单（增幅 + 畅通/拥堵），以及「要不要重算」的判定 | 把「这次改了什么」落成**可审的数据**——触发判定要问「受影响的边是否恰在当前路线的相邻两站之间」；增幅每次**重设**为 `baseTimeMin×(1+ratio)` 而非叠加 ⇒ 耗时不会逐次失控 | count = 改动边数（默认 `round(0.1×106)` = **11**）；选边用**部分 Fisher-Yates** O(count)；`needsReplan` O(count × 路线长度) | 分不清「改了但不在我路上」和「改在我必经段上」，只能每次事件都全量重算 | `simulateTrafficChange` → `updateEdgeTime` → `TrafficReport` → `needsReplan` / `replanIncremental(report)` | 只有「增幅 ≥ 阈值 **且**恰在路线相邻两站」才触发（畅通变更 `increaseRatio=0`，永不触发）；`needsReplan` 与 GUI 高亮共用 `isEdgeOnRoute` |

## 4. 表 3 · 调度状态层（被算法承载、被界面消费的记录）

| 结构 | 是什么 | 为什么是它（排除谁 / 依据） | 特点与复杂度（前提） | 没有它得自己写什么 | 连接：谁喂它 → 它 → 谁消费 | 代价与坑 |
|---|---|---|---|---|---|---|
| `Request` + `StopSpec`（构造期，`RoutePlanner.cpp` 匿名命名空间） | `Request` = 一张订单的取送请求（A/B/kg/逐单窗口/urgent/已取/在站）；`StopSpec` = 规划**中间态**的一次停靠（四个动作列表 + 阶段） | 构造期要频繁「插入/摘除/比较」，用**轻量描述**而不是最终 `Stop`（后者带时刻与明细，重放时才生成）⇒ 候选评价不必构造 O(n) 个明细对象；`Request` 让「按订单记账」成为唯一口径（同节点多单不会被按 nodeId 扣错） | `StopSpec` O(动作数)；比较时按需生成排序后的动作 ID 列表（手写插入排序） | 用最终 `Stop` 做候选 → 每次评价都构造明细，34 万次评价里成为最大开销 | `makeCtx`（`Order→Request`）→ `tryInsertPair`/`repairRoute` 改 `StopSpec[]` → `finalize` 转成 `Stop[]` | `StopSpec` 是**构造期**类型、不导出；`Request.alreadyPicked`/`inStash` 决定「本次要不要生成取货动作」 |
| `Stop`（结果期，头文件导出） | 一次停靠的**动作集 + 时刻 + 在车量**：`deliveries[]{orderId,late,penaltyMin}` / `pickups[]` / `offloads[]` / `reclaims[]` / `phase` / `rawArrivalMin`/`waitMin`/`arrivalMin` / `late`/`penaltyMin`（聚合）/ `remainingLoadKg` | **动作集是真源**：GUI 的 `onAdvanceStop` 完全按它做状态转移，不再有「趟」可反查；逐单窗口要求每张送达单带自己的 `late`/`penalty`；停靠零耗时 ⇒ 没有「离开时间」字段 | 定长 O(动作数)；停靠内**先卸后装**，峰值取「卸后/装后」较大者；`remainingLoadKg` = 到达在车 − 送达 − 降载 + 取货 + 取回 | 界面与汇总各自重算等待/罚时（口径必漂）；或维护一张「订单→停靠」的反查表 | `finalize` 生成 → `RoutePlan::stops`（真源）→ 停靠明细面板 / 超时订单面板 / `RouteMetrics` | `late`/`penaltyMin` 是**停靠级聚合**，别拿它代替逐单（逐单真源是 `deliveries[]` 与 `metrics.orders`） |
| `RoutePlan`（+ `PlanStatus`） | 一次规划的完整结果：`stops`（**真源**）+ `offloads`（custody）+ `metrics` + 由 `stops` 一次展平的 `nodes`/`nodeArrivalMin`/`nodeIsStop` + 汇总（距离/耗时/成本/penalty/回程时刻） | 真源只有一份（`stops`），扁平字段是**兼容视图**且只在一处生成 ⇒ 两套数据不会各自走样；界面按下标推进，扁平序列比「在结构里找第几个节点」直接 | 空间 O(节点数 + 停靠数)；展平 O(节点数 + 停靠数)；失败用 `PlanStatus{Ok, OrderExceedsCapacity, Unreachable}` + `reason` | 调用方自己维护「路线」与「整条节点序列」两份数据并保持同步 | `replan`/`planRoute`/`insertOrder`/`replanIncremental` 产出 → GUI 推进与高亮 / `sliceRemainder` 切剩余 → 再喂 `replanIncremental(previous)` | `plan.nodes` 为空时 `nodeIndexAtTime` 返回 0（**调用方自行判空**）；`totalTimeMin` 用**未取整**的 elapsed 算 |
| `finalize`（展平点） | 把 `stops` 展平成 `nodes`/`nodeArrivalMin`/`nodeIsStop`，并汇总指标与 custody | **唯一生成点**：任何出口都只在这里生成视图，忘一处就拿到旧视图 | O(节点数 + 停靠数)；在所有规划出口各调一次 | 每个消费者各自展平一遍，视图立刻与 `stops` 走样 | `RoutePlan::stops` → `finalize` → 扁平字段 → GUI 推进 / `isEdgeOnRoute` / `sliceRemainder` | `nodeIsStop` 与 `nodes` **等长**且同一节点可能多次出现（只有作为停靠的那次为 true） |
| `OnboardItem` | 车辆**此刻已在车上**的货：`nodeId`（目的 B）+ `kg` + `orderId` | 重规划若不知道「车非空」，规划器会假设货都在起点 ⇒ 每次重算都先跑回基地（P17 实测「车在仓库与客户间反复跳跃」）；**按订单记账**是因为同节点多单下按 nodeId 扣货会把别的单一起扣掉（issue #5） | O(在途单数) | 重规划出来的每一段都可能先回基地，与车的物理事实脱节 | GUI 从当前 `RoutePlan` 推出在途货 → `replan`/`insertOrder`/`replanIncremental` → `Ctx.onboard` → `replay` 的初始在车量 | 必须与 `StashState` 一起传；漏传会让在车货被当成「还没取」而重复生成取货动作 |
| `OffloadLeg`·`StashState` | 降载 custody 记录（站 / 单 / 送达点 / kg / 卸下时刻 / 取回时刻）与跨重规划暂存（站 + `OnboardItem[]`） | 「同车卸、同车取」必须有账可审：暂存守恒（Σ卸入 − Σ取回）、期末 0、取回先于该单送达，全靠它；与（规格二的）转运**分型**——判据就是「卸入车 == 取走车 ⇒ 降载」 | `OffloadLeg` O(降载单数)；选站对每座中转站构造一次降载版路线（可行者按三键取优），一经选定即**锁站单堆**；`StashState` 透传 O(暂存单数) | 从行程序列反推「哪张单在哪卸、还要回哪取」，守恒无从断言、界面也画不出「当前暂存货(kg)」 | `insertOffloadStop`/`insertReclaimStop` → `Stop.offloads`/`reclaims` + `RoutePlan.offloads` → 面板与守恒断言；GUI 把 `StashState` 透传 `replanIncremental`（含全量回退） | 不主动为「更优」进站；只卸**整张普通单**、绝不卸紧急货、不卸 A/B 目的地的货；锁站不可达 ⇒ 全量兜底，仍不行 ⇒ 拒绝该单 |
| `RouteMetrics` + `OrderMetric` | 摘要与验收口径：S / A / 逐单 penalty 与准时 / 取货准时率 / 送达准时率（总·紧急·普通）/ 平均在车 / 利用率 / 峰值 | `--plan-summary` 的四行与 13 字段都要落到**可断言**的结构上，而不是在渲染处现算；取货准时判据 `t_pick + 最短耗时(A→B)×timeFactor ≤ we` 必须与规划同口径 | O(订单数)；平均在车 = Σ(段在车量 × 段时长) / 总运行时长（含首末空驶段） | 各处渲染时各算一遍，口径必然分叉（G4 的「取货准时率 ≥ 送达准时率」也就守不住） | `finalize` 汇总 → `RouteMetrics` → `--plan-summary` / 路线信息面板 / `integration_tests` 黄金值 | 分母 0 的率打印 **`—`**（不是 0%）；峰值载重**不进**构造键，只作指标 |

## 6. 基础记录速查（没有算法、只有字段，故不占上面七栏）

| 类型 | 字段要点 | 一句话 |
|---|---|---|
| `Node` | `id` / `type` / `x,y` / `subNetworkId` | 2 仓库 + 3 中转站 + 25 配送点；`subNetworkId` 只做**界面分组**与**新客户归属继承**（不是簇划分、不是多级图） |
| `Edge` | `fromId`/`toId` / 三权重 / `baseTimeMin` / `congested` | 有向；同一对 `(from,to)` 至多一条；`baseTimeMin` 由 `addEdge` 在未指定时固化为当前 `timeMin` |
| `Order` | `id` / `nodeId`(B) / `pickupNodeId`(A, **必填**) / `demandKg` / `windowStartMin` / `windowEndMin` / `urgent` / `source` / `picked` / `served` | **全部 A→B 取送**；窗口只属于 B；`source` 是运行时字段（`initial/event_normal/event_urgent/manual_customer/manual_urgent`，前缀 O/N/U/C/U） |
| `Vehicle` | `id` / `startNodeId` / `capacityKg` / `departTimeMin` / `timeFactor` / `costFactor` | 六字段；因子只乘**当前耗时**与**成本**，距离/等待/penalty 不乘；约束的是**前缀在车量**，不是总需求 |
| `StopDelivery` | `orderId` / `late` / `penaltyMin` | 逐单窗口的直接产物：一个停靠一个到达时刻，但每张单按自己的 `we` 判迟到 |
| `PathResult` | `found` / `nodes` / `totalWeight` | `Dijkstra` 的唯一出口；`found=false` 时 `nodes` 为空 |
| `TrafficChange` | `fromId`/`toId` / `increaseRatio` / `congested` | 一次改动的账目；`increaseRatio` 就是本次施加的增幅（**不叠加**） |
| `EventLevel`·`EventWeights` | `extra_low/low/medium/high` → 1/3/9/27；默认 路况/紧急/普通/封路 = 27/3/9/1（Σ=40） | 配置只写等级；权重只有 `eventLevelWeight` 一处定义 |
| `PlanStatus` | `Ok` / `OrderExceedsCapacity` / `Unreachable` | 只有「**单笔**订单就超载」或「存在不可达点」才不可行；总需求超载是常态 |

## 7. 口径与三条别踩

1. **数字前提**：本文复杂度都按 §0 口径写；`ctest` **目标数 16**（`ctest -N` 为准）、9 个二进制**自报 2273 项**、`cli_plan_summary` **162 项**、`--self-check-actions` **79 条 OK**——**四个口径，不许混**（2026-11-24 实测）。
2. **「趟」已退役**：`Trip`/`multiTripPlan`/`flatten` 的趟边界/`nodeTripIndex` 在 `src` 里 `grep` **0 命中**；现行真源是 `RoutePlan::stops`（动作集）。设计 §2/§4/§5 里保留的「注（2026-09-26）」「多趟分批」段落**只作历史**，冲突时以 `src/` 为准。
3. **复杂度写成 O(·) 不等于本项目规模下真有收益**：`MinHeap` 换线性扫在 n=30 时同阶（它的意义是考点）；中转站集散的里程收益**不成立**（干线下界相同），评价该用「可行性 + 停靠数/动作数 + 总权重」。
