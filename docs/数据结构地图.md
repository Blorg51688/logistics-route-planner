## 0. 全文统一的前提（不写清前提的复杂度等于没写）

**n** = 节点数（当前数据 **30**）、**m** = 有向边数（**106**）、**deg** = 某节点的出度、
**m_task** = 订单数（**25**）、**S** = 停靠数（默认三策略 28–30）、**A** = 动作数（50）、
**s** = 堆内条目数、**count** = 一次路况改动的边数（默认 **11**）、**k** = 车数（**4**）、
**L** = 配置文本总行数、**r** = 某节的记录行数、**R** = 局部重排/转运的轮数上限（3）。

当前数据口径（`config/default.ini`，**已提交基线** `main`，2026-11-26 复核）：2 仓库 + 3 中转站 + 25 配送点 = 30 节点；
106 有向边 = 50 个双向道路对（100 条）+ **6 条单向边**；25 张订单（全部 A→B 取送，A≠B），总需求 516kg；
**四车** V01 400kg·08:00·1.00·1.50（快车）/ V02·V03·V04 160kg·08:00·1.25·0.80（慢车），全部 W01 发车（详见 `Vehicle` 一节）。

**事实来源**：`src/`（`main` @ `359ad44`，规格一 #32–#37、规格二 #39–#43、**规格三 #44–#50 均已落地**）+ 现有文档。
文中一律用「`文件:符号名`」，不用行号（行号会漂）。

## 2. 表 1 · 存储与配置层（结构本体 + 承载它的记录）

| 结构 | 是什么 | 为什么是它（排除谁 / 依据） | 特点与复杂度（前提） | 没有它得自己写什么 | 连接：谁喂它 → 它 → 谁消费 | 代价与坑 |
|---|---|---|---|---|---|---|
| `IniFile`·`IniSection`·`IniRecord` | INI 文本 → 带行号的记录序列（节 → 记录） | 解析错误必须报行号 ⇒ 记录自带 `lineNo`，而且 `findValue` 返回**记录本体**而非值（报错时才带得上行号）；节数与记录数都很小（`[general]` 8 行）⇒ 顺序 `vector` 足够，不必建键索引 | `parse` O(L)；`findSection` O(节数)；`findValue` O(r) | 逐行扫描 + 手维护一张「值 → 行号」旁表 | `config/default.ini` → `IniFile::parse` → `IniSection`/`IniRecord` → `ConfigLoader::load` | 只认 `#` 注释；重复节名直接失败；不做语义校验（语义都在 `ConfigLoader`） |
| `Config` | 一次加载的完整结果：图 + 车辆列表 + 订单 + 全局参数（含**四个事件等级**） | 把「文件里的四类数据」收成一个值对象，规划器与界面只依赖它、不依赖 INI 形状；事件**权重不落配置**，只落等级，权重由 `Config.h::eventLevelWeight` 的固定表派生 ⇒ 改配置不改代码、也不会出现两份权重表 | O(n + m + 订单数) 空间；纯数据、无方法 | `ConfigLoader` 要回传 4 个出参，或每个调用点自己再解析一遍 | `ConfigLoader::load` → `Config` → `replan`（GUI 入口）/ `planRoute`（CLI `--plan-summary`、测试入口）/ `MainWindow` 按值持有 | 事件参数只剩 `event_interval_min` + 四个 `event_level_*`；`Config::graph` 是**值**，不是引用；`vehicles` 是**列表**（现行四台，见 §0） |
| `LogisticsGraph` | 有向带权图：`nodes_` 顺序表 + `out_` 邻接表，两者下标严格对齐 | 图是稀疏的（30 节点 / 106 有向边）⇒ 邻接矩阵 900 格绝大多数为空、而每格还要塞 3 个权重；下标对齐让「节点 i 的出边」是 O(1) | n、m、deg：`indexOf` **O(n)**（线性扫）；`findEdge` O(deg)；`addNode` O(n)；`removeNode` **O(n+m)**（入边散落在别人的出边表里）；空间 O(n+m) | Dijkstra 每轮自己从边表里筛边（每次 O(m)），或另建一份邻接结构 | `ConfigLoader` 装配 → `Dijkstra` 只读 `adjacency()`、io 输出邻接表/矩阵 → `Traffic`/`GraphEdit` 就地改 → GUI 只读遍历 | 没有反向邻接表 ⇒ 删点 O(n+m)；`indexOf` 是 O(n)（节点数小，不为它引入索引）；**不提供可写 `Edge*`**，防调用方改坏 `fromId` 等不变量 |
| `Node`·`Edge`（记录） | 图的两条记录类型；`Edge` 携带三权重 + `baseTimeMin` + `congested` | 三权重并存才能「同一张图、三套策略」；`baseTimeMin` 单列，是因为路况判定要「相对基准的增幅」，而 `timeMin` 会被就地改写 | 定长 O(1)；`findEdge(from,to)` O(deg) | 想把耗时还原成「畅通」就得另存一张初始耗时表并永久同步 | `ConfigLoader` 构造 → `out_` → `Dijkstra` 松弛 / `Traffic` 改 `timeMin` / GUI 画箭头 | `updateEdgeTime` 只改 `timeMin`，`congested` 由「是否高于 `baseTimeMin`」自动维护；`Node::x/y` 只供 GUI 布局 |

## 3. 表 2 · 手写算法层（「手写算法、不手写轮子」的落点）

| 结构 | 是什么 | 为什么是它（排除谁 / 依据） | 特点与复杂度（前提） | 没有它得自己写什么 | 连接：谁喂它 → 它 → 谁消费 | 代价与坑 |
|---|---|---|---|---|---|---|
| `MinHeap` | 手写二叉最小堆，元素固定 `Entry{key:double, value:int}`（底层 `std::vector`） | 课程硬性要求堆自写（禁 `std::priority_queue`·`make_heap`）；**不做成模板**，因为全项目只有 Dijkstra 一处用、元素类型固定 | `push`/`popMin` 各 O(log s)；`siftUp`/`siftDown`/`swapEntries` 全自写；空堆 `popMin` 返回 false 且不改出参 | Dijkstra 每轮取最小扫一遍 `dist[]`（O(n)）——n=30 时同阶，所以收益是**考点**不是提速 | `Dijkstra::shortestPath` → `push`/`popMin` | **没有 decrease-key** ⇒ 同节点留下过期条目（≤ m），靠 `currentDist > dist[current]` 惰性删除 |
| `Dijkstra::shortestPath` + `dist[]`·`previous[]` | 单源单目标最短路：距离数组 + 前驱数组 + 惰性删除堆 | 三种策略**共用这一份实现**，只在 `pickWeight(Distance/Time/Cost)` 换权重来源；用前驱数组复原路径，而不是让堆条目携带整条路径 | `dist`/`previous` 各 O(n)；时间 **O(m·n + m·log m)**（松弛内层 `graph.indexOf` 是 O(n)）；路径复原 O(路径节点数) | 把前驱数组换成「堆里带路径」会让每次松弛多 O(n)；三套策略要写三遍 | `adjacency()` → `shortestPath` → `PathResult` → `CostMatrix::build` | 不可达时 `found=false` 且 `nodes` 为空；`kInfinity` 只是哨兵；**无 decrease-key 是设计，不是缺陷** |
| `CostMatrix`（+`scaledWeight`） | **全源最短路预计算**：V×V×3 三张表（按距离/耗时/成本各自最优路径的三项指标） | pair-insertion 每次评价要查大量 (站→站) leg，逐个调 Dijkstra 会让「一个候选 = 一次最短路」变成主开销 ⇒ 一次建表、之后 O(1) 查；同时把**车辆因子**收在一处（耗时×timeFactor、成本×costFactor） | 建表 = V×3 次 Dijkstra ≈ **O(V·(m·n + m log m))**；查询 `legAll` O(1)；空间 V²×3 | 每个候选位置对都现算最短路（数量级 ×n² 次），或缓存一份自己维护的旁表 | `Ctx.matrix.build(graph)` → `tryInsertPair`/`replay`/`repairRoute`/`insertReclaimStop` 的每次 leg 查询 | 表按**基础图**建、因子在查询处乘——所以路况改边后必须**重建**（`makeCtx` 每次规划都重建）；`reachable` 用「距离维 ≥ 0」判可达 |
| **pair-insertion**（`tryInsertPair` + `replay` + `compareRoutes`） | 把一张订单的 (A,B) **对**插到普通段的最省位置：枚举全部位置对、逐个重放评价、取键最小 | 规格一 #18 的构造器：**penalty 先**的 cheapest insertion，取代「贪心选最近邻」（最近邻会在紧窗单上迟到——测试 `testPairInsertionBeatsNearestNeighbourOnTightWindow` 直接钉住这一点）；同节点并入既有停靠，减少停靠数 | 单请求 = O(n²) 位置对 × O(n) 重放 = **O(n³)**；m_task 张单 ⇒ O(m_task·n³)；`replay` 里同时判 F1–F7（不可行立即剪掉） | 自己写「每个位置合不合法、代价多少」的评价器；写时间/载重/penalty 的推进 | `Request` + `StopSpec[]` → `tryInsertPair` → `replay`/Eval → `compareRoutes`（三键）→ 采用或进入兜底 | 键序是 (Σpenalty, 策略权重, tieKey)，**载重峰值不进键**；耗时维的权重**含早到等待**（否则「最短耗时」策略会输出更长总耗时，设计 §4.7-②） |
| `repairRoute`（有界 relocate） | 普通段**局部重排**：按 EDD 序把普通单逐个摘下、重插到更优位置，某轮无改进即停，轮数 ≤ 3 | 位置对枚举是「先来先占位」的，前一张单可能挡住了后一张更优的位置；有界 relocate 补这个局部性，又不用整批重算（全量兜底太贵） | O(R·m_task·n³)，R ≤ 3；实测默认数据下多数轮次第 1 轮即无改进 | 全量重跑构造（O(m_task·n³) × 次数），或接受次优 | `insertNormalAll` 失败时 → `repairRoute` → 成功则继续、失败进兜底 | **只动普通段**：紧急段受 FIFO 约束，relocate 恒等；取回停靠也作为单点请求参与 relocate（先于暂存单送达是硬约束） |
| `buildAll`（多起点 + 两级兜底 + 降载） | 构造总调度：起点版本枚举 → 全量兜底 → 降载 → 拒绝 | 单一 EDD 起点会让某个策略在 ② 上被反超（单起点时成本策略 168.5 元 > 距离策略 145.3 元）；多起点把「插入序」这一维也纳入搜索，仍用**同一把三键**取优 | 3 个起点版本 ×（构造 + repair）≈ 3 × O(m_task·n³)；多起点**只在整批构造**（基地 / 空车 / 发车时刻）启用 | 自己写「哪个起点更好」的判断、失败后的重排、降载触发 | `insertionStarts` → `buildAll` → `Outcome{route, reason}` → `finalize` | 中途重规划（`replan` 带在车货/非发车时刻）**单起点**：构造次数多、时间预算不允许；`--self-check-actions` 36s 量级正是这条链的代价 |
| `GraphEdit`（`addRandomCustomer`·`closeRandomRoad`·`makeSyntheticEdge`） | 动态增删：随机位置插新客户、随机封一条路（双向删边）、手工加边的权重估算 | 坐标 → 权重的换算**从图自身既有边推算**平均比值（`estimateScale`），不硬编码尺度；封路前用 BFS 检查连通性，**不封桥**；新节点**继承最近邻的 `sub_network_id`**（#30 缺陷修复） | `estimateScale` O(m)；`reachesSkipping` 手写 BFS，队列 `vector` + 游标、`seen` 线性查找 ⇒ O(n·(n+m))；`addRandomCustomer` 找最近点 O(n) | 自己写「最近点 + 双向连边 + 权重估算 + 连通性检查 + 归属继承」 | 事件分派 / 手动动作 → `GraphEdit` → `addNode`/`addEdge`/`removeEdge` → 新图上的后续规划 | `seen` 是线性查找不是 `set`（节点量小）；封路是**双向**删边；最近邻是仓库时 `sub_network_id` 回落到最近的编号非 0 配送点/中转站 |

  ① 聚类 + 簇→慢车固定指派（slowVehicleOfCluster，职责表唯一决定点 legVehicleEligible）

**`buildLegs`**（`RoutePlanner.cpp::buildLegs`，声明 `RoutePlanner.h:382`）
- 用途：把**订单**展开成**腿**并定执行车。本地单（A、B 同簇）⇒ 1 条 `CustomerToCustomer`；跨簇单 ⇒ 恰好 3 条（L1 客户→本簇站 S_A、L2 S_A→S_B、L3 S_B→客户）。簇→站按 `subNetworkId` 查 `NodeType::Transit` 取 ID 最小者，**不硬编码 T01/T02/T03**。
- 为什么是它：腿是**任务结构的真源**，而 `RoutePlan::stops` 是**执行结果的真源**——两者分工是「计划形态」与「实际动作」。展开放在 `planFleet` 收口**最后**一步，是为了让执行车/时刻读到分配、接力、转运的最终值。
- 复杂度前提：O(订单数) 轮 × 常数条腿；每腿一次 `chooseLegVehicle`（O(k)）+ 一次最短路估计（`CostMatrix` 已建表 ⇒ O(1) 查）；末尾手写插入排序 O(m²)，m ≤ 3×订单数。
- 语义要点：先按结构立腿、**按规划期估计填时刻**，再由 `readRelayExecution`（`RoutePlanner.cpp`）用**实际**卸入/送达时刻与**实际**执行车覆盖；覆盖失败（接力没跑）就保留估计值并记日志，**不伪造**。跨簇单若被职责降级直达，则按实际形态登记 1 条腿并打 `LEGDEGRADE`。
- 守卫：`routeplanner_tests::testLegsCrossClusterExpandsToThreeInFixedOrder`（跨簇单恰 3 条、固定顺序、行序）、`testLegsReadyTimeChainAndTemporaryAssignment`（L1.ready = 发车时刻、L2.ready == L1.plannedArrival、L3.ready == L2.plannedArrival、严格递增、`temporaryAssignment` 可断言）、`integration_tests::checkDefaultLegsAreLocalSingleLegs`（默认 25 单 ⇒ 25 条单腿）、`cli_plan_summary::checkLegDegradationVisibleInDump`。

**`applyRelayLayer` / `buildRelayChain`**（`RoutePlanner.cpp::applyRelayLayer` 是内部函数（不导出；见 `RoutePlanner.h`「跨簇单的处置」段）；`buildRelayChain` 在 `.cpp` 匿名命名空间，产物结构 `RelayBuild`/`RelayOutcome`）
- 用途：跨簇**普通**单走三段接力——L1 本簇慢车、L2 快车、L3 对簇慢车；跨簇**紧急**单只有「该单直达 penalty **严格小于** relay penalty」时才允许快车直达，否则也进来接力。分流判据与职责表 `legVehicleEligible` 的快车侧**同一句**，不在本层重新解释。
- 为什么是它：接力是**结构性必需**（跨簇单只能走三段腿），但僵化的形式会产生荒谬解 ⇒ 保留「不更差」兜底：三段腿方案劣于「把该单直接给快车」的对照方案时退回直达并记日志；比较分「对照合法（比 (逐单 penalty, 策略权重) 两键）/对照不合法（只比逐单 penalty）」两种，**都不带均衡键**（设计 §4.8-①）。
- 复杂度前提：每张待接力单一次 `buildRelayChain`，内部三次「摘单 + 插入一条腿 + 重放」，每次插入器 O(n²) 位置 × O(n) 重放 = O(n³)；单数少（只限跨簇普通单）⇒ 整体 O(#跨簇单 × n³)。前瞻窗口 `kLookaheadWindowMin = 60` 与站内停留上限 `kTransferMaxDwellMin = 60` 都在 `replay` 里**当可行性判据**用（有界性由构造保证，不靠事后过滤）。
- 车等货：`wait = max(窗口等待, readyTime − rawArrival)`，等待计入该车耗时、**不计** penalty；旧「货等车」模型下 dwell 恒为负 ⇒ 转运恒不可行。
- 守卫：`cli_plan_summary::checkCrossClusterRelayOnDefaultData`（默认配置 + O26 `D08→D18`，三策略都必须走完 L1 `D08→T01`(V02) / L2 `T01→T03`(V01) / L3 `T03→D18`(V04)、账本恰 1 笔 `TRANSIT` 且两端不同车、期末「已送达」、快车仍「空车 0」）、`routeplanner_tests::testRelayThreeLegChainViaPlanFleet`、`testDutyBoundaryOnFourVehicleFleet`、`routeplanner_tests` 的 `kLookaheadWindowMin` 有界性族（反向验证：把 `kLookaheadWindowMin` 改成无界即红）。

**`repairCustodyBreaks`**（`RoutePlanner.cpp::repairCustodyBreaks`，判定辅助 `unpairedUnloadOrders`）
- 用途：`rescheduleFleet` 收口前的 custody 断链修复。判据只读**计划产物**：某笔 `transitUnload` 找不到「同站、另一台车」的 `transitPickup` ⇒ 货物在站里没有承接人（跨站无承运，正是封路把 T01→T03 快车腿吃掉后的病灶）。
- 为什么是它：首选「用新图**重跑该单的三段接力**」而不是直接拒绝——封路只堵直连，经 W01 的绕行通常仍在，一刀切拒绝会把能走通的单也丢掉；只有新图下确实接不上才显式拒绝并记原因（落在五级链第 ⑤ 级）。
- 复杂度前提：`unpairedUnloadOrders` = O(全部停靠 × 动作数 × 同站扫)；只在**封路/路况**事件上修（`repairEnabled`），新单/手动不改已执行前缀；无断链时原样通过 ⇒ 默认数据与无跨簇事件逐字不变。
- 守卫：`integration_tests::checkClosureCustodyContinuous`（封路夹具上「T01 卸入、T03 取走」必须被修复成合法三段接力或被显式拒绝；反向验证 = 关掉本函数据即红，见 `docs/测试用例表.md` §6.6）。

**`auditCustody`**（`RoutePlanner.cpp::auditCustody`，声明 `RoutePlanner.h:620`）
- 用途：「期末 0」的**真断言**。逐单核三件事：① 每笔卸入都有「同站、另一台车、时刻不早于它」的取走；② 每笔取走都有同站卸入；③ 整单不可拆 ⇒ Σ卸入 kg == Σ取走 kg；④ 期末每单要么送达、要么在拒绝名单里被**显式**拒绝（有原因）。
- 为什么是它：只读用户能看到的产物（`--dump-plan` 的 STOP/TRANSIT 行同源），**不重算公式**；账本按站配对，跨站断链进不了账本 ⇒ 只查账本会「假绿」。
- 复杂度前提：O(Σ停靠 × 动作数)；事件按订单分桶（`std::map`），配对在同站内线性扫；缺口按「订单表顺序 + 事件顺序」输出，**确定性**。
- 守卫：`integration_tests::checkClosureCustodyContinuous`（调 `logistics::auditCustody(...)` 断言 `ok`）。
