## 1. M1 异构调度（默认数据，零额外操作）

**演什么**：三策略各自把哪些簇给哪台车、逐车指标差异、完工耗时 vs 车时合计。

```bash
for s in distance cost time; do echo "==== $s"; ./build/app --plan-summary $s 2>/dev/null; done
```

**现场操作（GUI）**：

1. 重启进程（干净状态）。状态栏「软件内时间：08:00」；车辆信息 **3 个页签**（V01·400kg / V02·160kg / V03·160kg）；路线信息底部「── 逐车指标 ──」三行。
2. 策略 = 最短距离 → 记录逐车指标三行与画布三色路线（红 V01 / 蓝 V02 / 绿 V03；选中页签的车加粗）。
3. 策略 = 最低耗时 → 三色路线与逐车指标都变（长腿簇归快车 V01 的可见证据）。
4. 指认 **均衡度（峰值利用率极差）** 一行；指认「完工耗时 ≠ 车时合计」两处数字（状态栏/路线信息），说明两个口径并列。

## 2. M2 跨车转运（**实测口径重要**）

### 2.1 先看默认数据上的实测结论（如实记录）

默认数据 **三条判据静态全不触发**（0 跨簇、每簇一批不超容量、初始无紧急单）。按 §7.7 的候选插一张跨簇普通单：

```bash
# A=D08（sub1 枢纽）、B=D18（sub3）、8kg、窗口 [现在, 24:00]
cp config/default.ini /tmp/with_m001.ini
printf 'M001, D08, D18, 8, 08:00, 23:59, 0\n' >> /tmp/with_m001.ini
for s in distance cost time; do
  echo "==== $s"; ./build/app --config /tmp/with_m001.ini --dump-plan $s 2>/dev/null | grep -E 'TRANSIT|ALLOC M001'
done
```

**实测（2026-11-24）**：三策略**都没有 TRANSIT 行**；时间策略把 M001 直接分给 V01（`ALLOC M001=V01`），跨车转运无从发生。对全部 **414 个跨簇有序对 × 8kg / 15kg** 做同一探测，**接受数 = 0**（探针读到 applyTransitLayer 的 acceptedRounds 全为 0）。原因：当前实现的 Δkey 选车会把跨簇长腿交给快车 V01；慢车接手后再 relay 的严格更优条件不成立。**这是当前实现的实测事实，不是脚本写错**；本脚本不承诺在默认数据上「一定看到转运账本行」。

- **观察点 ①**：时间策略有且仅有一行 `TRANSIT`，卸入车 V02 ≠ 取走车 V01，站内等待 0 ≤ 60，状态「已送达」。
- **观察点 ②**：距离策略**没有** TRANSIT 行（两版距离精确并列 ⇒ 严格更优不成立 ⇒ 保留禁转运版）。
- **观察点 ③**：`--plan-summary time` 的 9 行里，V02/V01 的距离/耗时/成本与禁转运版不同（转运收益落在「耗时」上）；这是「三策略三种结果」的 CLI 证据。

**GUI 形态**（同一夹具）：

```bash

```

1. 策略 = 最低耗时 → 重新规划 → 日志出现「[转运] 判据①（跨簇订单）…」分级播报。
2. 推进一站直到 08:03 的 T01 卸入 → **转运账本面板出现一行**（订单 O1 / 站 T01 / kg 10 / 卸入 V02 08:03 / 取走 V01 08:03 / 等待 0 / 状态在站）。
3. 继续推进直到 O1 送达 → 账本行状态变「已送达」；期末账本**不得有「在站」行**。
4. 回到默认配置再跑可见「没有转运」——默认数据三判据不触发，是「绝不更差」的经验证据。

## 3. M3 不可达处置（删桥边）

**为什么不用事件封路**：`closeRandomRoad` 显式跳过桥边（封闭后两端须仍连通），所以事件封路**永远**造不出不可达；必须用「手工增删…」删任意双向边。

**桥边实测（2026-11-24，4 对）**：`D04–T01`、`D16–T02`、`D23–T03`、`D24–T03`。

**CLI 复现（不依赖 GUI）**：

```bash
python3 - <<'PY'
lines = open('config/default.ini', encoding='utf-8').read().splitlines()
out = []
for ln in lines:
    p = [x.strip() for x in ln.split(',')]
    if len(p) >= 2 and {p[0], p[1]} == {'D04', 'T01'}:
        continue
    out.append(ln)
open('/tmp/no_bridge.ini', 'w', encoding='utf-8').write('\n'.join(out) + '\n')
PY
for s in distance time; do
  echo "==== $s"; ./build/app --config /tmp/no_bridge.ini --dump-plan $s 2>/dev/null | grep -E 'INFEASIBLE|PLAN'
done
```

**实测输出（2026-11-24）**：

```text
==== distance
PLAN V01 W01 W01 480
PLAN V02 W01 W01 480
PLAN V03 - - 480
INFEASIBLE V03 无法从 W01 到达送达点: D04
==== time
（同上：V03 INFEASIBLE，原因逐字相同）
```

**GUI 现场（8 步脚本的第 8 步，可选、放最后）**：

1. 重启进程（默认三车）。
2. 手工增删… → 选 D04 与 T01 → 删除边（双向）。
3. 重新规划 → 日志出现「不可达 / 不可行 + 原因」，且**照实拒绝并报原因**（不通过违反容量或先取后送去凑解）。
4. ⚠ 删边不可撤销；演示后重启进程。

## 4. §7.7 的 8 步现场脚本（逐字操作序列）

```text
0  重启进程（干净状态；默认三车）
1  载入：状态栏「软件内时间：08:00」；车辆信息 3 页签（V01·400kg / V02·160kg / V03·160kg）；
   路线信息底部「── 逐车指标 ──」三行
2  策略 = 最短距离 → 记录逐车指标三行与画布三色路线
3  策略 = 最低耗时 → 三色路线与逐车指标都变（长腿簇归 V01 的可见证据）
4  事件注入 →「插入普通订单…」：A=D08（sub1 枢纽）、B=D18（sub3）、8 kg
   → 订单表出现该单；日志播报「插入普通订单 M001：D08 取 → D18 送」与指派到的车
5  策略 = 最低耗时 →「重新规划」
   → 观察：日志出现转运分级播报行（**是否出现账本行以实测为准**；默认数据实测不出现）
6  策略 = 最短距离 →「重新规划」（同一张单、同一个图）
   → 观察：不出现转运（两版距离精确相等 ⇒ 严格更优不成立）
7  推进一站数次直到该单送达 → 若已产生转运，账本行状态变「已送达」；期末账本无「在站」行
8（可选）不可达：手工增删 → 删除 D04–T01 → 日志出现「不可达 / 不可行」播报；⚠ 此步不可撤销，放最后
```

**第 5/6 步的实测钉死（2026-11-24）**：默认数据上第 5 步**不会**出现转运账本行（无 TRANSIT / acceptedRounds=0）；第 6 步同样不出现。**M2 的可靠演示请走 §2.2 的夹具**。第 8 步已用 §3 的 CLI 复现钉死（V03 INFEASIBLE，原因「无法从 W01 到达送达点: D04」）。
