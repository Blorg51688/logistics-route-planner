## 0. 30 秒版

**一句话**：把城市物流网络建成**有向带权图**（邻接表存储，30 节点 / 106 有向边），用**手写二叉最小堆 + Dijkstra** 求任意两点在三种权重（距离 / 耗时 / 成本）下的最短路，再用**手写贪心**把最短路串成配送路线；配送过程由**软件内时间**驱动四类模拟事件（路况 / 紧急订单 / 新客户 / 道路封闭），事件可触发**增量式重规划**。

**必须记住的三组数字**（工作区基线实测）：

| 组 | 数字 |
|---|---|
| 数据规模 | 节点 **30**（2 仓库 + 3 中转站 + 25 配送点）· 有向边 **106**（其中无向道路对 **56**、单向边 **6**）· 订单 **25** |
| 车辆与趟数 | 载重 **200 kg** · 发车 **08:00** · 总需求 **740 kg** → 实测 **6 趟** |
| 三策略黄金值 | distance `178.200 km / 378.300 min / 244.200 元 / penalty 166 / 6 趟`<br>cost `186.300 / 461.000 / 235.900 / 207 / 6`<br>time `183.200 / 372.100 / 255.200 / 201 / 6` |

> 「6 趟」不是拍出来的：三个簇的需求分别是 262 / 220 / 258 kg，**每簇都略超 200 kg 载重** ⇒ 每簇 2 趟 ⇒ 6 趟。这条推导可在 §6.4 复核。

**质量口径**（两个口径，不许混）：
- `ctest` 目标数 **20**（`ctest -N` 为准），工作区基线实测 **20/20 通过**；
- 9 个测试二进制**自报检查项合计 829 项、0 失败**（前者是"测试目标数"，后者是"断言/检查数"）。
- 三策略黄金值上方三行已逐项复现一致。

## 2. `LogisticsGraph`：有向带权图的存储

**用途**：承载整个配送网络（节点表 + 邻接表），并提供 B3 要求的邻接表 / 邻接矩阵文本输出。

**存储**（`LogisticsGraph.h:LogisticsGraph` 私有段）：

```cpp
std::vector<Node>              nodes_;   // 节点表
std::vector<std::vector<Edge>> out_;     // 邻接表：out_[i] = nodes_[i] 的全部出边
```

**不变量**：`nodes_` 与 `out_` **下标严格一一对应**（`out_.size() == nodes_.size()`，删点必须两个表同位删）。

**选型理由：为什么是邻接表而不是邻接矩阵**

| 比较项 | 邻接矩阵 | 邻接表（本项目） |
|---|---|---|
| 空间 | O(n²) = 30×30 = **900 格** | O(n + m) = 30 表头 + **106** 边条目 |
| 遍历某点全部出边 | 必须扫整行 O(n) | 直接取 `out_[i]`，O(deg) |
| 多权重 | 每格要存 3 个权重（距离/耗时/成本），或开 3 张矩阵 | 每条边存一次，三个字段并排 |
| 删节点 | 要搬整行 + 整列 | 两表同位 erase + 扫全部出边表删入边 |

n=30、m=106（无向道路对 56）是**稀疏图**：矩阵 900 格里绝大多数是"无边"。需求原文也点名"采用**邻接表**存储图（适合稀疏路径网络）"。
**注意一句诚实**：本项目 V=30 小到两种表示都能跑；选邻接表的真正理由是**稀疏 + 遍历局部性 + 多权重存储**，不是"矩阵跑不动"。邻接矩阵输出仍然保留（`toAdjacencyMatrixString`），因为 B3 要求两种表示都输出。

**关键操作与复杂度**（前提：n = 节点数，m = 有向边数，deg = 该点出度）

| 操作 | 复杂度 | 说明 |
|---|---|---|
| `indexOf` | **O(n)** | **线性扫描，没有维护 id→下标映射表**（见下） |
| `addNode` | O(n) | 查重靠 `indexOf`；尾部 push + `out_.emplace_back()`（均摊 O(1)） |
| `addEdge` | O(n + deg) | 两端点校验 O(n) + 同 `(from,to)` 查重 O(deg) + 尾插 |
| `removeNode` | **O(n + m)** | 两表同位 erase（O(n) 搬移）+ 扫**全部**出边表删入边（O(m)） |
| `removeEdge` | O(n + deg) | |
| `updateEdgeTime` | O(n + deg) | 只改 `timeMin` 与 `congested`，**`baseTimeMin` 不动** |
| `findEdge` / `findNode` | O(n + deg) / O(n) | 未命中返回 `nullptr` |
| `edges()` | O(n + m) | 拍平副本，供遍历与输出 |
| `toAdjacencyMatrixString` | O(n²) | 输出矩阵本身就是 n² 格 |

**要主动讲清的一条（我核出来的、和常见说法不同）**：
`LogisticsGraph.cpp:indexOf` 是**线性扫描**，**没有** `std::map`/哈希做"id→下标映射"。
- **代价**：Dijkstra 每次松弛都要对 `edge.toId` 调一次 `indexOf` ⇒ 额外 **O(m·n)** 量级（m 次松弛 × 每次 O(n)）。
- **换来的**：删点 / 改图后**没有任何映射需要失效或重建**——一致性风险被结构性消除。
- **为什么接受**：n=30 时 O(m·n) ≈ 106×30 ≈ 3 千次比较，属常数级别；代码注释亦写明"节点数很小（30 量级），线性查找下标足够；不为此引入额外的索引结构"。
- **若现场问"节点上万怎么办"**：加一张 `std::map<std::string,int>` 或哈希即可（**容器不受 STL 口径限制**），算法一行不用改。这条"用查找换掉失效风险"本身就是答辩加分点。

**落点**：`LogisticsGraph.h:LogisticsGraph`（`nodes_` / `out_` / `adjacency()`）、`LogisticsGraph.cpp:indexOf/addNode/addEdge/removeNode/removeEdge/updateEdgeTime/toAdjacencyMatrixString`；`Node.h:Node`、`Edge.h:Edge`。

## 3. `GraphEdit`：图编辑（B5 动态增删）

**用途**：模拟"新客户"与"道路封闭"两种图变更，并给界面手工加边提供权重估算。

| 函数 | 做什么 | 关键点与复杂度 |
|---|---|---|
| `GraphEdit.cpp:addRandomCustomer` | 随机位置插入一个配送点，与**最近的既有节点**双向连通，返回新 ID | 找最近 = O(n) 扫描；双向各 `addEdge` 一次 |
| `GraphEdit.cpp:closeRandomRoad` | 随机封闭一条道路：删该有向边，反向边存在则一并删 | **不封桥**：封闭前用 `reachesSkipping` 双向各判一次"跳过这条双向路后还能不能互相到达"，不成立就换一条 |
| `GraphEdit.cpp:makeSyntheticEdge` | 为给定两点造一条与图中既有边口径一致的边 | 权重尺度**从既有边推算**（`estimateScale`：kmPerUnit / minPerKm / yuanPerKm），不硬编码"坐标单位→公里" |

**`reachesSkipping` 是本项目唯一的手写 BFS**（`GraphEdit.cpp` 匿名命名空间内）：用 `std::vector` 当队列 + 头指针 `head` 手动前进，用 `seen` 线性查重。
- 复杂度：O(n·(n+m)) 最坏（`seen` 线性查重，n=30 无所谓）。
- **为什么手写**：§10.1 明确"**图遍历的判定逻辑**必须自己写"——连通性判定属算法主体，不能借现成组件。（容器照样用 `std::vector`。）

**为什么"不封桥"值得讲**：初版封闭道路只看"这条边存不存在"，结果封掉 `T02↔D15` 后 D15 成孤岛，一次按钮点击就把演示锁死在"不可行"。修复后加了这个判定，并有跨 20 种子的连通性测试守着（见 `docs/设计.md` §15）。这是"**数据结构支撑调度决策**"的典型例子：图的连通性约束直接决定调度能不能继续。

**落点**：`GraphEdit.h:addRandomCustomer/closeRandomRoad/makeSyntheticEdge`、`GraphEdit.cpp:reachesSkipping/estimateScale`。

## 4. `MinHeap`：手写二叉最小堆

**用途**：Dijkstra 每轮"取出当前距离最小的节点"。

**存储与选型**（`MinHeap.h:MinHeap`）：
```cpp
struct Entry { double key; int value; };   // key = 权重，value = 节点下标
std::vector<Entry> entries_;              // 二叉堆的数组表示
```
- **非模板**：元素类型硬编码为 Dijkstra 需要的 `(double 权重, int 节点下标)`。
- **数组表示的堆**：下标 `i` 的父 `(i-1)/2`、左子 `2i+1`、右子 `2i+2`；**不建任何树节点/指针**，空间 O(s)（s = 当前堆内条目数）。
- 底层动态数组用 `std::vector` 承载——按 §10.1，**容器不受限**；受禁的只是"把算法主体交给 STL"。

**关键操作**（s = 堆内条目数）：

| 操作 | 复杂度 | 做法 |
|---|---|---|
| `push(key, value)` | O(log s) | 尾部插入 → `siftUp`：与父比较、更小就上浮 |
| `popMin(key, value)` | O(log s) | 取 `front` → **末元素补到根** → `pop_back` → `siftDown`：与左右子中较小者交换下沉 |
| `empty()` / `size()` | O(1) | |

**两个必须答对的边界**：
1. **空堆 `popMin` 返回 `false`，且不修改 `key` / `value`**（调用方传入的引用保持原值）——`Dijkstra.cpp:shortestPath` 里就是 `if (!heap.popMin(currentDist, current)) break;`。
2. 弹出后若堆已空，**不再调 `siftDown`**（`MinHeap.cpp:popMin` 里 `if (!entries_.empty())` 守卫）——避免对空堆做无意义的下沉。

**替代了哪个 STL 设施**：`std::priority_queue`（以及 `std::make_heap` / `push_heap` / `pop_heap`）。
**一句要如实说的话**：`MinHeap.h` 里"为满足课程要求不使用类库、连 `min`/`max`/`swap` 都不引入"的注释属**旧口径残留**——§10.1 已于 2026-09-26 放宽：`std::min` / `std::max` / `std::swap` / 迭代器 / 容器**都允许**。代码里自写的 `swapEntries`（三赋值交换）**不违规、也不是"更手写"**，只是历史写法。老师若问"你现在允许用 `std::swap` 吗"，答"允许，§10.1 修订后不构成算法主体；这里保留自写只是没改"。

**落点**：`MinHeap.h:Entry`、`MinHeap.cpp:push/popMin/siftUp/siftDown/swapEntries`。

## 5. `Dijkstra`：最短路、路径复原与权重口径

**用途**：求任意两点在指定权重维度下的最短路——它是**贪心串联的每一步**的基础设施（§6.3 会给出调用次数）。

**接口与结果**（`Dijkstra.h`）：
```cpp
struct PathResult { bool found; std::vector<std::string> nodes; double totalWeight; };
PathResult shortestPath(const LogisticsGraph&, const std::string& sourceId,
                        const std::string& targetId, WeightType);
```
- `nodes` **含起点与终点**；起点等于终点时返回只含起点的单元素路径、权重 0；
- 端点不存在或目标不可达 ⇒ `found == false` 且 `nodes` 为空（调用方据此报"不可达"并给出原因）。

**路径复原（前驱数组，这是考点）**：
```
dist[n]      ← 源到各点的当前最短距离，初始 kInfinity（1e100）
previous[n]  ← 前驱节点下标，初始 -1
松弛成功时：dist[next] = candidate; previous[next] = current; heap.push(candidate, next)
```
到达目标后**从 target 沿 `previous` 回溯到 source，再整体反转**，得到起点→终点顺序（`Dijkstra.cpp:shortestPath` 末尾）。
**没有**用"每个节点存一整条路径"的写法——那样每次松弛都要复制 O(n) 的路径，时间复杂度会被推高一个量级。**前驱数组 = 只存一步，O(n) 空间，回溯 O(路径长度)。** 这条对比是常问点。

**权重口径**（`WeightType.h`）：
- `enum class WeightType { Distance, Time, Cost }`；
- `WeightType.h:pickWeight(distance, time, cost, type)` 一处实现，被 `Dijkstra` 与 `LogisticsGraph::toAdjacencyMatrixString` **共用**；
- `WeightType` **刻意独立于 `Dijkstra.h`**：`LogisticsGraph` 要按维度输出邻接矩阵，但**图不应依赖算法**。这是模块边界的一个具体动作（§6），也是"消除两处各写一份权重选择"的修法。

**没有 decrease-key —— 到底怎么绕过的（高频追问，答这条）**：
`std::priority_queue` 与本项目的 `MinHeap` 都**没有**"把堆里某个元素的 key 改小并重新堆化"的操作。本项目的做法是**惰性删除**：

1. **每次松弛成功都压入一条新条目**（`heap.push(candidate, next)`），**旧条目留在堆里**；
2. 堆里因此可能出现同一节点的多条 `(key, value)` 条目；
3. 弹出时做一次**过期条目清理**：
```cpp
if (!heap.popMin(currentDist, current)) break;
if (currentDist > dist[current]) continue;   // 这是旧条目，丢掉
```
4. 堆内条目数上限 = **松弛成功次数 ≤ m**（m = 有向边数），所以空间 O(n + m)。

**代价与复杂度**（前提：n = 节点数，m = 有向边数，s ≤ m = 堆内条目数）：
- 时间：每轮 `popMin` O(log s)；每条出边一次松弛尝试，其中 `indexOf` 是 O(n)（见 §2）。故 **O(m·n + m·log m)**。
- 本项目 n=30、m=106：两项都是常数级别；**真正的开销在"每次选下一站都要重跑一次最短路"**（§6.3 的 O(k²) 次调用），不在一次 Dijkstra 内部。
- 空间：`dist` + `previous` 各 O(n)，堆 O(n + m)。

**"这条守卫是性能优化，不是正确性必需"——可当答辩料**：
堆总先弹出更小的 key，所以某节点的**正确条目必定先于其旧条目被处理**，旧条目算出的候选值不可能更小。代码注释记录：**经变异测试验证，去掉这个守卫全部测试结果不变**。因此它是**性能优化**；而"破坏权重选择"会被 5 条断言捕获。

**落点**：`Dijkstra.h:PathResult`、`Dijkstra.cpp:shortestPath`（`kInfinity` = 1e100）。

## 6. 调度（重心）：`RoutePlanner` 的数据结构

这是本课设最该讲透的一块：**用什么结构承载"调度的状态"，这些结构怎样组合，手写的选择与排序落在哪几行，代价多大。**

### 6.1 七种调度数据结构的职责与组合

| 结构 | 承载什么 | 关键字段 |
|---|---|---|
| `RoutePlanner.h:Stop` | **一次配送停靠的时间与载重结算** | `nodeId`、`rawArrivalMin`（未经等待的到达）、`waitMin`、`arrivalMin`（实际送达）、`late`、`penaltyMin`、`remainingLoadKg` |
| `RoutePlanner.h:Trip` | **一趟连续行程**（调度的一次"批次"） | `nodes` / `nodeArrivalMin` / `nodeIsStop`（三个**平行数组**、与 `nodes` 一一对应）、`stops`、`loadKg`（订单货）、`bufferKg`（缓冲货，**不混入 `loadKg`**）、`loadedFromDepot` / `supplyInPlace`（区分"出仓趟 / 在途趟 / 就地满足趟"）、`bankOps`（顺路寄存，至多一条）、`totalDistanceKm` / `totalCostYuan` / `totalTimeMin`、`endNodeId` |
| `RoutePlanner.h:RoutePlan` | **一次规划的完整结果** | `status` / `reason`、`trips`（**真源**，见 6.2）、展平视图 `nodes` / `nodeArrivalMin` / `nodeIsStop` / `nodeTripIndex` / `stops`、汇总 `totalDistanceKm` / `totalTimeMin` / `returnArrivalMin` / `totalCostYuan` / `totalPenaltyMin`、`transitStock` / `transitOps` |
| `RoutePlanner.h:OnboardItem` | **车此刻已经载在车上的货**（`{nodeId, kg}`） | 途中重规划时告诉规划器"车不是空的"——否则规划会假设车还在起点重新装货 |
| `RoutePlanner.h:InsertResult` | **插单结果 + 就地满足的取用明细** | `plan`、`warning`、`carBufferUsedKg`、`stationUsed`、`stationUsedKg`（供调用方把取用**落成物理事实**） |
| `RoutePlanner.h:TransitOp` | **一次站内装卸的记账单元** | `nodeId`、`kgDelta`（>0 入库 / <0 出库）、`atMin` |
| `RoutePlanner.h:TransitStock` | **站内库存快照** | `nodeId`、`initialKg`、`finalKg`（供界面显示与守恒断言） |
| `RoutePlanner.h:PlanStatus` | 规划状态 | `Ok` / `OrderExceedsCapacity`（单张订单货量 > 载重，多趟也无解）/ `Unreachable` |

**组合关系**：
```
RoutePlan
 ├─ trips : vector<Trip>             1 个计划含 1..* 趟
 │    ├─ nodes / nodeArrivalMin / nodeIsStop     三个平行数组，长度相同（不变量）
 │    ├─ stops : vector<Stop>                    仅配送停靠点，按服务顺序
 │    └─ bankOps : vector<TransitOp>             0..1 条（顺路寄存）
 ├─ transitOps : vector<TransitOp>   展平后的全部站内装卸（= 各趟 bankOps + 紧急单出库），按 atMin 有序
 └─ transitStock : vector<TransitStock>  各站期初/期末库存
```

### 6.2 单真源：`trips` 是源，展平视图只在一处生成

`RoutePlan` 同时提供"按趟"和"按节点"两种视图，但**只有一个真源**：
- `trips` 是**真源**；`nodes` / `nodeArrivalMin` / `nodeIsStop` / `nodeTripIndex` / `stops` 以及四个汇总量，全部由 `RoutePlanner.cpp:flatten` **一处**生成。
- **为什么**：如果"按趟"和"按节点"各自维护，任何一次改动（重规划、插单、推进）都可能让两边漂移——本项目历史上真的踩过"趟号塌成 1""车在仓库与客户间反复跳跃"这类**同一事实存在两份副本**的坑（`docs/设计.md` §16 P15/P17/P24）。
- `flatten` 细节：后续趟的首节点与上一趟终点是同一节点，展平时**跳过**（`firstTrip ? 0 : 1`），避免出现"原地一步"；`nodeTripIndex[i]` 告诉界面该节点属于第几趟，**界面不必自己反推趟边界**。
- `flatten` 复杂度：O(总节点数 + 停靠点数)。
- ⚠️ 一个精度细节：`totalTimeMin` 用**未取整的 `elapsed`** 计算（`elapsed - startTimeMin`），不用 `returnArrivalMin`（已取整）反推——否则引入 0.1min 级精度回归。

### 6.3 贪心串联 `weave`：手写的选择逻辑在哪

**规则**（`设计.md` §5.2）：从当前位置出发，每步在所有未服务停靠点中选"**当前位置到它的最短路权重最小**"者，紧急订单未清空时**只在紧急订单里选**，最后回仓库。

**一轮循环做了什么**（`RoutePlanner.cpp:weave`）：
1. 先扫一遍候选集判 `hasUrgent`；
2. 对每个候选调一次 `shortestPath(graph, current, 候选, weight)`；
3. **手写选择**：维护 `bestIndex` / `bestWeight`，线性扫描取最小；**同权重时按 `nodeId` 字典序 tie-break**（保证同一输入必得同一条路线，输出可复现）；
4. `RoutePlanner.cpp:appendLeg` 沿最短路把**全部途经节点**写进 `trip.nodes` 并累加耗时/距离/成本（这也正是 §6.6"顺路寄存零成本"的前提）；
5. 结算 `Stop`（`wait` / `arrival` / `late` / `penalty`），并把该节点的记录时刻**改写为实际送达时刻**（不是 `appendLeg` 记下的未等待时刻）；
6. `pool.erase(begin() + bestIndex)` 移除已服务候选。

**必须讲对的两条口径**：
- **紧急优先内嵌在逐轮选择内部**（`hasUrgent` 时非紧急候选 `continue` 跳过），**不是**对订单事后排序——这是 `设计.md` §5.2 的明文要求；
- **时间推进始终用耗时维度**（`appendLeg` 里累加的是 `edge->timeMin`），**与本次规划所选策略无关**。也就是说选"最短距离"策略时，**选下一站**用距离权重，**算到达时刻**仍用耗时。

**手写的选择与排序（替代 `std::min_element` / `std::sort` / `std::shuffle` 的五处）**：

| # | 位置 | 手写内容 | 替代 |
|---|---|---|---|
| 1 | `RoutePlanner.cpp:weave` | 最小权重选择 + 字典序 tie-break | `std::min_element` |
| 2 | `RoutePlanner.cpp:buildCandidates` | 同点订单**线性扫描合并**成停靠点（需求求和、窗口取并集、任一紧急则该点按紧急） | `std::map` 分组 + 排序 |
| 3 | `RoutePlanner.cpp:eraseCandidateByNode` | 按 nodeId 线性查找移除候选 | `std::find` + `erase` |
| 4 | `RoutePlanner.cpp:sortTransitOpsByTime` | **插入排序**（注释明写"`std::sort` 不可用"） | `std::sort` |
| 5 | `Traffic.cpp:simulateTrafficChange` | **部分 Fisher-Yates**（只洗前 `count` 个位置，不用洗完全量） | `std::shuffle` |

复杂度（前提：k = 停靠点候选数，n = 节点数，m = 边数）：
- 手写选择本身是 O(k)（线性扫描），**但每个候选都跑一次最短路** → 每轮 O(k) 次 Dijkstra；
- 整趟 **O(k²) 次 Dijkstra**：k=25 时约 25+24+…+1 = **325 次**。这是"贪心 + 全量最短路"的真实成本，被问"为什么慢/为什么贵"时用这个数。
- 插入排序 O(t²)（t = 站内装卸条数，实际很小）；部分 Fisher-Yates O(count)（但先复制全部边 O(m)）。

### 6.4 多趟分批 `multiTripPlanImpl`（D20 / D21）

**触发**：`replan` 里 `Σdemand > capacity` ⇒ 走多趟；否则保持单趟直接送达（历史行为与黄金值不变）。
**为什么这样设计**：载重约束的对象是**单趟在车货量**（`0 ≤ 车货量 ≤ capacity`），**不是总需求**。`Σdemand > capacity` 不再判"不可行"，而是**多趟往返**（D21）；只有"单张订单货量 > 载重"或"订单不可达"才是不可行。

**流程**：
1. **紧急单摘出来独立成趟**（E3）：多趟下若只做"簇内紧急优先"，分属两簇的紧急单会被各自簇的行程隔开，不满足"优先满足紧急订单"；故紧急批**独立批次、最先执行、直接从仓库送达**；
2. **簇划分数据驱动**（D17）：配送点按数据里的 `sub_network_id` 归属到该子网络的中转站（需求原文"中转站 A **下属** 3 个社区配送点"是行政归属，不由距离重算）；`sub_network_id == 0` 的归仓库簇；
3. **按载重分批**：`RoutePlanner.cpp:multiTripPlanImpl` 里贪心装箱（`batchLoad + demandKg ≤ capacity` 就装入本批），装满一趟：`weave(..., startPos = 仓库, endNode = 仓库)`；
4. 每站记录 `remainingLoadKg`（本趟发车量逐站递减）；
5. **收尾**：全部送达后若 `current != 起始仓库`，补一趟返仓（`current` 每趟结束都回到 `vehicle.startNodeId`，故本例不产生额外趟）。

**⚠️ 已废弃的说法（讲之前必看）**：`docs/设计.md` §5.6 正文里的"车辆不必每趟回仓库""枢纽 = 中转站""`stock[t]` 取货分支"描述的是**已移除**的"中转站集散/暂存"机制（§16 P25/P30 移除，该节正文有"注（2026-09-26）"覆盖）。**现口径：每趟终点均为起始仓库，中转站不参与常规排线。**

**默认数据为什么正好 6 趟（可复核的推导）**：三簇需求 262 / 220 / 258 kg，各自都略超 200 kg 载重 ⇒ 每簇 2 趟 ⇒ **6 趟**。（总需求 740 kg，若允许跨簇混装理论下界是 ⌈740/200⌉ = 4 趟；实测 6 趟是因为**按簇分批**、簇间不混装。）

**`multiTripPlan` 现在只剩单次调用**：历史上这里做过"直达 vs 经中转站"两版取优；第 13 轮实测证明经站路线全面更差（距离 178.2→198.2 km、趟数 6→13），中转站因此退出排线，两版变成参数完全相同的两次调用，故收敛为一次（注释里留了"将来要重新引入备用方案取优"的指引）。

### 6.5 动态调度：紧急插单与增量式重规划

**紧急插单（E3）`RoutePlanner.cpp:insertUrgentOrder`**：
1. **强制 `urgent = true`**（调用方传什么都不作数），并入 `remainingOrders`；
2. 冲突判定：按**耗时维度**算"从当前位置出发的最早到达时刻"，若晚于新单窗口止 ⇒ 写 `warning`；但按 D13 **订单仍纳入规划**（超时不弃单）；
3. **两版取优**：
   - **候选 A（现状）**：独立紧急趟**先回仓库装货**再送；
   - **候选 B（就地满足）**：用「**车上缓冲** + 该紧急点**所属站的库存**」当取货点。可用性先判：车上够（`avail ≥ d`）用车上；否则该站库存补足才可用；都不行就直接退回 A（连参与取优的资格都没有）。**只换取货点**——紧急批仍独立成趟且排在所有普通停靠点之前（E3 优先性不被取优牺牲）；
   - **取优判据**：`penalty` 更差 ⇒ **一票否决，选 A**。所以"绝不更差"是**构造保证**，不是"顺路所以零成本"的推理。
4. ⚠️ 一个易错点：`d` 取的是**停靠点合并后的需求**，不是"这一张订单的需求"。同一配送点若还有普通订单，它们会被 `buildCandidates` 合并成同一停靠点；按单张订单的 kg 去凑会出现"车送它没装的货"（§16 P25/P26 那类缺陷）。

**代价**：一次插单会**重跑两次完整规划**（A 与 B 各一次），即 §6.3 那 O(k²) 次 Dijkstra 的两倍量级——这正是"增量式重规划"被需要的原因。

**增量式重规划（D22）`RoutePlanner.cpp:replanIncremental`**：
- **切段**：把当前路线按**停靠点**切成 leg（起点→第 1 站、第 1 站→第 2 站、…、末站→仓库）；`RoutePlanner.cpp:sliceRemainder` 负责从已规划 plan 切出"尚未走完的部分"，并且**保留趟结构**——若把剩余路线压成一趟，重规划后界面上的「第 N 趟」会全变成「第 1 趟」（这是本项目真实修过的坑，§16 P22）。
- **受影响判定**：某 leg 受影响 ⟺ 它走过的边里有一条被路况标为"耗时增幅 ≥ 阈值"（复用 `RoutePlanner.cpp:isEdgeOnRoute`）。
- **就地改了什么**：**只对受影响的 leg 重新求最短路**，其余 leg **原样复用**，**停靠顺序不变**（只调整路径段，不重排服务顺序）。逐趟增量（`replanOneTrip`），趟与趟之间互不影响。
- **失败回退**：任一趟增量失败（序列不全 / 受影响 leg 不可达）⇒ **整体退回全量重算**（`multiTripPlan`）。是否真走了增量由 `usedIncremental` 指针**回报**——调用方**不许从趟数猜**（早期实现按"剩余路线是否单趟"猜，多趟时把走成增量的情况误报成"退回全量"）。
- **必须把 `initialStock` 带走**：否则路况重规划后站内库存凭空归零（头文件注释点名）。
- **强断言口径**（`设计.md` §5.7）：① 全部停靠点仍被服务且**顺序逐位相同**；② **未受影响的 leg 逐位不变**（这才是"增量"的定义）；③ 总耗时 ≤ 重规划前；④ **没有任何 leg 受影响时结果与原路线逐位相同**（幂等）；⑤ 每段仍可达、仍回仓库。
- **一个"反面"常问点**：为什么不与全量重算比对相等？因为全量重算会**重新做贪心选点、停靠顺序可能变化**，两者本就**不必相等**；把"与全量一致"写成断言会把正确的增量结果判为失败。全量只在增量不可用时兜底。

### 6.6 中转站缓冲库存（D23）：正文只留一句结论

> **一句话结论**：仓库每次**出仓装满**，本趟订单用不到的那部分成为**不属于任何订单的缓冲货**（`Trip::bufferKg`，不混入 `loadKg`）；返程**顺路**经过本簇中转站时**纯记账**寄存进站（不新增节点/时刻/里程）；**紧急单**先用车上缓冲、不足再取该紧急点所属站的库存**就地满足**，并与"独立紧急趟回仓库"**两版取优、penalty 更差一票否决**。**中转站只服务紧急单，常规趟绝不进站。**

完整四条规则、代价与守恒口径见 **附录 C**（讲解主线不展开）。

**落点汇总**：`RoutePlanner.h:Stop/Trip/RoutePlan/OnboardItem/InsertResult/TransitOp/TransitStock/PlanStatus`、`RoutePlanner.cpp:buildCandidates/weave/appendLeg/multiTripPlanImpl/flatten/replan/replanIncremental/sliceRemainder/replanOneTrip/insertUrgentOrder/isEdgeOnRoute/nodeIndexAtTime`。
其中 `RoutePlanner.cpp:nodeIndexAtTime` 的语义是"**半路显示所在段的起点**"：车在 `i → i+1` 途中时返回 `i`；它**只用于显示与断言比对**，界面推进**不许**用它跳过沿途节点。

## 7. `SimEvent` + `Rng`：软件内时间的事件调度

**用途**：把"什么时候该发生什么"从真实时间与按钮节奏里**剥离**出来，只由**软件内时间**决定。

**时间基准**：一律「相对当日 00:00 的**分钟数**」（整数）。`08:00 = 480`；`depart_time 08:00`、`service_time_min` 默认 5。

**核心设施一：下一个事件刻 `SimEvent.cpp:nextEventTimeMin(nowMin, intervalMin)`**
- 语义：**严格大于** `nowMin` 的最小的 `intervalMin` 整数倍——**绝对时刻对齐**，不是"从上一次事件起算"的相对值。这正是它作为可断言语义的价值：
  - `nextEventTimeMin(495, 15) == 510`（**正好在刻上，必须前进一格**）
  - `nextEventTimeMin(496, 15) == 510`（不在刻上，取下一个刻）
  - `nextEventTimeMin(1439, 15) == 1440`（可跨日）
- 边界：`intervalMin <= 0` ⇒ 返回 `nowMin + 1`（防御：**不得死循环、不得返回自身**）；负数时刻也正确（显式修正 C++ 整除向零截断的偏差）。
- 复杂度 O(1)。

**核心设施二：加权抽签 `SimEvent.cpp:pickEvent(weights, rng)`**
- 四类事件（`SimEvent.h:SimEventKind`）：`Traffic` 路况 / `UrgentOrder` 紧急订单 / `NewCustomer` 新客户 / `RoadClosure` 道路封闭；
- 权重（`SimEvent.h:EventWeights`）：**10 : 3 : 1 : 1**（合计 15），可从配置读（`Config.h:GeneralConfig` 的 `eventWeightTraffic/Urgent/Customer/Closure`）；
- 实现契约（都必须讲对）：
  1. **一次 O(4) 的累积前缀扫描**（事件种类固定 4 个，故是常数级）：掷一次骰子落在 `[1, total]`，顺前缀和找区间；没有"先算总和再赌一次再校验"的回旋；
  2. **权重 ≤ 0 的种类永不被抽中**（跳过，不撑大区间）；
  3. **全部权重 ≤ 0 时保底返回 `Traffic`**：不得除零、不得死循环——**并且仍然消耗一次随机数**。原因见下条；
  4. **契约「一次抽签 = 一次 rng 消耗」**：否则两条本该看到同一串事件的路径（按站模拟 / 推进一刻）会因保底分支**错位**；
  5. `total` 用 `long long` 累加，避免极端权重下 `int` 溢出。

**纪律：事件结算挂在"软件时间前进"上**（`MainWindow.cpp:settleEventsUpTo`）：`onAdvanceStop` 与 `onAdvanceMoment` 移动位置后**都必须**补结算跨过的事件刻。因此"一次推进一刻"与"逐个推进到同一时刻"看到**同一串事件**（§16 P34 的等价性断言的前提），事件密度与推进粒度解耦。每过一个事件刻**恰抽 1 个**事件（`event_interval_min` 默认 **15min**）。

**`Rng`（`Random.h:Rng`）**：手写 **xorshift32**，`nextU32` / `nextUnit` / `nextInt` / `nextRange`。
- **不用 `<random>` 的理由是"可复现"，不是"标准库被禁"**：固定种子必得完全相同的序列，因此"随机"逻辑可以被**逐值断言**而不 flaky；`simulateTrafficChange` / `pickEvent` 都接收种子或 `Rng&`。
- 这条口径要主动说，否则容易被误答成"老师不让用标准库"。

**主动交代的偏差**：需求原文【实现提示 2】写"每 **30 秒**修改 **10%** 路径"。D24 主动放弃了"30 秒"这个字面点——改由**软件内 15min 事件刻**承担；"改 10%"保留为 `traffic_change_ratio = 0.1`。旧的两套触发（真实秒级 `traffic_change_interval_sec`、以及"每推进一次就触发路况"）都已**从配置与代码中移除**（`Config.h` 里只剩一条说明它们"已被取代并移除"的注释；`grep` 可复核）。要求原文与 `docs/课设要求整理.md` 不动，偏差只记在 `设计.md` D24 与 `docs/功能实现清单.md` H3。

**落点**：`SimEvent.h:SimEventKind/EventWeights`、`SimEvent.cpp:pickEvent/nextEventTimeMin/simEventName`、`Random.h:Rng`。

## 8. `Traffic`：路况变化与重规划触发

**用途**：按比例改动边耗时，并判断"要不要重规划"。

**`Traffic.cpp:simulateTrafficChange(graph, ratio, minRatio, maxRatio, seed, clearProbability)`**
1. 改动条数 = `round(ratio × E)`，`ratio > 0` 时**至少 1 条**，且不超过 E。本项目 E=106、`ratio=0.1` ⇒ **11 条**。
2. **选边用部分 Fisher-Yates（手写）**：先把全部边复制成 `pool`（O(m)），只对**前 `count` 个位置**做交换洗牌，`j` 从 `[i, total-1]` 随机取——**只洗需要的部分，不洗全量**。O(count)（外加复制 O(m)）。
3. 每条边：掷一次决定**畅通**还是**拥堵**（`clearProbability` 默认 0.5——需求把路况定义为"拥堵 / 畅通"两种动态属性，**两个方向都必须能出现**）：
   - 畅通：`timeMin` 恢复到 `baseTimeMin`，`congested = false`，`increaseRatio = 0`；
   - 拥堵：`timeMin = baseTimeMin × (1 + [minRatio, maxRatio] 内随机值)`，`congested = true`。
   - **不叠加**：每次都相对 `baseTimeMin` 重设。所以 `TrafficChange.increaseRatio` 就是"本次施加的增幅"，**不是累计增幅**（字段曾叫 `cumulativeIncreaseRatio`，因名不副实已更名，避免耗时逐次失控）。
4. `baseTimeMin` **始终不变**——它是"是否增加 ≥ 20%"的判定基准。
5. 写回图用 `LogisticsGraph::updateEdgeTime`（O(n+deg)）。

复杂度：O(m + count · (n + deg))；n=30、m=106、count=11 时是常数级。

**`Traffic.cpp:needsReplan(routeNodes, report, thresholdRatio)`**
- 触发条件：某条被改动的边**恰好是路线中相邻的一对**（`RoutePlanner.cpp:isEdgeOnRoute`，**有向，方向必须一致**）**且** `increaseRatio ≥ thresholdRatio`（需求口径：耗时增加 ≥ 20%）。
- 复杂度 O(|changes| × |routeNodes|)。
- 畅通（增幅 0）**不触发**重规划；只有"当前路径上的边"才触发（不在路上的拥堵不影响已定路线）。
- 触发后走 `replanIncremental`（增量），失败才退回全量（§6.5）。

**落点**：`Traffic.h:TrafficChange/TrafficReport`、`Traffic.cpp:simulateTrafficChange/needsReplan`。

## 10. 被追问时怎么答（8 条）

**1. 为什么用邻接表不用邻接矩阵？顺便说 `indexOf`。**
n=30、m=106 是稀疏图（无向道路对 56）：矩阵 900 格绝大多数为空，且每格要放 3 个权重。邻接表存储 O(n+m)、遍历某点出边 O(deg)（矩阵必须扫整行 O(n)）、删节点不必搬整行整列。另外如实说：`LogisticsGraph.cpp:indexOf` 是 **O(n) 线性扫描，没有映射表**——用"每次查找 O(n)"换掉"删点后映射要重建/失效"的一致性风险；n=30 时 O(m·n) 是常数级。要提速就加 `std::map`/哈希（容器不受限），算法不改。

**2. `std::priority_queue` 不让用，那 decrease-key 怎么办？**
不用 decrease-key，用**惰性删除**：松弛成功就 `heap.push` 新条目，旧条目留在堆里；弹出时 `if (currentDist > dist[current]) continue;` 丢掉失效条目。堆条目上限 = 松弛成功次数 ≤ m，空间 O(n+m)，总时间 O(m·n + m·log m)（n 节点、m 边）。补一句可作加分：**这个守卫是性能优化而非正确性必需**——堆总先弹出更小的 key，正确条目必先于旧条目被处理；变异测试验证去掉它结果不变。

**3. 为什么不能用 `std::priority_queue` / `std::sort` / `std::lower_bound`？边界在哪？**
判据是"**手写算法，不手写轮子**"（D4，§10.1）：排序、堆、二分、最短路松弛、贪心选择、**图遍历的判定逻辑**必须自己写；**容器与辅助设施不受限**——`std::vector`/`std::map`/`std::string`、`std::min`/`std::max`/`std::swap`/迭代器、以及 io/tests/gui/日志全部随意。可现场佐证：在 `src/core/` 与 `src/io/` 里 grep 禁用清单（`std::sort`、`std::priority_queue`、`std::lower_bound`、`std::min_element`、`std::*_heap` 等），**唯一命中是 `RoutePlanner.cpp` 里解释"为什么手写插入排序"的注释**。

**4. 为什么是贪心而不是最优解？代价多少？**
D3 明确**不实现全局 TSP**：用"逐点最短路累加 + 贪心串联"，是课程给定口径（需求原文亦指定 Dijkstra + 邻接表）。代价要主动报：每轮对每个候选跑一次最短路 ⇒ 每轮 O(k) 次 Dijkstra，整趟 **O(k²) 次**；k=25 时约 **325 次**。因此"单次 Dijkstra 内部很省"（n=30）但"**反复调用**"才是主要开销——这也是为什么插单与重规划必须做增量、而不是无脑全量重算。

**5. 超时和 penalty 谁算的？什么口径？**
唯一一套时间推进函数（`RoutePlanner.cpp:appendLeg` 累加耗时 + `weave` 结算 `Stop`）：`rawArrival = 上一站 departure + travel_time`；`wait = max(0, windowStart − rawArrival)`；`arrival = rawArrival + wait`；`isLate = arrival > windowEnd`；`penalty = arrival − windowEnd`（**分钟**）。**早到等待计入总耗时、不计 penalty**；`arrival == windowEnd` **不算超时**。规划、重规划、插单**共用同一套函数**（D13），不存在"规划只标记、执行才计分"两套规则。默认数据下三策略**都只有 D05 一个超时点**（distance penalty 166 / cost 207 / time 201）。

**6. 怎么证明你的"增量重规划"真的是增量？**
用逐位等值断言，而不是"感觉更省"：① 停靠点顺序与重规划前**逐位相同**；② **未受影响的 leg 逐位不变**；③ 总耗时 ≤ 重规划前；④ **没有任何 leg 受影响时结果逐位相同**（幂等）；⑤ 每段仍可达、仍回仓库。此外 `usedIncremental` 由函数**回报**，调用方**不许从趟数猜**。并说明：**不与全量重算比"相等"**——全量会重新贪心选点、顺序可能变，两者不必相等，那样断言是错的。

**7. 如果节点/订单规模变大，哪里先坏？（必须留）**
按"先坏顺序"答（前提：n 节点、m 边、k 订单/停靠点）：
① **`indexOf` 的 O(n) 进了 Dijkstra 内层** ⇒ O(m·n)，第一个该换（加映射表，容器不受限）；
② **`weave` 的 O(k²) 次最短路** ⇒ k 增大是平方级，应改成"一次 Dijkstra 求全源距离矩阵并复用"，或把候选集压缩；
③ **`removeNode` 扫全部邻接表** O(n+m)（有向图入边分散的必然代价），大规模应补入边索引；
④ **`buildCandidates` 的 O(k²) 线性合并**（同点订单两两比对）；
⑤ **`IniSection::findValue` / `findSection` 线性扫描**（节/键很多时）；
⑥ **`reachesSkipping` 的 `seen` 线性查重**（BFS 退化）。
再补一句：这些都是"**结构选型换来的简单**"，n=30 时不值得优化，但**知道它们在哪**本身就是这门课的考点。

**8. 验收现场改需求，你往哪儿改？（必须留）**
- **换/加规划目标**：`WeightType` 加枚举 + `pickWeight` 一处分派；`RoutePlanner` 的策略参数已是枚举，不用动算法。
- **改车辆数 / 多车**：接口已按集合设计（`Vehicle` 以 `vector` 传、`planRoute`/`replan` 参数是"集合 + 配置"），预留点在 `设计.md` §11；单车的 `trips` 结构可直接扩成"每车一组 trips"。
- **加一类模拟事件**：`SimEventKind` 加一项 + `EventWeights` 加权重 + `Config.h:GeneralConfig` 加字段 + `pickEvent` 的 4 元数组改成按种类数循环；结算处加一个 `case`。
- **改图/加节点类型**：`Node.h:NodeType` 与 `LogisticsGraph` 邻接表无关（节点表 + 出边表结构不依赖类型）。
- **兜底说明**：`src/core/` 与 `src/io/` 能用 `g++` 独立编译，"改完即跑 829 项检查 + 三行黄金值"就是改动是否破坏行为的判据（行为改动后必须跑 `ctest` 并对比黄金值）。

## 附录 B：三策略为什么不同（一句话 + 证据）

同一份 `shortestPath`，只在 `pickWeight` 处换维度（距离 / 耗时 / 成本），所以"三策略"没有三套算法。
**为什么距离最优 ≠ 成本最优**：数据生成时 `cost` 按**道路等级**差异化（主干道快而贵、支线慢而便宜），**不是** `cost = dist × 常数`。后者曾使"最低成本"恒等价于"最短距离"、B7 双策略名存实亡——这是集成测试抓出的**真实数据缺陷**，修法与证据见 `docs/设计.md` §15。
可现场对照：distance `178.200 km / 244.200 元` vs cost `186.300 km / 235.900 元`——**距离策略更短但更贵**，正是分化的直接证据。

## 附录 C：D23 中转站缓冲库存——四条规则、代价与守恒

> 正文（§6.6）只留一句结论，细节收在这里。答辩时按需展开，别让它挤占主线。

**规格与留档**：`docs/留档/实现规格/transit-urgent-buffer.md`（实现规格）、`docs/留档/决策/transit-stock-full-load.md`（四轮商议与实测）、`docs/留档/决策/probes/`（可复现探针）。

**四条规则**

1. **满载出仓（生产者）**：`RoutePlanner.cpp:fillBufferFromDepot` —— 每次"在仓库装货出发"的趟，把本趟订单货量之外的空位全部装成**缓冲货**：`Trip::bufferKg = capacity − batchLoad`，并置 `loadedFromDepot = true`。
   **口径不变量**：`loadKg + bufferKg ≤ capacity`，`bufferKg ≥ 0`；**缓冲货绝不混入 `loadKg`**（界面「本趟装载」与装载一致性守卫只读 `loadKg`）。
   只在"出仓趟"调用——**在途货趟与收尾趟不得凭空计缓冲**。
2. **顺路寄存（入库，纯记账）**：`RoutePlanner.cpp:bankBufferEnRoute` —— 若本趟停靠点同属**唯一**一个簇站（`tripHub`），且返程**真的**经过该站，就把 `bufferKg` 记一条 `TransitOp`（`kgDelta = +bufferKg`，`atMin` 取该站在序列里的真实到达时刻）。
   **双条件缺一不可**：① 该站必须真的出现在"最后一个停靠点之后"的回程段**实际序列**里；② 顺路等式再交叉核对 `d(最后停靠点→站) + d(站→仓库) ≤ d(最后停靠点→仓库)`。只信距离等式不够——并列最短路时等式可能成立而车并没走那条路，那就会"把货卸在车没去过的站"。
   **为什么零成本**：`appendLeg` 会把最短路上的**全部途经节点**写进 `trip.nodes`，所以"顺路"意味着该站**本来就在序列里**——寄存**不新增节点、不改时刻、不改里程/成本**（本项目停靠无服务时间）。
   **至多一条**：一趟只寄存一次（`Trip::bankOps` 最多 1 条）。
3. **紧急单就地满足（出库）**：`RoutePlanner.cpp:insertUrgentOrder` 的候选 B —— **只换取货点**：车上缓冲够（`avail ≥ d`）⇒ 取货点 = 车上（不新增节点）；否则取该紧急点**所属簇站**的库存补足（`avail + stock[hub] ≥ d`）⇒ 取货点 = 该站；都不行 ⇒ 候选 B 不可用，直接退回 A。
   - `d` = **该停靠点合并后的需求**（不是单张订单的 kg）；
   - 出库用 `RoutePlanner.cpp:recordStationDraw` 记账：扣期末库存 + 写一条**负的** `TransitOp`；`atMin` 必须从计划自己的节点序列里**实读**"车真的到过该站的时刻"，读不到**就不记账**（宁可不记，也不记一条追溯不到的出库）；
   - **不借货**：绝不动本趟要送的订单货（只动缓冲）。
4. **两版取优 + penalty 一票否决**：候选 A（独立紧急趟**先回仓库装货**）vs 候选 B（就地满足）。**若 B 的 penalty 更差则一票否决，选 A**。因此"绝不更差"是**构造保证**，不是推理。
   同时**必须满足**：紧急批仍**独立成趟且排在所有普通停靠点之前**（E3 优先性不得被取优牺牲）；用了候选 B 的趟标 `supplyInPlace = true`、`bufferKg = 0`（它没在仓库装货，"出仓却未满载"是个误报陷阱，两种标记就是为把三类趟区分开）。

**已知并接受的建模代价**（要如实说，不要掩饰）
- 未消耗的缓冲 = **仓库多发出的货**；
- 守恒口径：`Σ发出缓冲 − Σ紧急单消耗 = 期末站内 + 期末车上缓冲`；
- 中转站**只服务紧急单**，常规趟**绝不进站**（守卫 G1）。历史实测：常规排线经站全面更差（距离 178.2→198.2 km、趟数 6→13、penalty 256→323），因此"不进站"是被**数据**钉住的结论，不是省事。

**为什么这套机制绕却值得留**：它把"满载出仓必然产生多余货"这个**物理事实**变成了可用的**库存供给**，代价只是记账；而"绝不变差"由取优的构造保证兜住。**讲解时一句话带过，细节留给追问。**
