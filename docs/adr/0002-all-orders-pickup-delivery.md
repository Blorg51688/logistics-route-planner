# 全订单改为客户间取送，仓库降为基地，单条连续路线 + 停靠合并 + 硬优先

**Status**: accepted（2026-11-23）

**Supersedes**: [ADR 0001](0001-urgent-pickup-delivery.md) 的适用范围——0001 只把**紧急订单**改为客户间取送；本决定把**全部订单**统一为取送，并退役多趟机制。0001 的中转站「降载暂存」语义继续有效，扩展为「只存车辆实际卸下的货」的一般语义。

## 背景与决定

规格一（wayfinder map #16）已拍板骨架：所有订单 A→B、车辆初始空、仓库/中转站非货源。本票（#21）在其上定稿四个分叉（本人 2026-11-23 拍板）：

1. **Q1 合并停靠**：同一节点既是某单取货点又是另一单送达点时，合并为**一次停靠**（取货动作集 + 送达动作集，先卸后装）；窗口与 penalty 只由送达单决定。
2. **Q2 硬优先**：路线中全部紧急停靠排在全部普通停靠之前；紧急队列严格 FIFO；普通动作唯一例外是顺路交货。
3. **Q3 停靠零耗时**：停靠不消耗时间（无服务时间）；耗时只来自行驶与早到等待。
4. **Q4 紧急阶段不顺路取货**：紧急阶段只做紧急动作 + 已在车普通货的顺路交货；普通取货留到普通阶段。

## 为什么（非显而易见的取舍）

- **为什么全订单取送**：第一性原理——货全部来自客户 A、车初始空，则「仓库供货 / 多趟补货」**没有对象**，是被模型淘汰而非裁剪；载重约束随之从「每趟装载量」变为「路线前缀在车量」。
- **为什么硬优先（Q2 选 B）**：备选的软优先（字典序目标）不牺牲地理可行性，但要引入字典序目标函数与对应验收口径；本人取**实现更简单**——优先级直接体现在停靠顺序上，验收一眼可查。代价如实承认：紧急 B 窗口很远时可能绕路、普通 penalty 可能变差。
- **为什么停靠零耗时（Q3）**：按停靠/按方向/按动作三种计时都会让汇总值随合并情况浮动、口径更难解释；零耗时把耗时归约为「行驶 + 等待」两项，最简、最好核。`service_time_min` 不再参与任何计算（配置键去留归数据契约票 #23、迁移项归迁移清单票 #20）。
- **为什么紧急阶段不顺路取（Q4）**：顺路取会让普通货占载重，后续紧急取货可能装不下而触发降载绕行，拖慢紧急件——与硬优先自相矛盾；ADR 0001 原文「仅限此刻已在车上」本就只允许交付。

## 关键约束（实现与评审要守住）

- 一次停靠 = 一次节点访问，停靠内先卸后装；同阶段同节点只停一次；跨阶段（紧急 / 普通）允许重访同一节点（Q4=A 的代价，已接受）。
- 停靠零耗时：推进递归 `departure = arrival`；**早到等待保留**（计入总耗时，不计 penalty）。
- 硬优先断言：路线上不存在「普通停靠先于紧急停靠」；紧急队列严格 FIFO。
- 顺路交货仅交付：紧急停靠点不发生普通取货动作。
- 全部旧黄金值作废重算（map #16 Notes 既定）。

## 备选（已否决）

- **Q1=B 分两次停靠**：同节点访问两次、重复计时，破坏合并不变量；否决。
- **Q1=C 数据禁止 A/B 同节点**：限制事件刷单的选择空间；否决。
- **Q2=A 软优先（字典序目标）**：实现与验收更重；否决（本人取舍：实现简单）。
- **Q2=C 只改插单时机**：优先级无法在验收中体现；否决。
- **Q3=A/B/C 三种计时**：口径复杂、汇总值随合并浮动；否决（含本人新案以外的全部计时方案）。
- **Q4=B/C 紧急阶段顺路取普通货**：占载重拖慢紧急件；否决。
