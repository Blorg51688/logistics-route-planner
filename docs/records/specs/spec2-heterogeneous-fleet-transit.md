### 2.3 五条跨票不变的骨架（写代码时最先要守住的）

1. **每车一条连续路线**：从自己的 `start_node` 按自己的 `depart_time` 空载出发、服务分配到的订单、回**同一**基地；不恢复「趟 / 多次回基地」（#19 不变量 3）。
2. **一单一车（转运例外）**：A、B 在同一台车的同一条路线上，A 的停靠索引 < B 的停靠索引；转运版由时刻链把两台车连起来（#19 不变量 4 + #28 §9.3）。
3. **决策键恒为字典序**：`(Σpenalty, 当前策略权重合计, 均衡键, tieKey)`——penalty 一票否决＝第一键；**所有比较都用各车缩放后的边权重放**（#18 Q2=A + #19 §2）。
4. **载重是前缀量**：任一时刻 0 ≤ 在车量 ≤ 该车 capacity；停靠内先卸后装；**禁止**用「该车分到的订单总重 ≤ 容量」判可行性（#21 + #30 表 4）。
5. **确定性**：同输入（车队配置 + 策略 + 事件序列 + 种子）必得同一分配、同一路线、同一事件串；并列按 `tieKey`（车辆 ID 升序 → 节点 ID 升序 → 订单 ID 升序）（#19 不变量 9 / #30 §3-5）。

## 3. 车队模型（#19）

> **来源**：[#19](https://github.com/Blorg51688/logistics-route-planner/issues/19) resolution §1–§11｜**权威落盘**：[ADR 0003](../../adr/0003-heterogeneous-fleet.md) + [GLOSSARY.md](../../../GLOSSARY.md)「车辆」节

### 3.1 `[vehicles]` 六列（顺序固定）

```ini
# ID, start_node, capacity_kg, depart_time, time_factor, cost_factor
V01, W01, 400, 08:00, 1.00, 1.50
V02, W01, 160, 08:00, 1.25, 0.80
V03, W01, 160, 08:00, 1.25, 0.80
```

**八条校验**（一律 `第 N 行 [vehicles]: <具体原因>`，首个错误即返回）：

| # | 规则 | 报错文案 |
| --- | --- | --- |
| 1 | 字段数必须 **6**；旧 4 列/多列均报错 | `需要 6 个字段，实际 K 个: <原文>` |
| 2 | 节缺失＝错误；**空节＝错误**（车队不能为空，与 `[orders]` 允许空节不同） | `缺少 [vehicles] 节` / `[vehicles] 节为空：至少需要 1 台车` |
| 3 | `ID` 非空且**全局唯一**（现实现两者都不查） | `车辆 ID 为空` / `车辆 ID 重复: <ID>` |
| 4 | `start_node` 存在且 `type = warehouse` | `起始节点不存在: <ID>` / `起始节点必须是仓库: <ID>` |
| 5 | `capacity_kg` 有限正实数 | `载重上限不是合法数值` / `载重上限必须为正数` |
| 6 | `depart_time` 为 `HH:MM` | `发车时刻格式应为 HH:MM` |
| 7 | `time_factor` / `cost_factor` 为**有限正实数**（不设上下限） | `耗时倍率不是合法数值` / `耗时倍率必须为正数`（成本同理） |
| 8 | 空字段不静默跳过，逐字段给具体消息 | 见上列 |

**生成器自检另加**（比解析层严，只约束**默认数据集**，不是契约）：因子 ∈ `[0.5, 2]`；至少 1 台 `time_factor = 1` 且 `cost_factor = 1` 的基准车；至少一台 `capacity_kg ≥ 2 × min(capacity_kg)`；存在 `time_factor > 1` 与 `cost_factor < 1` 的车（保证两型车真的分化）。

### 3.2 默认车队（数据集事实）

| 车辆 | 类型 | 容量 | 发车 | time_factor | cost_factor |
| --- | --- | --- | --- | --- | --- |
| V01 | 快车 | 400kg | 08:00 | 1.00 | 1.50 |
| V02 | 慢车 | 160kg | 08:00 | 1.25 | 0.80 |
| V03 | 慢车 | 160kg | 08:00 | 1.25 | 0.80 |

- 全部从 **W01** 发车、**同刻**发车（不引入错峰：那会多一个影响 penalty 的变量）；W02 仍是普通节点（跨仓库调度在 Out of scope）。
- 初始 25 单**不变**（同 #23 权威表）；`demand_kg < min(capacity_kg)` 的跨节校验随车队变成 `< 160kg`，初始最大单笔 24kg 仍满足，**订单数据一个字不改**。
- **列名口径**：票面写 `speed_factor`，定稿为 `time_factor`（> 1 = 更慢）。配置键、代码、文档、报告统一用 `time_factor`；票面字样只作历史引用（#19 §10）。

### 3.3 因子与拥堵的先后（定稿口径）

```text
timeEff(edge, v)  = edge.timeMin  × v.timeFactor     // timeMin 是当前（拥堵后）耗时
costEff(edge, v)  = edge.costYuan × v.costFactor
distEff(edge)     = edge.distanceKm                  // 与车型无关

rawArrival(next)  = departure(prev) + Σ timeEff(leg 的每条边, v)
wait              = max(0, max{ws_i} − rawArrival)   // 等待不乘因子
arrival           = rawArrival + wait
penalty_i         = max(0, arrival − we_i)           // penalty 不乘因子
departure         = arrival                          // 停靠零耗时（规格一已定）
```

- 拥堵只改 `edge.timeMin`（`baseTimeMin` 保留）⇒ 因子在取用处乘一次，拥堵更新后自动生效，**无派生状态、无缓存层**。
- 「耗时增加 ≥ 20%」的拥堵判定仍在**基础图**上做，与车型无关。
- **图表示不缩放**：邻接矩阵 / 邻接表 / 画布权重标签继续显示**基础边权**；因子只出现在规划指标与车辆面板。

### 3.4 每车五项 + 车队汇总

| 指标 | 定义 |
| --- | --- |
| 距离 | Σ 该车路线各边 `distanceKm`（与车型无关） |
| 耗时 | 该车返回基地时刻 − 该车发车时刻（含行驶与早到等待，停靠零耗时） |
| 成本 | Σ 该车路线各边 `costYuan × cost_factor` |
| penalty | 该车各送达单 penalty 之和（逐单窗口） |
| 停靠数 | 该车路线上的停靠点个数（取送动作合并后计一次，与 #29「停靠点数」同口径） |

**车队汇总**：距离 / 成本 / penalty / 停靠数各自**求和**；**总耗时（主口径）＝完工耗时** = `max(各车返回时刻) − min(各车发车时刻)`；**车时合计（参考口径）＝Σ 每车耗时**，并列显示但**不替代**完工耗时。空闲车（0 停靠）五项全 0、返回时刻 = 发车时刻、**不抬升**完工耗时，但参与 `min(发车时刻)`。

**为什么完工耗时作主口径**：与单车耗时可比（同量纲、同演示口径），`docs/设计.md` §14.3 的「总耗时 ≤ 12 小时工作日」可原样沿用；Σ 车时约 3 倍，容易被读成「更慢了」。

### 3.5 GUI 车辆面板（容器口径）

- 「车辆信息」dock 内**每台车一个页签**，页签数 = `[vehicles]` 行数；标题 = `<车辆 ID> · <容量>kg`（如 `V01 · 400kg`）。
- 每页**两块**（纯文本小标题，不新增控件类型）：**固定信息**（ID / 起始仓库 / 载重上限 / 发车时刻 / 耗时倍率 / 成本倍率，共 6 行）；**运行状态**（字段清单归 #25/#27，见 §7.5）。
- **`--ui-probe` 断言改造**：页签数 == `vehicles.size()`；每页含两块标题；逐车能读到 ID / 容量 / 两因子且与配置一致；「车上载重 ≤ 该车容量」改**逐车**判定。断言仍读用户可见文本（`vehiclePanelSummary`），不重算公式。

### 3.6 九条不变量（验收直接断言）

1. `[vehicles]` 每行 6 列、字段顺序固定；旧 4 列显式失败。
2. 车辆 ID 非空唯一；起始节点存在且为仓库；容量 > 0；两因子为有限正实数。
3. 每车**一条连续路线**：自己的 `start_node` / `depart_time` 空载出发，回**同一**基地；不恢复趟。
4. 每张订单**恰好由一台车全程完成**（默认；跨车转运归 #28，见 §2.2 的精确化）。
5. 每车任一时刻 0 ≤ 在车量 ≤ **该车** capacity（前缀载荷，停靠内先卸后装）。
6. 时间推进用该车缩放后的耗时；等待与 penalty **不乘**因子；停靠零耗时；`arrival == we` 不算迟到。
7. 距离与车型无关；图表示显示基础边权。
8. 指标可加：Σ每车距离/成本/penalty/停靠数 == 车队汇总对应项；**完工耗时 ≠ 车时合计**，二者不得互相顶替。
9. 输出确定性：同输入必得同一分配与同一路线；并列按稳定 tieKey（车辆 ID 升序、节点 ID 升序）。

### 3.7 复杂度

- 多车「逐单跨车插入」的朴素代价 **O(m·k·n³)**（k = 车数，默认 3）；目标规模 m ≤ 50 单 / n ≤ 100 停靠点 / k = 3 时约 1.5×10⁸ 重放步，与规格一已接受的单车 2×10⁸ 同量级。
- 因子本身**不增加复杂度**：每边乘一次 O(1)；**不建每车一张 V² 最短路矩阵**（内存 ×k，且与「杜绝过于复杂的机制」相悖）。

### 3.8 「慢车 160kg 零余量」＝例外而非常态（含回退预案）

**为什么默认三策略下不是常态**：① 三个枢纽批次是 **160 / 144 / 152kg**，全部 ≤ 160；② 峰值发生在「先卸后装」之后（回程货 20kg 在枢纽停靠的**卸**阶段就下车），装派送单 160kg 时峰值是 160kg，不是 180kg；③ 3 台车 / 3 个批次天然一一对应。

**例外何时出现**：分配或动态改派把两个批次压到同一台慢车、或事件刷单让满载慢车还要取货 ⇒ 走规格一的降载 / 兜底链。**本文不新增任何机制**来回避它。

**回退预案（只记录，不预置）**：若实施后实测默认三策略**频繁**因容量触发降载 / 拆批（判据示例：三策略中 ≥2 条出现降载或拒绝），按 ① 慢车 160 → **180** → ② 仍不够 → **200** 的顺序回退；**只改 `[vehicles]` 的数值**，不动 schema / 算法 / 不变量，并重跑 §7.1 的捕获流程。

**出处**：#19 resolution §9（含裁决原则「最终呈现效果优先，但杜绝过于复杂的机制」）。

## 4. 类型感知的订单分配（#30）

> **来源**：[#30](https://github.com/Blorg51688/logistics-route-planner/issues/30) resolution §1–§12｜**权威落盘**：[ADR 0005](../../adr/0005-type-aware-allocation.md) + [GLOSSARY.md](../../../GLOSSARY.md)「订单分配」节｜**选型依据**：[pdp-multivehicle-research.md](pdp-multivehicle-research.md) §2.1(d)/§2.2/§3.2/§3.3

### 4.1 三阶段总览

```text
阶段一 聚类     簇(order) = node(order.A).sub_network_id；A、B 跨网 ⇒ 跨簇单，单独成队列
阶段二 整簇指派 枚举全部「簇 → 车」排列（默认 3 簇 3 车 = 6 种），各车独立跑规格一的单车构造器，
                按 (Σpenalty, Σ策略权重, 均衡键, tieKey) 取最优
阶段三 有界改派 单请求跨车 relocate，R ≤ 3 轮，只动普通段，字典序严格改进 **且完工耗时不得变差**
```

### 4.2 阶段一 · 聚类判据（定稿）

```text
簇(order)          = node(order.A).sub_network_id
isCrossCluster(o)  = node(o.A).sub_network_id ≠ node(o.B).sub_network_id
```

- **本地单**（A、B 同网）进 A 所在簇；**跨簇单**不属任何簇、进**跨簇队列**，由阶段二/三按边际代价指派。
- **手动新客户单**（B = 新节点）按 A 的子网络归簇——**前置修正**：建节点时必须继承最近邻节点的 `sub_network_id`，否则落进不存在的「子网络 0」（现状 `Node.h` 默认 0、`GraphEdit.cpp` 建节点从不设置）。该缺陷已进迁移清单 **MC-C04 / MC-G05**。
- **为什么不用几何聚类**：`sub_network_id` 已在数据里（复用零成本）；手写 k-means / 极角 sweep 会与既有字段重复真值，且几何聚类对时间窗盲（调研 §2.1(d)）。

### 4.3 阶段二 · 整簇指派 + 全排列枚举（定稿）

```text
for 排列 p in 全部「簇 → 车」排列:              # 默认 6 种
    for 簇 c in p 分到的簇:
        route[p(c)] = 单车构造(簇 c 的订单, 车 p(c))    # 规格一的 pair-insertion + EDD + relocate
    候选 = (routes, 跨簇队列按边际代价指派)
取 key 最小的排列
key(R) = ( Σpenalty, Σ策略权重, 均衡键, tieKey )
```

- **簇数 ≤ 车数**：枚举全部排列。**簇数 > 车数**：按簇货量降序取前 k 个簇各占一车，剩余簇并入「货量最接近且仍可行」的车（默认数据不触发，事件场景才用）。
- **「类型倾向快车」是枚举的结果，不是阈值规则**：默认数据 **0 条跨簇、0 条大宗**（最大单笔 24kg，最小容量 160kg），任何「跨簇 / 大宗 → 快车」的硬规则在默认数据上**没有对象可作用**。三策略各自选出不同排列，是枚举的自然分化。
- **载重均衡（均衡键）**：`峰值利用率(v) = max_t 在车量_v(t) / capacity_v`；`车队均衡度 = max_v 峰值利用率 − min_v 峰值利用率`（极差，越小越均衡）。**地位 = 决策键第三级 + 报告指标，不作硬约束**。
  - **「总 kg / 容量」是非法判据（实证否证）**：顺序轮转方案里 V02/V03 各分到 165kg > 160kg 容量，但峰值只有 64 / 57kg，**完全可行**。容量约束在路线前缀上，用总 kg 度量会把合法解误报为违规。
  - **为什么不作硬约束**：默认数据整簇不可分时均衡极差最小就是 0.55（距离策略），硬卡 0.3 立刻不可行；唯一出路是拆簇，而拆簇代价很大（sub1 整簇给一台慢车 39.8km，拆给两台各 5/4 单 = 60.8km，+53%）。

### 4.4 阶段三 · 有界跨车改派（定稿）

```text
for round in 1..3:                              # R ≤ 3
    improved = false
    for o in 普通段订单（EDD 序）:
        src = o 当前所在车
        for dst in 全部车, dst ≠ src:
            候选 = src 移除 o, dst 插入 o（规格一的 pair-insertion 评价器，用 dst 的因子重放）
            若 候选不可行: continue
            若 key(候选) < key(当前) 且 候选.完工耗时 ≤ 当前.完工耗时: 接受; improved = true
    若 not improved: break
```

- **只动普通段**：紧急段由订单级 FIFO 完全固定，relocate 对它是恒等操作。
- **两条接受条件**：① 字典序**严格改进**；② **完工耗时不得变差**。
- **为什么必须有第三阶段**：纯两阶段在**车队主口径上劣于基线**——距离策略 407min vs 顺序轮转 383min（整簇不可分：sub3 整批压给一台慢车它 14:47 才回仓，而快车 09:32 就空下来了）。
- **完工耗时守卫是实测得出的必要机制**（不加会退化）：

| 策略 | 无守卫的三阶段 | 有守卫的三阶段 |
| --- | --- | --- |
| 距离 | 136.6km / 407min / 改派 2 次 | **136.6km / 407min** / 改派 2 次 |
| 成本 | 142.5 元 / **429min** / 改派 12 次 | **169.0 元 / 418min** / 改派 5 次 |
| 时间 | Σ时间权重 433.9 / 383min / 改派 21 次，**每车 2 / 1 / 22 单** | **378min** / 改派 0 次，每车 9 / 9 / 7 单 |

> 上表是 #30 resolution §1 Q3 的**票内实算**（探针输出，不是规划器产物、不进任何断言）。它的用途只有一个：说明「守卫只有一条判定（本次改派不得让完工耗时变差），却守住 #19 定为主口径的量」。

### 4.5 顺序轮转基线（对照组，不是候选方案）

```text
排序 = 订单 ID 升序（O01..O25）；第 i 单 → 第 (i mod k) 台车；车辆序 = [vehicles] 行序
不跳车、不重分配、不做可行性预判；分完后各车独立跑规格一的单车构造
```

- **基线的分配只由「订单 ID 升序 + 车队行序」决定**，与策略、容量、窗口**全部无关**——这正是它作为对照的意义（换成 EDD 序会把「顺序」与「排序」混在一起，说不清差异来源）。
- 票内实算：213.2km / 278.6 元 / 完工 383min / 车时合计 937min / penalty 0（**不是黄金值**）。

### 4.6 分配失败兜底链（定稿）

```text
① 换车：枚举本就覆盖全部排列，能换就换（阶段二内部）
② 拆簇：装不下的簇按 EDD 前缀拆成两段给两台车；仅此级触发并留日志
③ 交规格一的降载 / 全量兜底链
④ 仍不可行 ⇒ 拒绝该单并报原因（不通过违反容量或先取后送去「凑」解）
```

默认数据走不到 ②③（快车单簇峰值 152–160/400；一次接两簇 sub1+sub2 总量 344kg、峰值 244/400 仍合规）。

### 4.9 九条分配不变量（验收直接断言）

1. **全部订单被服务**：每张**恰好**出现在**一台**车的路线上（转运版例外：取货车 ≠ 送达车），一次取货一次送达。
2. **簇归属完备且互斥**：每张本地单恰好属于一个簇；跨簇单不属任何簇；两集合的并 = 全部订单。
3. **容量（前缀峰值）**：每车任一时刻 0 ≤ 在车量 ≤ 该车 capacity；**禁止**用「总分配 kg ≤ 容量」判定。
4. **路线首尾相接**：每车从**自己的** `start_node` 按**自己的** `depart_time` **空载**出发、回**同一**基地；空车五项全 0、不抬升完工耗时（但参与 `min(发车时刻)`）。
5. **确定性**：同输入同输出；tieKey = (车辆 ID 升序, 节点 ID 升序, 订单 ID 升序)。
6. **时间口径**：到达时刻用**该车缩放后**的耗时重放；等待与 penalty 不乘因子；停靠零耗时；`arrival == we` 不算迟到。
7. **可加性**：Σ每车距离/成本/penalty/停靠数 == 车队汇总；完工耗时与车时合计并列、不互相顶替。
8. **第三阶段守卫**：任何被接受的 relocate 都必须满足「完工耗时不变差」；断言可在改派日志上核对（每条记录改派前后的完工耗时）。
9. **基线确定性**：顺序轮转基线的分配只由「订单 ID 升序 + 车队行序」决定，与策略/容量/窗口无关。

### 4.10 复杂度

| 阶段 | 代价 |
| --- | --- |
| 一 · 聚类 | O(m) 逐单查 `sub_network_id` |
| 二 · 枚举 | 排列数 k!（默认 6）；每排列各簇跑单车构造 O(m_c·n_c³) ⇒ **O(k! · Σ m_c n_c³)**，默认毫秒级 |
| 三 · 改派 | 每轮 O(m·k·n³)，R ≤ 3 ⇒ **O(R·m·k·n³)**，默认可忽略 |

目标规模 m ≤ 50 / n ≤ 100 / k = 3；**k > 4 时改用「簇货量降序贪心 + 阶段三修」并如实记录**（默认 k=3 不触发）。内存 O(m + n)，不建每车 V² 矩阵。

### 4.11 已知代价（如实记录）

- **均衡度劣于基线**：峰值利用率极差 0.54 / 0.85 / 0.76（三策略）vs 基线 0.18 / 0.38 / 0.22——整簇不可分的结构性代价，不掩饰。
- **只有时间策略在主口径上占优**：距离策略 Σ距离 −36% 但完工 407 > 383；成本策略 Σ成本 −46% 但完工 418 > 383；时间策略 378min＝可证下界，优于基线 383min。
- **完工耗时守卫是必要的额外机制**：不加会退化（成本 418→429、时间每车 2/1/22 单）。

## 5. 中转转运网络（#28）

> **来源**：[#28](https://github.com/Blorg51688/logistics-route-planner/issues/28) resolution §1–§19｜**权威落盘**：[ADR 0004](../../adr/0004-transit-transfer-network.md) + [GLOSSARY.md](../../../GLOSSARY.md)「节点角色」节｜**历史否证**：[中转站策略分析.md](../../中转站策略分析.md) §六/§七

### 5.1 转运是什么、不是什么

```text
禁转运版（基线）  [车1] … A …… B … → 基地        [车2] ……… → 基地
转运版           [车1] … A → S(整单卸，零耗时) … → 基地
                 [车2] ……… S(整单取，零耗时) → B … → 基地
                 时刻链：取货(A) ≤ 卸入(S) ≤ 取走(S) ≤ 送达(B)；站内等待 ≤ 60 min
```

**它不是「站里有一堆无主库存随便用」**：站里的每一份货都对应一笔确定的卸入（哪台车、什么时刻）与一笔确定的取走（哪台车、什么时刻），期末必须为 0。

### 5.2 转运 ≠ 降载（必须先分清，否则规格会写串）

| 维度 | **降载暂存 / 取回**（规格一 #18） | **跨车转运**（本文） |
| --- | --- | --- |
| 卸货车 | 某车 | 某车 |
| 取走车 | **同一台车** | **另一台车**（必须 ≠ 卸货车） |
| 触发 | 最后手段：插入/兜底都找不到可行位置 | 三条场景判据之一（§5.8） |
| 站的结构 | 全局**至多一堆**、**锁站** | 可多站多笔、各笔独立；无「堆」无锁站 |
| 取回位置 | 普通段的**必做停靠** | 接收车路线上的停靠 |
| 期末 | 暂存必须为 0 | 账本必须为 0 |
| 共用 | 「站只存车辆实际卸下的货」「站停靠零耗时、无窗口、不计 penalty」 | 同左 |

**同一台车卸了又取回，永远算降载，不算转运**——这条是判据、是验收断言，也是迁移时的分界（迁移清单 MC-A09）。

### 5.3 账本最小记录单位（TransitLeg）

```text
TransitLeg {
    orderId      : string   # 整单转运：kg 即该单全部需求
    stationId    : string   # 中转站
    kg           : double   # = 订单需求
    inVehicleId  : string   # 卸入车（≠ outVehicleId）
    inTimeMin    : int      # 卸入时刻（软件内时间）
    outVehicleId : string   # 取走车
    outTimeMin   : int      # 取走时刻
}
```

- 两端**都必填**：没有「只卸不取」的合法记录；无 `outVehicleId` 的候选在构造期就被丢弃。
- 无「计划/实际」双份：软件内时间只有一条时间轴，计划时刻即执行时刻（重规划时才重算，见 §6.7）。

### 5.4 停靠与合并

- 站上的**卸货停靠**与**取货停靠**都是一次停靠：沿用规格一——无窗口、不计 penalty、零耗时（`departure = arrival`）。
- 站停靠**计入该车的停靠点数**（是否单列「转运停靠」的文本口径归 #29 / 迁移清单，见 §7.9 G14）。
- **同一台车在同一个站既卸又取**（不同订单）：合并为一次停靠、停靠内先卸后装，峰值按「卸后/装后」较大者。
- 站上的卸/取动作**不属于**任何订单的取货点 A 语义（站不是 A；A 与 B 都是 delivery 节点）。

### 5.5 时刻链、容量与站内等待上限

```text
取货(A) ≤ 卸入(S) ≤ 取走(S) ≤ 送达(B)
站内等待 dwell = outTimeMin − inTimeMin ≤ 60      # 常量 kTransferMaxDwellMin，不加配置键
每次停靠：departure = arrival（零耗时）；早到等待只按送达点 B 的窗口开启时刻计（站无窗口）
容量：卸货车与接收车各自按自己的前缀载重检查 0 ≤ L ≤ 该车 capacity
```

**为什么用可行性而非指标管住等待**：站没有窗口、停靠零耗时 ⇒ 货在站里等多久**不产生耗时、不产生 penalty**；若不管，转运可以把等待搬进站里让完工耗时/车时合计变好看，而货实际更晚到——「绝不更差」就成了空话。用可行性管住它最省、也最难绕过（不新增指标、不扩摘要行）。

### 5.6 守恒三式（验收直接断言）

```text
(C1) 整单不可拆：任一站任一订单，站内量 ∈ {0, kg} ⇒ 同一 (stationId, orderId) 至多一笔「未取走」记录
(C2) 非负：任一站任一时刻，Σ卸入 − Σ取走 ≥ 0
(C3) 期末 0：计划结束时每一笔都有 outVehicleId/outTimeMin；站内为 0
```

- **期末 0 由构造保证**：规划器只产出「取走车在收工前把货送达」的方案——「留站过夜」不是合法计划；期末非 0 ⇒ 该转运候选**不可行**，退回禁转运版。收尾不是「事后补一趟」。
- **跨重规划**：站内存货只能来自**已实际执行**的卸入；计划内未执行的卸入在重规划时**全部作废**；已执行的卸入必须被继承（见 §6.7）。**不得跨轮累积**（P25 的 870kg 库存膨胀就是反面教材）。
- **custody 校验（送达前）**：校验「这段货确由该站、该车取走，且 kg 与订单需求一致」；不一致 ⇒ 该计划不可行（缺陷，不是软约束）。

### 5.7 「绝不更差」的可执行判据（严格字典序）

```text
key(P) = ( Σ penalty_i（该计划内全部送达单，逐单窗口）,
           Σ 策略权重（全部车辆，用各车缩放后的边权重放）,
           tieKey(P) )
accept(relay, direct) ⟺ key(relay) < key(direct)      # 严格字典序小于
```

- **penalty 一票否决的精确形式 ＝ 字典序第一键**：Σpenalty 更大就直接否决，哪怕距离/成本/耗时全面更优。**不需要额外分支**。
- **完全并列 ⇒ 保留禁转运版**。
- **tieKey**：按车辆 ID 升序、各车停靠序列逐位比较（节点 ID，该停靠排序后的动作订单 ID）；再并列取枚举序最小者（站 ID、接收车 ID 升序）。
- **为什么必须严格（本节最重要的一条）**：本图 84.2% 的配送点对存在**精确零绕行**站 + 停靠零耗时 ⇒ 转运版在 distance/time/cost 上**常常完全并列**。若用「不更差即启用」，默认数据会被大量零收益转运改写：路线、custody、停靠数全变，而三项指标一个不动——验收与复核成本陡增。严格更优让「并列 ⇒ 保留禁转运版」成为一句可执行的话。

### 5.8 启用场景（三条可执行判据，场景门控）

| # | 场景 | 判据（全部可从禁转运版直接读出） | 候选站集合 |
| --- | --- | --- | --- |
| ① | **跨簇订单** | 存在订单 o，`sub(A) ≠ sub(B)` | 零绕行站：`d(A,S)+d(S,B) ≤ d(A,B)+ε` |
| ② | **容量腾挪** | 禁转运版里某车在某停靠前的**前缀载重将超该车 capacity**（即规格一会走降载/判不可行） | 卸货车自然路线上的零绕行站 |
| ③ | **紧急响应** | 禁转运版里某**紧急单** penalty > 0（＝迟到） | 零绕行站：`d(A,S)+d(S,B) ≤ d(A,B)+ε` |

- 「零绕行」按**当前策略权重**判（距离看距离、耗时看耗时、成本看成本）。
- 判据②的选货沿用规格一：只卸**整张普通订单**，kg 降序、同 kg 按订单 ID，取前缀直至够腾。
- **判据②与降载并列比较**：两者都构造出来，各自整计划 key 比较，**严格更优者胜**；都不可行则该单判不可行（走规格一的兜底链）。

### 5.9 有界贪心与执行顺序

```text
plan = 禁转运版（= 规格一构造 + #30 分配的结果；转运层不改分配）
for trigger in [跨簇, 容量腾挪, 紧急响应]:        # 固定顺序，保证确定性
    for round in 1..3:                            # R ≤ 3
        cands = generate(trigger, plan); best = argmin_key(cands)   # 并列按站 ID、接收车 ID 升序
        if best == none: break
        if accept(best, plan): plan = best; continue
        else: break
```

**每类判据最多 3 轮、每轮至多接受一个**（该轮 key 最优者）；无更优即停 ⇒ 转运版永远由**逐步严格变优**得到，**绝不更差是构造保证**，不依赖事后校验。转运层**不改分配**：谁走哪台车归 #30。

### 5.10 紧急单的最后手段通道（比通用判据更严的双门槛）

```text
触发（只有一条）：禁转运版里该紧急单已被记 penalty > 0；否则不构造紧急转运候选
accept_urgent(relay, direct) ⟺ penalty_该单(relay) < penalty_该单(direct)   # 门槛一：该单 penalty 严格下降
                            and key(relay) < key(direct)                   # 门槛二：整计划 key 严格更优
```

**与紧急硬优先的三条不变量如何共存（精确化，不是推翻）**：

| 原不变量 | 本机制的精确化 | 为什么仍可验收 |
| --- | --- | --- |
| 紧急队列**订单级 FIFO** | `U_k 的送达时刻 ≤ U_{k+1} 的取货时刻` | 单条路线内二者等价；跨车后仍是可计算的不等式 |
| **同刻至多一张紧急单在车** | 同刻至多一张紧急单处于**已取未送**（在车**或**在站） | 转运把「在车」扩成「在执行」；在站期间仍是同一张单 |
| **硬优先** | 取走车必须在**自己的紧急段内**完成该取货与送达 | 逐车可断言 |

### 5.11 十二条不变量（验收直接断言，读规划产物）

1. **转运段完整**：每笔 TransitLeg 两端（in/out 车辆与时刻）都非空；`inVehicle ≠ outVehicle`。
2. **整单不可拆**：同一 (站, 订单) 至多一笔未取走记录；kg ＝ 该单需求。
3. **守恒**：任一站任一时刻 `Σ卸入 − Σ取走 ≥ 0`；**期末为 0**。
4. **时刻链**：取货(A) ≤ 卸入(S) ≤ 取走(S) ≤ 送达(B)。
5. **站内等待**：每笔 dwell ≤ 60 min。
6. **容量**：两台车各自任一时刻 0 ≤ 前缀载重 ≤ 该车 capacity（停靠内先卸后装）。
7. **停靠语义**：站停靠无窗口、不计 penalty、零耗时；计入该车停靠点数。
8. **penalty 归属**：转运单的 penalty 只在**送达车**的指标里出现一次；取货车不记。
9. **先取后送**：每张订单 A 的停靠索引 < B 的停靠索引（跨车时按各自路线分别成立，链由第 3、4 条连起来）。
10. **严格更优**：最终计划的 key **严格小于**禁转运版的 key，或两者**完全相同**（＝未启用转运）。不存在「更差」的第三种结果。
11. **确定性**：同输入（车队配置、策略、事件序列）必得同一 plan；并列按 tieKey 与枚举序。
12. **不残留**：重规划后不存在「上一版计划里卸入、但从未实际执行」的站内存货。

## 6. 动态事件复调度（#27）

> **来源**：[#27](https://github.com/Blorg51688/logistics-route-planner/issues/27) resolution §1–§9｜**权威落盘**：[ADR 0007](../../adr/0007-dynamic-event-rescheduling.md) + [GLOSSARY.md](../../../GLOSSARY.md)「模拟事件与动态订单」节

### 6.1 单一全局车队时钟 + 一个推进原语

```text
advanceFleetTo(T):                        # T = 目标软件内时刻
    repeat:
        Tnext = min over 车 v of (v 的下一节点到达时刻，若存在)
        if Tnext == +inf or Tnext > T: break
        对每台「下一节点到达时刻 == Tnext」的车 v：onAdvanceStopFor(v)   # 唯一状态转移点
    settleEventsUpTo(T)                   # 每刻恰 1 抽，与推进粒度无关
```

两条推进路径**都归结为这一个原语**：「推进一站」的 T = 所有车下一节点到达时刻的最小值；「推进一刻」的 T = `nextEventMark_`（下一个未结算事件刻，**全局唯一**）。

- **事件刻属于车队，不属于某台车**：每刻恰抽 1 个事件、恰消耗 1 次抽签（规格一事件模型不变）。
- **每车一份游标**：`nodeIndex_` → `nodeIndex_[v]`；`VehicleState`（位置/时刻/在车货/已送达/已发生 penalty）→ 每车一份。
- **等价性由构造保证**：两条路径调用同一原语、同一时间轴、同一事件刻游标 ⇒ 任何时刻看到的事件串与车辆状态都相同。**不靠断言事后比对**——断言只用于证明「原语确实被两条路径共用」（§6.10）。
- **同刻多车**：Tnext 并列时**同刻推进多台车**，然后才结算事件；这消掉了「谁先谁后」的歧义。
- **如实记录的代价**：「推进一站」的语义从「这台车走一站」变成「全局走一站」，节奏由最慢的车决定。

### 6.2 复调度的共同边界：已执行前缀不重排

以下四项作为复调度的**输入常量**：各车当前位置与当前时刻、各车在车货、**站内已执行账本**（只有转运；降载暂存归原车）、已送达订单集合与已发生 penalty 累计。

### 6.3 局部重规划 = 两版比较，严格更优才改序

```text
localReplan(v, 事件):
    # ① 顺序不变版：停靠顺序完全不变，只把该车「剩余停靠序列」按新边权重放一遍
    R1 = replay(v.剩余停靠序列, 新边权, now_v, pos_v, onboard_v, ledger)
         # 任一 leg 不可达 ⇒ R1 不可行
    # ② 重排版：对该车剩余订单重跑规格一的构造器（pair-insertion + repair R≤3）
    R2 = plan(v.剩余订单, 新边权, now_v, pos_v, onboard_v, ledger, v.因子)

采用 R2 当且仅当 R2 可行 且 key(R2) < key(R1)     # 严格字典序，并列保留 R1
否则采用 R1（R1 也不可行则进入 §6.4 的第②级）
```

- **key 沿用**：`(Σpenalty, 当前策略权重, tieKey)`；**策略权重必须用该车缩放后的边权重放**，不能先排路线再缩放。
- **不重写 A→B 版 leg 级增量**（对规格一 §10 的显式偏离）。理由与两方原文见 **§10 待裁定 1**；本文不选边。

### 6.4 五级升级链

**「失败」的可执行定义**：该级产不出**可行解**。可行 = 容量（前缀载荷 0 ≤ L ≤ C_v，停靠内先卸后装）+ 窗口（只影响 penalty，不判不可行）+ **可达**（任一 leg 不可达即不可行）+ 先取后送 + 紧急硬优先/FIFO 全部成立。

```text
reschedule(事件):
    V = affectedVehicles(事件)                        # 见 §6.5；可以是空集
    # ① 局部重排
    for v in V: v.plan = localReplan(v, 事件)
    若全部可行 ⇒ 接受，结束（**不跑全局**，见 §6.6）
    # ② 跨车再分配：把失败车上的一张订单移到另一台车
    for o in 失败车的剩余订单（普通段 EDD 序、紧急单优先）:
        for dst in 全部车按 Δkey(o, dst) 升序（dst ≠ 当前车）:
            候选 = 当前车移除 o、dst 插入 o（规格一 pair-insertion 评价器，用 dst 的因子重放）
            若可行 且 key(候选) < key(当前) ⇒ 接受
    若全部成功 ⇒ 接受，结束
    # ③ 全车队重调度：#30 的三阶段全跑
    # ④ 降载 / 转运并列比较：先构造降载版，再构造转运版；整计划 key 严格更优者胜；并列保留降载版
    # ⑤ 拒绝该单/该事件并报原因（不通过违反容量或先取后送去凑解）
```

**每级都复用已定稿的构造器，不新增算法**：① 重放 + 规格一构造器；② 规格一 pair-insertion 评价器；③ #30 三阶段；④ 规格一降载链 + #28 §5.8。

**分级播报行（守卫要读的可见输出之一）**：`[复调度] 局部重排（1 台车）` / `[复调度] 跨车再分配 O12 V02→V01` / `[复调度] 全车队重调度` / `[复调度] 降载（T01，2 张单）` / `[复调度] 转运（T02，V02→V01）` / `[复调度] 拒绝：<原因>`。

### 6.5 受影响车集合（可执行判据）

| 事件 | 判据（逐车，全部可从「该车剩余路线 + 当前图」直接读出） |
| --- | --- |
| **路况** | 存在被改动的边 e，使 `e 在该车剩余路线上（有向，相邻两站）` **且** `e.increaseRatio ≥ traffic_time_increase_min` |
| **封路** | 该车剩余路线上**用到**被封闭的边（任一方向） |
| **普通/紧急订单** | **不重算任何既有车**——只对选中的车做**插入**；插入失败才把该车加入集合进升级链 |
| **手动新客户 / 手动普通单** | 同普通订单 |

**实测分布**（票内实算，不是断言）：0 台 10.2% / 1 台 34.9% / 2 台 39.8% / 3 台 15.1%，E[受影响车] = 1.60。**规格里不得写成「最多一台车」**。

### 6.6 新订单的选车顺序

```text
assignNewOrder(o):
    cands = 全部车，按 Δkey(o, v) 升序（并列按车辆 ID 升序）
    for v in cands:
        若 o 能在 v 上可行插入 ⇒ 接受，只对 v 重规划
    否则 ⇒ 进入 §6.4 的升级链
```

- **普通单与紧急单共用**这条规则；跨车再分配（第②级）**同一条**规则。
- **与 #30 Q7 不冲突**：#30 交出「取 Δkey 最小的车」，来源票 #27 补「最小但不可行」时的退路——Δkey 最小的车有解时首个命中，语义一致。
- **Δkey 必须用候选车自己的因子重放**。
- **不做「局部 vs 全局两版取优」**：局部可行即接受，不跑全局（与规格一「不做周期性全量重规划」同向）。**如实记录的代价**：短视，可能错过全局更优解——被显式接受。

### 6.7 紧急硬优先与订单级 FIFO：逐车

```text
逐车成立：
  (E1) 该车的全部紧急停靠 先于 该车的全部普通停靠
  (E2) 该车车内订单级 FIFO：U_k 的送达时刻 ≤ U_{k+1} 的取货时刻
  (E3) 该车同刻至多一张紧急单在车
全局只保证：
  (E4) 紧急单先于普通单被**分派**（新紧急单立即处理，普通单走 §6.6 同规则）
```

- **显式声明放弃**「全车队同刻至多一张紧急单在执行」的读法。依据：#19 §5 已把它落成**按车计**；#28 §9.3 精确化为「同刻至多一张紧急单处于**已取未送**（在车或在站）」，那条要防的是「同一张单被记成两张」，**不是**「两台车各有一张」。
- **算例佐证（票内实算）**：全局 FIFO 下 U2 要等 U1 送完再花 40min ⇒ t+65 送达、超窗 5min、penalty 5；逐车 FIFO 下 U2 派给车 B ⇒ t+40 送达、penalty 0。⇒ 跨车再分配的全部价值在**并行**上。
- **如实记录的代价**：一场 25 刻里约 0.9 个刻出现「两张紧急单分属两台车同时在执行」。演示时必须能解释这是逐车 FIFO 的正常形态，不是 FIFO 失效。

### 6.8 先降载还是先转运

- **落在第④级**（不是第①级）：只有 ①②③ 都失败后，才做降载/转运的比较——两者都是**改变货物路径**的重手段，不该在局部能解时介入。
- **执行顺序固定**：先构造降载版，再构造转运版（顺序固定才能保证确定性）。
- **接受判据**：整计划 key **严格字典序更优者胜**；**完全并列保留降载版**（理由与 #28 §5.7 同构：并列时选跨车耦合更浅的那个——降载是同车、不依赖另一台车的路线、不产生转运账本、不引入 dwell 约束）。
- **期末 0 仍是硬门槛**：转运版若留下站内存货 ⇒ 该候选不可行。

### 6.9 已执行卸入的继承与未执行卸入的作废

| 类型 | 谁取走 | 跨重规划继承 | 期末 |
| --- | --- | --- | --- |
| **降载暂存**（同车卸、同车取） | **原卸入车** | 沿用现有 `StashState` | 暂存为 0 |
| **转运账本**（卸入车 ≠ 取走车） | **任一可行车**（复调度重新指派） | 作为**一等输入**进复调度 | 站内为 0（C3） |

- **未执行的卸入 = 结构性作废**：复调度的输入里**根本没有它**（输入只有已执行账本），所以不需要任何清理动作——旧计划里的「打算卸入」随旧计划一起丢弃。这符合本项目「不要把物理事实从计划反推」的纪律（P25/P28 那类缺陷）。
- **取走车** = `argmin Δkey` 且可行（原计划指定的取走车若仍经过该站且可行，它通常就是 argmin）；`dwell ≤ 60` 不可行则整个候选不可行。
- **custody 校验**：送达一张转运单前校验「这段货确由该站、该车取走，且 kg 与订单需求一致」。

### 6.10 等价性守卫 A1–A7（读用户可见输出）

```text
前置：同一份 config、同一个随机种子、两次独立运行（重新加载配置，不深拷贝 MainWindow）
路径 A：反复「推进一刻」直到车队时钟 ≥ T
路径 B：反复「推进一站」直到所有车都到达 ≥ T

断言（全部必须逐字/逐值相同）：
  A1 事件日志序列：所有 `[事件] HH:MM 抽取：…` 行，逐行逐字相同（含时刻前缀）
  A2 已送达订单集合（按车分组）
  A3 各车已发生 penalty 之和
  A4 各车在车货（订单 + kg）
  A5 站内已执行账本（订单/站/kg/卸入车/卸入时刻/取走车/取走时刻）
  A6 各车位置（节点 ID）与时刻
  A7 车队时钟 nextEventMark_
```

- **A2–A7 覆盖「同刻多车」**：Tnext 并列时同刻推进多台车，若两条路径顺序不同，A6 会立刻分叉。**A1 覆盖「推进粒度不变性」**。
- **不读 `nodeIndexAtTime`**：它是显示用函数，拿它断言等于「从计划反推物理事实」。
- **反向验证对象（必须能变红）**：把 `settleEventsUpTo` 从 `onAdvanceStop` 删掉 ⇒ **A1 必须红**；把 `advanceFleetTo` 的 Tnext 并列分支改成「只推进第一台」⇒ **A6 必须红**。
- **这是规格一遗留缺口**（现状零断言），本规格把它补上，落地归迁移清单。

### 6.11 十四条不变量（验收直接断言）

1. **事件刻唯一**：全车队一个 `nextEventMark_`；每刻恰 1 次抽签；一次推进跨多刻则连续结算多次。
2. **推进原语唯一**：「推进一站」与「推进一刻」都只经由 `advanceFleetTo(T)` 改变车辆状态与时刻。
3. **等价性**（§6.10 的 A1–A7）。
4. **已执行前缀不可重排**：复调度前后，各车已送达集合、已发生 penalty、在车货只增不减（由实际执行改变，不由重规划改变）。
5. **受影响集合正确**：被重算的车 ⊆ `affectedVehicles(事件)` ∪ {被选中插入新单的车} ∪ {升级链涉及的车}；**未受影响的车路线逐字不变**。
6. **局部两版**：采用重排版当且仅当 `key(重排) < key(顺序不变版)`；否则停靠顺序不变。
7. **升级链单调**：第 k 级只在第 1..k−1 级都失败后执行；日志出现第 k 级的分级播报行。
8. **逐车紧急**：(E1)(E2)(E3) 逐车成立；(E4) 全局成立；**不存在**「全车队同刻至多一张紧急单在执行」的断言。
9. **先再分配后转运**：紧急单的转运候选只在「全部车都不可行」后才构造（#28 的双门槛不变）。
10. **降载先于转运构造、并列保留降载**。
11. **账本**：只含已执行的卸入；每笔都有取走车与取走时刻；dwell ≤ 60；期末为 0。
12. **降载/转运分界**：同一台车卸了又取回 ⇒ 记降载，不记转运。
13. **确定性**：同输入（含车队配置、策略、随机种子）必得同一事件串、同一分配、同一路线。
14. **不丢单**：新单通过校验即并入订单集合；插入失败照实播报并保留未服务状态。

### 6.12 复杂度

| 环节 | 代价 | 默认规模 |
| --- | --- | --- |
| `advanceFleetTo` | O(k) 找 Tnext + 每次状态转移 O(1) | k=3，可忽略 |
| 顺序不变版（重放） | O(n_v) | n_v≈10，微秒级 |
| 重排版（该车） | O(m_v·n_v³) | m_v≈9、n_v≈10 ⇒ 约 10⁴ 重放步，毫秒级 |
| 跨车再分配 | O(m_v·k·n_v³) | 约 3×10⁴，毫秒级 |
| 全车队重调度 | O(k!·Σm_c n_c³) + O(R·m·k·n³) | 只在升级时触发 |
| 降载/转运并列 | O(|T|·n³) + O(3×3×27×n³) | 只在第④级触发 |
| 一场 25 刻总量 | 16.9 次路况 × 平均 1.60 台车 × 毫秒级 | 远低于一次全车队重调度（这就是「局部优先」的量化收益） |

**内存**：O(m + n) 路线 + O(k) 游标；不建每车 V² 矩阵。

**不进 63 的两项，各有理由**：

- **该车停靠数**：逐车路线序列（§7.3）已冻结，停靠数是它的**函数**——再冻一遍是重复真值。它仍打印（人读有用），也仍受车队级第 5 项与 Σ 恒等式约束。
- **该车两率的紧急/普通分列**：逐车订单数小（默认 7–13 单），紧急单在单车上常为 0 ⇒ 分母 0 的 `—` 会在多数车上出现，冻结一堆 `—` 不携带信息。分列**只在车队级**。

### 7.3 每车路线序列逐字冻结

第 7–9 行的节点序列是**冻结集的一部分**（不进 102 个数值常量，但 L1 逐字比对）：① 它是「谁跑哪些单」的**完整证据**，比 7 个汇总数更强；② 它是 L3 oracle 算术对拍的输入（多车下必须每车一条，否则 oracle 无法复算每车指标）；③ 冻结序列后「每车停靠数」自动被守住。

| --- | --- | --- |
| 1 | 当前位置 | 节点 ID（与画布标记一致） |
| 2 | 下一站 | 下一停靠点节点 ID；无剩余则「—」 |
| 3 | 阶段 | 紧急 / 普通 / 已收工（由剩余路线的阶段标记推出） |
| 4 | 车上载重 | 该车此刻实际载着的订单货量 kg（物理事实，不反推） |
| 5 | 已送达 X 单 · 剩余待送 Y kg | 该车的服务进度 |
| 6 | 已发生 penalty | 该车累计、跨重规划保留 |

- **软件内时间不进页签**：它是全局量，已由状态栏常驻显示；每车页签重复打印 3 次是噪声。
- **「本趟出发装载」「第 N 趟」两行随趟结构退役**，`--ui-probe` 的对应正则一并删除。

**③ 停靠明细 8 → 9 列**（列序固定）：**车辆** / 序号 / 阶段 / 配送点 / 动作（`取<a>·送<b>`）/ 原始到达 / 等待(分) / 送达 / 余货(kg)（语义 = 离开该站时的在车货量）。

**④ 超时订单 7 → 8 列**（列序固定）：**车辆** / 订单 / 配送点 / 档位 / 状态 / 到达 / 窗口 / penalty(min)。

- **行序**：先按车辆行序（`[vehicles]` 行序），车内再按序号（停靠明细）/ 按到达时刻（超时面板）。这让「一屏全队」可读，也让 L2 守卫能整表比对。
- **为什么不用「序号复合成 V01-3」**：序号列会被 G8 当作纯整数解析；加一列比改语义便宜。**为什么不做「跟随页签过滤」**：演示时要一眼看到三车在同一时间轴上的停靠交错。

**⑤ 画布三色 + 选中加粗**：

```text
配色（代码常量，按 [vehicles] 行序取，超出 3 台时循环）
    V01 #C0392B（红）   V02 #1F6FEB（蓝）   V03 #1A7F37（绿）
高亮权重：选中页签的车 不透明度 1.00、线宽 3；其余车 0.45 / 1.5
共享边归属（多车经过同一有向边）：颜色 = **行序最前**那台车的颜色；不重复绘制
                              加粗判定 = 该边是否属于**选中车**（与颜色归属解耦）
```

- **`EdgeItem` 的改造**：`setHighlighted(bool)` → `setRouteStyle(ownerVehicleIndex, isSelectedVehicleRoute)`（或等价的 `setHighlightColor + setHighlightWeight`）。这是实现细节，本文只钉语义。
- **空车**不参与绘制，页签仍在。**权重标签**仍只在被高亮的边上显示，内容仍是**基础边权**、不按车缩放。

**⑥ 转运账本面板**（新增 dock，与「中转站 / 集散」tabify 叠放，7 列）：订单 / 中转站 / kg / 卸入（`<车辆ID> <HH:MM>`）/ 取走（同形；未取走显示 `—`）/ 站内等待(min)（未取走显示 `—`）/ 状态（在站 / 已送达）。

- **账本只记「已实际执行」的卸入**；**期末必须为空**（若有「在站」行是缺陷）。
- **与中转站面板第 4 列的分工**：第 4 列是**降载暂存堆**（同车取回，聚合 kg）；账本是**转运**（跨车，逐笔）。

### 7.6 新增「插入普通订单…」动作（演示入口）

**工具栏**：「事件注入」条，紧跟「插入紧急订单」，动作名 **`插入普通订单…`**（带省略号，表示会弹对话框）。**对话框**与「插入紧急取送单」同形：取货点 A（全部 delivery 节点下拉）/ 送达点 B（全部 delivery 节点、**排除当前 A**）/ 货量 kg（整数 **3–15**，且 `< min([vehicles].capacity_kg)`）。

```text
id = 前缀 M + 递增号（M001, M002, …）    pickupNodeId = A    nodeId = B
demandKg = 整数 3–15                     windowStartMin = 当前软件内时刻    windowEndMin = 24:00
urgent = false    served = false    来源 = manual_normal
```

- **走同一条插入链**：`assignNewOrder`（§6.6）；插入失败照实播报并保留未服务，不丢单。**不计入自动刷单额度**。
- **无头路径**（`--self-check-actions` / `--demo` / offscreen）：与 `onInsertUrgentOrder` 同处理——退化为随机 A/B，保持自动化可跑。
- **为什么必须有这个动作**：默认数据上转运三判据**静态全不触发**（0 跨簇、每簇一批不超容量、初始无紧急单），紧急转运通道也不开（三车都能 60min 内送达 ⇒ Δpenalty 恒 0 ⇒ 双门槛第一条永不满足）。现有手动动作里没有「可控 A/B 的普通单」这一档：「插入紧急订单」可控但走紧急通道；「模拟新客户」造普通单但 A 随机、B = 新节点 ⇒ 造不出跨簇对。**没有这个动作，规格二最强机制在验收现场根本不可演示。**
- **来源枚举扩展（如实记录）**：#24 R5 定的是四类来源（`initial / event_normal / event_urgent / manual_customer`）+ 前缀 `O / N / U / C`。#25 **新增第五个值** `manual_normal` / 前缀 `M`，**不改既有四个**（复用会让「该单是否带新节点」或「事件来源计数」的区分消失）。交接 #24 / 本文 / 迁移清单。

### 7.7 演示口径

**三条主线**：

| 主线 | 演什么 | 依赖 |
| --- | --- | --- |
| **M1 异构调度** | 三策略各自把哪些簇给哪台车、逐车指标差异、完工耗时 vs 车时合计 | 默认数据即可（零额外操作） |
| **M2 跨车转运** | 插入一张跨簇普通单 → 时间策略下接受转运、距离策略下否决、成本策略下否决 | **需「插入普通订单…」** |
| **M3 不可达处置** | 删桥边造不可达 → 日志「不可达 / 不可行 + 原因」播报（升级链末端） | **需「手工增删…」删桥边**（事件封路不产生不可达） |

**现场脚本（8 步，每步一个可指认的观察点）**：

```text
0  重启进程（保证从干净状态开始；默认三车配置）
1  载入：状态栏「软件内时间：08:00」；车辆信息 3 个页签（V01·400kg / V02·160kg / V03·160kg）；
   路线信息底部有「逐车指标」三行
2  策略 = 最短距离 → 记录逐车指标三行与画布三色路线
3  策略 = 最低耗时 → 三色路线与逐车指标都变（类型倾向快车的可见证据：长腿簇归 V01）
4  事件注入 →「插入普通订单…」：A=D08（sub1 枢纽）、B=D18（sub3）、8 kg
   → 观察：订单表出现该单；日志播报「插入普通订单 M001：D08 取 → D18 送」与指派到的车
5  策略 = 最低耗时 →「重新规划」
   → 观察：日志出现转运分级播报行；**转运账本面板出现一行**（卸入车 ≠ 取走车、站内等待 ≤ 60）
6  策略 = 最短距离 →「重新规划」（同一张单、同一个图）
   → 观察：**不出现转运**（两版距离精确相等 ⇒ 严格更优不成立 ⇒ 保留禁转运版）
7  推进一站数次直到该单送达 → 转运账本该行状态变「已送达」；期末账本无「在站」行
8（可选）不可达：手工增删 → 删除 D04–T01（桥边之一）→ 日志出现「不可达 / 不可行」播报，
   且**照实拒绝并报原因**；⚠ 删边不可撤销，此步放最后，演示后需重启进程
```

- **第 5/6 步的转运是否真被接受，由实施后的实测钉死**：本规格只钉「操作序列 + 观察点种类」，**不钉具体数字**。若实测该对未被接受，按 #25 §2 的方法复算候选换一对。
- **第 8 步用删桥边而非事件封路**：事件封路的实现显式跳过桥边（避免把区域变孤岛），**永远**造不出不可达；「手工增删」可删任意双向边。
- **`D08→D18` 是候选而非承诺**：#25 §2 P9 给出时间策略下的一个可行对（票内实算增益 4.475min），实施后以实测为准。

**无头演示（回归用途，不是现场主线）**：

# 必须带 --render-window：单独 --demo N 会在事件循环里挂死（实测 exit 124）
QT_QPA_PLATFORM=offscreen ./build/app --demo 3 --render-window /tmp/demo.png --export-log /tmp/demo.log

- 演示脚本（若落成 `scripts/demo.sh`）**必须**用这个形态；实施时把这条写进脚本注释与 `--demo` 的 `--help` 说明。
- `--demo` 的既有语义（推进一站 + 路况 + 隔轮插紧急单 + 隔三轮封路）**不改**；它是回归装置，不是现场演示主线。
