## 提案（用户原话）

> 在我观察模拟后，发现紧急订单可能极大的增加总配送距离/时间。我想利用起中转站的暂存功能，首先我有个假设，
> 满载着出仓库并在派送完毕准备返回仓库时（因为出仓库时可能带了多余本趟配送的货物，故会出现盈余）
> 顺路把盈余货物留在中转站中。如此积少成多，随着趟数增加中转站中的空闲货便会积累。
> 之后若出现紧急订单这种突发情况，车辆可以就近去中转站补充货物并送去紧急订单以减少车辆返回仓库的次数，
> 从而提高整体配送效率。首先满载着离开仓库肯定不会让结果变得更糟，而为中转站补货这个操作也都是顺路进行的
> 没有额外成本。而确实可能出现为后面提到的让留在中转站中的货去就近补充了紧急订单而使整体效率提升。
> 那么这样一个绝对不会更差且有可能更好的提议就应该被采纳。

拆开是**三条互相独立的前提** + 一条结论：

| # | 前提 | 隐含断言 |
|---|---|---|
| P1 | 「满载出仓 → 派送完毕返程时车上会有盈余」 | 常规（非途中重规划）规划下，每趟返程载重 > 0 |
| P2 | 「顺路寄存，没有额外成本」 | 寄存不需要绕路，寄存前后总里程不变 |
| P3 | 「积少成多 → 紧急单就近取货 → 减少回仓库次数 → 提高效率」 | 站内库存能把紧急单的 Δ距离/Δpenalty 显著压低 |
| 结论 | 「绝对不会更差且有可能更好 → 应当采纳」 | 存在一个既不改坏任何指标、又能改善紧急单的实现 |

### P1「返程有盈余」→ **否证（实测 0 kg）**

探针 A 输出（三策略 × 各 6 趟，摘 distance）：

```
-- 策略 distance: 总距离 178.2km 趟数 6
  第1趟 load=190kg 实送=190kg 盈余=0kg 停靠7 末站=D04
  第2趟 load=72kg  实送=72kg  盈余=0kg 停靠2 末站=D12
  第3趟 load=196kg 实送=196kg 盈余=0kg 停靠7 末站=D17
  第4趟 load=62kg  实送=62kg  盈余=0kg 停靠2 末站=D25
  第5趟 load=178kg 实送=178kg 盈余=0kg 停靠6 末站=D13
  第6趟 load=42kg  实送=42kg  盈余=0kg 停靠1 末站=D16
  >> 本策略最大返程盈余 = 0 kg
```
`time` / `cost` 两策略同样为 `0 kg`（各 6 趟逐趟为 0）。

**原因（代码级）**：`multiTripPlanImpl` 的每批装载量 = `Σ该批订单货量`（`RoutePlanner.cpp:461-477` 的
`batchLoad`），而 `weave` 会把该批 pool **全部送完**才回仓库（`:126-205`，循环直到 `pool.empty()`）。
因此 load 恒等于实送量，返程恒为空车。

**这条与历史作者的自述完全一致**（`git show 1f5b552` 提交信息原文，第一手读取）：

> 「不是常规直送——常规直送时车**空车**回仓库，没有可寄存的货。
>  真正触发的是**途中重规划**：车正在簇内执行某趟、载着尚未送达的货，而新规划要求它先回仓库。」

**结论：P1 不成立。**「满载出仓」不产生盈余，无货可寄存。

### P2 与「满载」本身：**满载是空操作（静态检索，0 处决策点）**

核心层 `loadKg` 的全部出现点（`grep -rn "loadKg" src/core/*.cpp src/core/*.h`）：
`RoutePlanner.cpp:112`（形参）、`:115`（记账）、`:199-200`（减法 + 写入 Stop）、
`:588-604`（`makeStop` 同构）、`:645`（`sliceRemainder` 复制）、`:717-719`（`replanIncremental` 复用上一趟记录）。
**没有任何一处是选路条件、分批条件或趟次条件。**分批只看 `demandKg` 与 `capacityKg`（`:463-477`）。

**结论：把车装到满载这件事本身，对距离/耗时/成本/penalty/趟数全部零影响**——
既不会更差（用户这点对），也不会更好（用户这点的推论不成立）。要让它有影响，
必须改变"**哪些货上哪趟车**"，那只有两条分支：
① 装上别簇的货 → 卸在错误的中转站（见"反驳与风险" R1 的历史反例）；
② 装上本簇后续批次的货 → 后续批次改从站里取，净效果见 R2。

### P3「顺路零成本」→ **只部分成立（实测 4/6 零绕路，2/6 有绕路）**

探针 B 输出（distance 权重）：

（用户提案里的"顺路"约束若严格照做——不满足就不寄存——那它自动退化为"什么都不做"，

## 反驳与风险（含"最坏情况代价"）

**R1（对 P1/P2 的反例，历史实测）**「满载 + 余货卸在错误的中转站」会更差。
范本 §二给出可复现反例：按簇装货 **124 km / 2 趟** vs 一律满载 + 余货卸在当前站 **236 km / 3 趟**（**+90%**）。
根因不是"满载"，而是**把不相关的货卸在了某个站**。→ 这正是"满载出仓"要凑够货量时唯一可能的货源。

**R2（对 P3 的机理反驳）**同簇"寄存—取用"是**自抵消**的。
若满载的货来自本簇**后续批次**，后续批次必然要来站里取回它（否则该货的客户无人配送）；
货仍然要从仓库跨越到簇区域（范本 §三的干线下界 `ceil(簇货量/C)` 不变），
只是多了一次装卸与一个跨重规划的状态维度。**净效果 = 0 距离收益 + 更多状态**。

**R3（对"绝不更差"的反驳）**不加取优守卫时，"有货就用"**实测更差**。
范本 §2.4(b)：期初存满一个载重时，距离 **179.6 vs 直达 178.2**、penalty **193 vs 166**。
本对话探针 C 也独立复现了同构现象：20 个组合中有 3 个"经站"比"经仓库"更远（最多 −10 km，即使用站是倒贴）。
→ 用户"绝不会更差"的**论证**（顺路 ⇒ 零成本 ⇒ 不会更差）在逻辑上是断的：
顺路只保证"不绕路"，不保证"取用站里那批货不会让别的客户/别的趟变差"。

**R4（对"积少成多"的反驳，第一手文本）**库存要"攒得住"，只能靠**看不见的额外供给**。
历史实现自己的测试 `testOnboardSurplusIsBankedEnRoute`（`git show 0b56315:tests/routeplanner_tests.cpp`）
写着这段语义断言：

> 「寄存后站里那 20kg 是**不记名库存**，不再绑定 D2；D2 仍按正常流程被服务（从仓库装货）。
>  所以「D2 被送达」与「站里留 20kg」同时成立是**设计意图**（库存由仓库额外供给），不是重复计数。」

即：为了"积少成多"，同一批货被**同时**记为"已送达"与"站内库存"——这是**凭空多出的货**。
在"订单 = 唯一货量来源"的模型里，这条语义不守恒，也正是库存**单调膨胀**的来源。

**R5（最坏情况代价）**做这件事的最坏结果不是"白干"，而是**把已经修好的缺陷类别请回来**：
`docs/设计.md` §16 P25 记录，停车在站里会排出「站 → 仓库 → 站」的补货趟，造成车在仓库附近来回跳；
用**计划反推物理事实**这一根因曾导致「车在 28 tick 内不回仓库却送完 17 站」「载重 200kg 的车送 740kg 货」。
恢复库存 = 恢复第二份物理事实，与 P25 的"唯一状态源"规则正面冲突。
**量化代价**：≈ src +820/−320、tests +630/−160；回退 P25/P12 的两条用户裁定；
且默认数据上收益实测为 0（P1 否证）~ 上界 3–9 km（P3，需假设有货）。

**R6（成本-收益比）**即便按最有利的口径取范本 §2.4 的最好一格（每站期初 C/2）：
距离 178.2 → **175.3**（**−1.6%**）、耗时 −19.2 min、成本 −1.9 元、penalty −3，但**趟数 6 → 10（+67%）**。
即"用 4 趟换 1.6% 里程"。而本提案要拿到这一格，还得先解决 P1（没有货）与 R4（货从哪来）。

## 【第二轮】用户精化版：装满 200 出仓 + 只放"回程本来就经过"的站

> 本轮起因：用户指出第一轮我反驳得太重。核对后**承认两点**，但结论不变，理由换到更精确的位置。

### 用户精化的要点（原话）

> 现在的逻辑的每次出仓只携带刚好够本趟需要派送的货物，**比如这一趟总派送量仅有 160 但我还是 200 出仓**。
> 按正常流程派送完 160 后就会发现车内还剩余 40。而对于我说的顺路，是**在不改变本来规划的回程路线**的情况下：
> 如果本来配送完这一趟最后一个客户不会经过任何中转站就回到仓库，那就载着这 40 回仓库。
> 但如果回程的路上恰好经过中转站，便将身上的 40 留在经过的中转站中，载着 0 回仓库。
> 以上两点证明实施该方案无成本（**所有路线都没有改变，变了的数据只有载货量**），从而推断永远不更差。

### 我承认的两点（第一轮说得过重，此处更正）

| 用户主张 | 核对结论 | 证据 |
|---|---|---|
| 「装满 200 出仓」不改变任何路线 | **成立** | 核心层 `loadKg` **0 处**参与选路/分批/趟次决策（第一轮 A2 全量检索）；装载量只被记录 |
| 「回程顺路放货」零成本 | **成立**，前提是该站恰好落在回程最短路线上 | 路线不新增节点；停靠**无服务时间**（`66e282e` 已按用户要求移除）⇒ 距离/耗时/成本/penalty 全不变 |

→ 第一轮我写的「返程盈余恒为 0 ⇒ 无货可寄存」，**只对"默认装载规则"成立，对"强制装满"不成立**。
用户说得对：**装满是可以在不改变任何路线的前提下多带货的**。这一点更正，并承认"生产端零成本"成立。

### 但"永远不更差"仍不成立——缺口在**消费端**（本轮实测 D1）

那 40kg 属于某张订单，最终必须送到客户手上。于是只有两条分支：

**(a) 由后续的普通趟从站里取走 → 路线会改（用户的证明未覆盖这一步）。实测代价：**

```
D01(簇1,T01): 直达 1.90km, 经站 8.30km, +6.40km     D13(簇2,T02): 直达 10.80, 经站 11.50, +0.70
D02(簇1,T01): 直达 3.30km, 经站 7.50km, +4.20km     D17(簇3,T03): 直达 11.70, 经站 12.60, +0.90
D03(簇1,T01): 直达 5.00km, 经站 7.10km, +2.10km
D05(簇2,T02): 直达 6.60km, 经站 16.60km, +10.00km
D06(簇2,T02): 直达 8.40km, 经站 18.40km, +10.00km
D09(簇2,T02): 直达 8.10km, 经站 10.40km, +2.30km
  >> 更差客户 8 个 / 等距 17 个 / 更好 0 个；最差 D05 经 T02 多跑 +10.00km
```

**25 个客户里 8 个更差（最多 +10.0km）、17 个等距、0 个更好。**
即"从站里取货再送客户"**永不比从仓库直达更省**（最短路的下界），只会更贵。
要让它"不更差"，必须再加**两版取优**（把两版都算出来取优者）——
那正是 P30 判定为"参数完全相同的空转调用"而删掉的东西。

**(b) 只留给紧急订单取用（不喂给普通趟）→ 账不平。**

### 而且"积少成多"在**零改路线**约束下几乎不发生（本轮实测 D2）

判据：某趟可寄存量 = `min(本趟空位, 本簇后续趟尚未上车的货)`，且回程须**零绕路**经过本簇站。

```
[distance] 第1趟 空位 10.00kg，本簇(簇1)后续未上车货 72.00kg -> 顺路寄存 10.00kg 于 T01
           策略结束时站内累计库存 = 10.00 kg
[time]     同上 = 10.00 kg
[cost]     第1趟 寄存 10.00kg 于 T01；第3趟 空位 4.00kg -> 寄存 4.00kg 于 T03
           策略结束时站内累计库存 = 14.00 kg
```

**默认数据上三策略的库存总量只有 10 / 10 / 14 kg**——不是"积少成多"。原因是可核的结构性事实：

1. 空位大的趟（第 2/4/6 趟，空位 128/138/158kg）**恰好都是本簇的最后一趟**——本簇再没有"后续未上车的货"可拿来填，可寄存量 = **0**；
2. 有"后续货"的趟（第 1/3 趟）**已被贪心装箱填到接近满载**（190/196）——空位只有 **10kg / 4kg**；
3. 两条同时成立，逼出结论：**在"不改路线 + 只放本簇货"的约束下，能攒的量被贪心装箱压到个位数公斤。**

要攒得多，只有两条路，而两条都破坏前提：
- 改装箱/改路线 → 落回分支 (a)，付 D1 的绕路代价；
- 放**别簇**的货去填空位 → 余货卸在错误站，即范本 §二的可复现反例（**+90% 里程、多一趟**）。

### 综合：(a)(b) 两条都不通

| 分支 | 距离代价 | 账是否平 | 能否给紧急单留货 |
|---|---|---|---|
| **(a) 后续普通趟从站里取** | 8/25 客户更差（≤ +10km），**0 个更好** | 平 | **不能**：取走就空了；能留下的只有那 10/14kg |
| **(b) 只留给紧急单取用** | 0（路线不变） | **不平**：站里那批货的客户仍需从仓库整份发货 ⇒ 同一批货被发两次 | 能，但只有 10/14kg；且**无紧急单时永久趴账** |

> **「不改路线」与「攒得住」不可兼得。**前者把可寄存量压到个位数公斤；
> 要把量做大，就必须改路线（在 (a) 付代价）或让账不平（在 (b) 违背守恒）。
> 这正是 P25 移除该机制的本质：*「寄存的货再无取用路径，只会在车上↔站里空转，库存单调膨胀（实测 870kg）」*。
> （D2 的静态计划算出 10–14kg；P25 的 870kg 出现在**动态连续重规划**下——而那种模式里"路线不变"的前提本来也不成立。）

### 收益侧（沿用第一轮实测 C，未变）

即便站里恰好有那 10/14kg：20 个（时刻 × 目标）组合里只有 7 个收益上界 > 0（3.0–9.4km），
最大 20km 出现在**车恰好停在中转站里**；还有 3 个组合为负。
且这要求库存恰好属于紧急单所在簇——而 D2 的 10kg 全部在 T01（簇 1）。

## 【第三轮】用户再精化：库存**只**服务紧急单 + "先看车上现成载货"

### 用户对本轮的关键修改（原话要点）

> 这些顺路放在中转站中的盈余货物**肯定不是给常规订单使用的**。只有在出现紧急订单时……要优先去送紧急订单。
> 车辆**先判断自身现有载货能不能满足**这个紧急订单……如果发现自身载货不能满足，则先查看是否能通过去中继站
> 收集之前留下的盈余货物以补充自己载货……若还是不能满足，那只好像现在一样回仓库补货再来送。
> 总体来说放在中转站的货物就是一个应对紧急订单的手段，将其视为一个**仅为紧急订单服务的前置仓库**。

拆成三条处置链：**M1（车上现成货）→ M2（站内库存）→ M3（回仓库，现状兜底）**。

### 我承认的（第三轮更正）

1. 用户把"站只在紧急单时被用"写死 ⇒ **常规排线不含站，路线不变**。
   第一轮 D1 的"+10km/客户"针对的是"后续普通趟从站里取货"这条分支，**在该设计下不再适用**，我撤回它对这个设计版本的适用性。
2. **M1 不需要中转站、也不需要新状态**：车上现成的货 GUI 侧已由 `VehicleState.onboard` 跟踪
   （`onboardGoods()` 喂给 `replan`/`insertUrgentOrder`），所以 M1 的实现代价远低于 M2。

### 新实测 E：M1 的乐观上界（车上货直接满足紧急单）

判据：`现状代价(insertUrgentOrder 的 Δ距离)` vs `M1 乐观上界代价(把紧急点插进"当前这趟"最便宜的相邻边之间)`，
单位 km；**乐观 = 忽略"被借货客户被推迟到后续趟"的代价**（这一项本轮没测，见下）。

```

   ->D08: 现状 +12.0km | M1上界 0.0km | 可省 12.0km     <- 紧急点本来就在在途趟路线里
   ->D10: 现状 +13.4km | M1上界 0.0km | 可省 13.4km
   ->D20: 现状 +21.8km | M1上界 18.0km| 可省  3.8km
```

两条读法：
- **M1 可行且有量**：车上现成货 **20–190kg**、单项最小 **20kg** ≥ 紧急单需求 **3–10kg**（实测列）；
  乐观上界可省 **10–23km**，20 组里 15 组可省。
- 本轮实测中 **M1 从不需要 M2 兜底**——"车上货不够满足 3–10kg 紧急单"这个情形在默认数据上一次都没出现。

### 同一实验暴露的更值钱的发现：紧急单的高代价**主要是规划策略，不是物理必然**

**时刻 8:30，车就停在仓库（W01），紧急单目标 D08 本来就在当前这趟的路线里 —— 但 `insertUrgentOrder` 仍要多跑 +12.0km。**
原因在 `RoutePlanner.cpp:297-349`：紧急订单一律被摘成**独立批次**，且 `weave(...)` 的 `pickupNode` 被写成
`vehicle.startNodeId` ⇒ **强制回仓库装货**，于是每张紧急单至少多出一趟 `仓库→紧急点→仓库`。
当紧急点本来就在在途趟的路线里、车又在仓库附近时，这个往返是**纯浪费**（实测 12.0km / 单）。

> **这是本轮最重要的线索**：用户要解决的"紧急单极大增加距离"，其大头可能不需要任何中转站就能收回——
> 只要允许"紧急单并入在途趟"与"独立紧急趟"**两版取优**。
> 但这一条的完整验证（两版都算、比全局距离/penalty、并检查紧急单是否仍被优先满足）**我本轮没做**，
> 原因见下节——它的完整评估属于**另一个提案**，不在用户这次的"中转站暂存"范围内。

### M2（站内前库存）在用户新规则下的量化结论

- **可寄存量**：**10kg（distance）/ 10kg（time）/ 14kg（cost）**，且全部落在 **T01**（第二轮 D2 实测）。
  用户新规则下它不进常规排线，所以它只能服务"**簇 1 的紧急单**"。
- **它填的正是 M1 的缺口**（车上货不满足时），但如上所述 **M1 在默认数据上从未需要它兜底**。
- **账**：库存的货属于常规客户，而这些客户按用户规则**仍从仓库发货** ⇒ 只有被紧急单真正取用时才守恒；
  默认数据 25 单全非紧急 ⇒ 那 10–14kg **永久趴账**（与 P25 的 870kg 同源；P25 记录 *"寄存的货再无取用路径，只会在车上↔站里空转"*）。
- 结论：**M2 是给 M1 打的一个 10–14kg 的补丁，而 M1 一次都没用上它**；却要付出库存状态、装载规则、寄存记账、
  跨重规划延续、GUI 列与测试的全部代价（≈ 第一/二轮估算的 +820/−320 src）。

## 结论：**不做（维持现状 = 方案 A / D23）**

> **第三轮修订**：本轮的结论要分成两半说清楚，因为 M1 与 M2 的处境完全不同。
>
> **① M2（中转站暂存/前置库存）：不做。** 维持 D23。新证据：
> 它只能提供 **10–14kg**（且只在 T01）、只服务簇 1 的紧急单；而它要补的缺口（车上货不够）**实测从未出现**；
> 默认数据下这 10–14kg 没有消费者、永久趴账（P25 同源）。
> **代价 ≈ 整个库存机制，收益 ≈ 一次紧急单省几公里且要看运气。**
>
> **② M1（车上现成货优先满足紧急单）：再议——它是本提案里唯一值得做的部分，而且不需要中转站。**
> 实测乐观上界可省 10–23km（20 组中 15 组），可行性无争议（车上单项最小 20kg ≥ 紧急单 3–10kg）。
> **决定性未知量 = "被借货的客户被推迟到后续趟"的代价**，本轮没测（要改规划器，本对话边界不允许）。
> 这一项必须实测后才能判"做/不做"，因此**本次不给 M1 出实现规格**。
>
> **③ 顺带发现（比 M1/M2 都直接）：紧急单的代价大头是"强制独立成趟 + 强制回仓库"这一策略**，
> 实测在"车停在仓库、紧急点已在路线里"时仍多花 **12.0km**。
> 若用户的目标就是"压紧急单的距离"，**这条线比中转站更该先试**（需要另一次商议与两版取优的量测）。


> **第二轮修订说明**：第一轮把「P1 返程无盈余」当作核心否证，**这条在本轮被更正**——
> 强制装满确实能在不改路线的前提下多带 40kg，用户这一点是对的。
> 但结论不变，否证点从"生产端"移到"**消费端 + 攒不住的量**"：
> 装满攒出的库存，在默认数据上只有 **10–14kg**（D2），
> 而要用掉它就必须改路线、付 **最多 +10km/客户** 的代价（D1），或让账不平（R4）。
> 用户证明的是"生产端零成本"；"永远不更差"还需要**消费端**也零成本，而后者实测为 0 收益 / 有代价。


代价与理由（按权重排序）：

1. **提案的三个前提被否证两个、第三个只部分成立**：
   P1「返程有盈余」→ **实测 0 kg**（3 策略 × 6 趟），且"满载"本身对结果**零影响**（核心层 0 处决策点）；
   P2「顺路零成本」→ **实测 4/6 趟成立**，2/6 需绕路（最多 +10 km）；
   P3 的收益上界 → **多数时刻为 0**，最好一格 -1.6% 里程却换来趟数 +67%；
   唯一的 20 km 级收益出现在"车恰好停在中转站里"，这不是机制带来的，是位置巧合。
2. **用户观察到的真问题是真的**（紧急单典型 +12~+30 km/单，实测），
   但"用站内库存解决"在**逐边计费、单车单库、订单即唯一货量**的模型下不成立：
   货仍须从仓库跨越过去（范本 §三的下界），站内库存只能**把成本提前**，不能**消除**它；
   而"攒得住"的库存必然凭空产生（R4）。
3. **代价显著且会回退已修好的东西**：≈ +820/−320 src + 630/−160 tests；
   与 D23 直接冲突，与 P25 的单一物理源规则**实现上互斥**；守卫目前是"结构保证"，
   恢复实现必须连同断言一起恢复（否则静默失效）。
4. **不做也有正当说法**：报告里按 §5.6 的"效率诚实说明"写"实现了、实测否证、依裁定移除、附可复现证据"，
   比勉强实现更站得住（范本 §5 已确立这个口径）。

**若用户/教师明确要求提高字面符合度**，范本 §5 已给出**更便宜的替代路径**（仍不做集散链）：
只做"配置给定期初库存 + 两版取优 + penalty 一票否决"的最小实现，
默认配置库存为 0（黄金值不变）+ 另备演示配置。
**但本对话实测表明该路径在默认数据上收益为 0**（P1 否证：没有生产者就没有库存），
所以它只是"字面符合度"的动作，不是"效率改进"的动作——**要按这个目的去买，不要按收益去买**。

## 【第四轮】用户澄清"没有借货"——机制的每个环节都对上了，剩下一个**建模前提**待你裁定

### 用户澄清（原话要点）

> 从来没有涉及到借货，一开始检测车上载货是否满足也只是**检测盈余部分**是否满足紧急订单，这样**不打乱一开始设计好的趟次**。
> 而发现盈余部分不够满足紧急订单时，去该紧急配送点的**上属中转站**收集货，这样就可能出现收集完后**就地满足**紧急订单
> 而不需要回仓库的情况。举例：本趟常规用货 196、盈余 4；某中转站已存 10；出现一个目标为该站下属配送点的紧急订单、需求 12；
> 4 不够，但车可先去站里收集 8 把自己的盈余变成 12，**无需回仓库就完成一次紧急配送**。

**这条澄清使机制的每一环都自洽**（我核对后确认）：

| 环节 | 核对 |
|---|---|
| 只用**盈余**，不动本趟要送的货 | 成立：不改变任何已计划客户的服务顺序/趟次 |
| 盈余不足 → 去**该紧急点的上属站**补足 | 成立：站由 `sub_network_id` 确定（`RoutePlanner.cpp:290-295`） |
| 补贴后就地送达 | 成立：`weave` 已支持"从当前位置出发、途经点装载" |
| 站只在紧急单时被用 | **把第一/二轮 D1 的"+10km/客户"整条反驳消掉了** —— 常规趟不进站，路线不变。**撤回对本文档该设计版本的适用** |

### F1（分水岭实测）：所谓"盈余货物"，**它是谁的货**？决定了机制能攒 10kg 还是 434kg

| 读法 | 含义 | distance / time / cost 站内总量（默认数据静态规划） |
|---|---|---|
| **读法 1** | 盈余只能是"**本簇后续趟尚未上车的货**"（模型里唯一存在的货） | **10 / 10 / 14 kg**（T01=10；cost 另加 T03=4） |
| **读法 2** | 仓库可发出"**不属于任何订单的缓冲货**"（= 不记名库存；历史实现的真实口径） | **434 / 434 / 438 kg**（T01=138 / T02=158 / T03=138） |

```
[distance] 读法1 站内总量 = 10kg  明细: T01=10 T02=0 T03=0
          读法2 站内总量 = 434kg 明细: T01=138 T02=158 T03=138
[time]     读法1 = 10kg     读法2 = 434kg
[cost]     读法1 = 14kg     读法2 = 438kg
```

**为什么差这么远**：读法 1 下，能填空位的货必须来自"本簇后续趟"；而空位大的趟（第 2/4/6 趟，空位 128/138/158kg）
**恰好都是各簇最后一趟**——本簇再没有后续货，于是可寄存量归零；有空位又有后续货的只有第 1/3 趟（空位 10/4kg）。
读法 2 下没有这个约束，**每趟的空位都能装满**，故是 434kg 级。

> **口径警告（诚实声明）**：F1 量的是**静态规划**。在 GUI 的**动态连续重规划**下（用户实际观察的场景），
> 每次重规划都会重新产生空位与"后续货"，历史实现因此累积到 **870kg**（P25 记录）。
> 所以 **10–14kg 是静态规划的下界，不是动态场景的上界。**

### F2（实测）：直接实例化你的例子——站方案对一次紧急单能省多少

```
                     ->D10: 现状 +13.4km, 站方案 +0.8km => 省 12.6km
```
