2. 表 1 · 存储与配置层（结构本体 + 承载它的记录）

结构 是什么 为什么是它（排除谁 / 依据） 特点与复杂度（前提） 没有它得自己写什么 连接：谁喂它 → 它 → 谁消费 代价与坑
IniFile·IniSection·IniRecordINI 文本 → 带行号的记录序列（节 → 记录）解析错误必须报行号 ⇒ 记录自带 lineNo，而且 findValue 返回记录本体而非值（报错时才带得上行号）；节数与记录数都很小（[general] 8 行）⇒ 顺序 vector 足够，不必建键索引parse O(L)（L = 总行数）；findSection O(节数)；findValue O(r)（r = 该节记录数）逐行扫描 + 手维护一张「值 → 行号」旁表config/default.ini → IniFile::parse → IniSection/IniRecord → ConfigLoader::load只认 # 注释；重复节名直接失败；不做语义校验（语义都在 ConfigLoader）
Config一次加载的完整结果：图 + 车辆 + 订单 + 全局参数把「文件里的四类数据」收成一个值对象，规划器与界面只依赖它、不依赖 INI 形状；事件等级与间隔集中在 GeneralConfig，权重由 eventLevelWeight 一处派生（配置里不写权重数字）O(n + m + 订单数) 空间；纯数据、无方法ConfigLoader 要回传 4 个出参，或每个调用点自己再解析一遍ConfigLoader::load → Config → replan（GUI 入口）/ planRoute（CLI --plan-summary、自检与测试入口）/ MainWindow 按值持有事件参数只剩 event_interval_min（旧的真实秒级字段已删除）；Config::graph 是值，不是引用
LogisticsGraph有向带权图：nodes_ 顺序表 + out_ 邻接表，两者下标严格对齐图是稀疏的（30 节点 / 106 有向边）⇒ 邻接矩阵 900 格绝大多数为空、而每格还要塞 3 个权重；下标对齐让「节点 i 的出边」是 O(1)，Dijkstra 不必每步筛边n、m、deg：indexOf O(n)（线性扫，无 ID→索引映射）；findEdge O(deg)；addNode O(n)；removeNode O(n+m)（入边散落在别人的出边表里）；空间 O(n+m)Dijkstra 每轮自己从边表里筛边（每次 O(m)），或另建一份邻接结构ConfigLoader 装配 → Dijkstra 只读 adjacency()、io 输出邻接表/邻接矩阵 → Traffic/GraphEdit 就地改 → GUI 只读遍历没有反向邻接表 ⇒ 删点 O(n+m)；indexOf 是 O(n)（源码注明「节点数很小（30 量级），不为它引入索引结构」）；**不提供可写 Edge***，防调用方改坏 fromId 等不变量
Node·Edge（记录）图的两条记录类型；Edge 携带三权重（距离/耗时/成本）+ baseTimeMin + congested三权重并存才能「同一张图、三套策略」（pickWeight 只换维度）；baseTimeMin 单列出来，是因为路况判定要「相对基准的增幅」，而 timeMin 会被就地改写 ⇒ 没有基准就无法判断「畅通」定长 O(1)；findEdge(from,to) O(deg)想把耗时还原成「畅通」就得另存一张初始耗时表，并与图永远保持同步ConfigLoader 构造 → LogisticsGraph::out_ → Dijkstra 松弛 / Traffic::simulateTrafficChange 改 timeMin / GUI 画箭头updateEdgeTime 只改 timeMin，congested 由「是否高于 baseTimeMin」自动维护；Node::x/y 只供 GUI 布局，不参与权重计算

3. 表 2 · 手写算法层（「手写算法、不手写轮子」的落点）

结构 是什么 为什么是它（排除谁 / 依据） 特点与复杂度（前提） 没有它得自己写什么 连接：谁喂它 → 它 → 谁消费 代价与坑
MinHeap手写二叉最小堆，元素固定为 Entry{key:double, value:int}（底层 std::vector）课程硬性要求堆自写（禁 std::priority_queue·make_heap）；不做成模板，是因为全项目只有 Dijkstra 一处用、元素类型固定为（权重, 节点下标），模板只会加噪音s = 堆内条目数：push/popMin 各 O(log s)；siftUp/siftDown/swapEntries 全自写（不引 <algorithm>）；空堆 popMin 返回 false 且不改出参Dijkstra 每轮取最小扫一遍 dist[]（O(n)）——n=30 时同阶，所以这里的收益是考点，不是运行时提速Dijkstra::shortestPath → push（松弛成功）/ popMin（取当前最近）没有 decrease-key ⇒ 同一节点会留下过期条目（堆条目 ≤ m），靠弹出时 currentDist > dist[current] 惰性删除（源码注明：去掉该守卫结果不变，属性能优化）
Dijkstra::shortestPath + dist[]·previous[]单源单目标最短路：距离数组 + 前驱数组 + 惰性删除堆三种策略共用这一份实现，只在 pickWeight(Distance/Time/Cost) 换权重来源 ⇒ 不是三套算法；用前驱数组复原路径，而不是让堆条目携带整条路径n、m、s：dist/previous 各 O(n)；时间 O(m·n + m·log m)（每条边一次松弛，松弛内层的 graph.indexOf 是 O(n)）；路径复原 O(路径节点数)；起点=终点返回单元素路径、权重 0把前驱数组换成「堆里带路径」会让每次松弛多 O(n)；三套策略要写三遍LogisticsGraph::adjacency() → shortestPath → PathResult{nodes, totalWeight} → 两个调用点：CostMatrix::build（全源预计算）与 traffic_tests 的直接断言不可达时 found=false 且 nodes 为空；kInfinity=1e100 只是哨兵；无 decrease-key 是设计，不是缺陷
CostMatrix（+ scaledWeight）全源最短路预计算：V×V×3 三张表（按距离/耗时/成本各自最优路径的三项指标）pair-insertion 每次评价要查大量 (站→站) leg，逐个调 Dijkstra 会让「一个候选 = 一次最短路」变成主开销 ⇒ 一次建表、之后 O(1) 查；同时把车辆因子收在一处（耗时×timeFactor、成本×costFactor）建表 ≈ O(V·(m·n + m log m))；查询 legAll O(1)；空间 V²×3每个候选位置对都现算最短路（数量级 ×n² 次），或缓存一份自己维护的旁表Ctx.matrix.build(graph) → tryInsertPair/replay/repairRoute 的每次 leg 查询表按基础图建、因子在查询处乘 —— 路况改边后必须重建（makeCtx 每次规划都重建）
tryInsertPair + replay + compareRoutes（pair-insertion）把一张订单的 (A,B) 对插到普通段最省的位置：枚举全部位置对、逐个重放评价、取键最小规格一 #18 的构造器：penalty 先的 cheapest insertion，取代「贪心选最近邻」——最近邻会在紧窗单上迟到（testPairInsertionBeatsNearestNeighbourOnTightWindow）；同节点并入既有停靠以减少停靠数单请求 = O(n²) 位置对 × O(n) 重放 = O(n³)；m_task 张单 ⇒ O(m_task·n³)；replay 里同时判 F1–F7（不可行立即剪掉）自己写「每个位置合不合法、代价多少」的评价器；写时间/载重/penalty 的推进Request + StopSpec[] → tryInsertPair → replay/Eval → compareRoutes（三键）→ 采用或进入兜底键序 = (Σpenalty, 策略权重, tieKey)，载重峰值不进键；耗时维权重含早到等待（否则「最短耗时」策略会输出更长总耗时，设计 §4.7-②）
buildAll（多起点 + 两级兜底 + 降载）构造总调度：起点版本枚举 → 全量兜底 → 降载 → 拒绝单一 EDD 起点会让某个策略在 ② 上被反超（单起点时成本策略 168.5 元 > 距离策略 145.3 元）；多起点把「插入序」这一维也纳入搜索，仍用同一把三键取优3 个起点版本 ×（构造 + repair）≈ 3 × O(m_task·n³)；多起点只在整批构造（基地 / 空车 / 发车时刻）启用自己写「哪个起点更好」的判断、失败后的重排、降载触发insertionStarts → buildAll → Outcome{route, reason} → finalize中途重规划（replan 带在车货/非发车时刻）单起点：构造次数多、时间预算不允许；--self-check-actions 36s 量级正是这条链的代价
GraphEdit（addRandomCustomer·closeRandomRoad·makeSyntheticEdge）动态增删：随机位置插新客户、随机封一条路（双向删边）、手工加边的权重估算坐标 → 权重的换算从图自身既有边推算平均比值（estimateScale），不硬编码「坐标单位 → 公里」⇒ 不与数据集尺度脱钩；封路前用 BFS 检查「封了以后还连不通」，不封桥 ⇒ 不会把一片区域变成孤岛estimateScale O(m)；reachesSkipping 手写 BFS，队列用 vector + 游标、seen 线性查找 ⇒ O(n·(n+m)) 量级；addRandomCustomer 找最近既有节点 O(n)自己写「最近点 + 双向连边 + 权重估算 + 连通性检查」事件分派 → GraphEdit → LogisticsGraph::addNode/addEdge/removeEdge → 图变了，后续规划在新图上跑seen 是线性查找而不是 set（节点量小）；封路是双向删边，在含单向边的图里反向边本就可能不存在；makeSyntheticEdge 在坐标重合时返回 false；addRandomCustomer 建边失败会回滚删点
SimEvent（nextEventTimeMin·pickEvent·EventWeights）+ Rng软件内时间的事件模型：每 intervalMin 一个事件刻、每刻恰抽 1 个事件，四类权重由等级派生（默认 27:3:9:1，Σ=40）两个独立理由，别混：①用软件内时钟而不是真实定时器／推进计数，是为了「推进粒度不影响事件串」（D24）；②手写 xorshift32 而不是 <random>，是可复现性选择（同种子必得同序列，测试能逐值断言不 flaky），不是因为 STL 被禁pickEvent 单次 O(4) 前缀扫描（不预先算总和再赌一次）；nextEventTimeMin O(1) 且严格大于 now；Rng 每步 3 次移位异或 O(1)自己写加权抽签、全零权重的兜底、事件刻对齐GeneralConfig（权重 + 间隔）→ nextEventTimeMin + pickEvent → GUI 事件分派 → Traffic / insertUrgentOrder / GraphEdit权重 ≤ 0 的种类永不被抽中（写 0 再问「为什么不出现」是误用）；全零时保底 Traffic 且仍消耗一次随机数（契约：一次抽签 = 一次 rng 消耗，否则两条路径的事件串会错位）；intervalMin <= 0 返回 nowMin + 1
simulateTrafficChange·TrafficChange·TrafficReport·needsReplan一次路况变化中被改动的边清单（增幅 + 畅通/拥堵），以及「要不要重算」的判定把「这次改了什么」落成可审的数据——因为触发判定要问「受影响的边是否恰在当前路线的相邻两站之间」；增幅每次重设为 baseTimeMin×(1+ratio) 而不是在原值上叠加 ⇒ 耗时不会逐次失控增长，baseTimeMin 永远是基准count = 改动边数（默认 round(0.1×106) = 11）：选边用部分 Fisher-Yates O(count)（只需前 count 个位置被打乱，全排列是浪费）；needsReplan O(count × 路线长度)分不清「改了但不在我路上」和「改在我必经段上」，只能每次事件都全量重算simulateTrafficChange → LogisticsGraph::updateEdgeTime（就地改 timeMin）→ TrafficReport → needsReplan / replanIncremental(report)只有「增幅 ≥ 阈值 且恰在路线相邻两站」才触发（畅通变更 increaseRatio=0，永不触发）；needsReplan 与 GUI 高亮共用 isEdgeOnRoute 同一条逻辑

4. 表 3 · 调度状态层（被算法承载、被界面消费的记录）

结构 是什么 为什么是它（排除谁 / 依据） 特点与复杂度（前提） 没有它得自己写什么 连接：谁喂它 → 它 → 谁消费 代价与坑
Request + StopSpec（构造期，匿名命名空间）Request = 一张订单的取送请求（A/B/kg/逐单窗口/已取/在站）；StopSpec = 规划中间态的一次停靠（四个动作列表 + 阶段）构造期要频繁「插入/摘除/比较」，用轻量描述而不是最终 Stop（后者带时刻与明细）⇒ 候选评价不必构造 O(n) 个明细对象；Request 让「按订单记账」成为唯一口径StopSpec O(动作数)；比较时按需生成排序后的动作 ID 列表（手写插入排序）用最终 Stop 做候选 ⇒ 每次评价都构造明细，数十万次评价里成为最大开销makeCtx（Order→Request）→ tryInsertPair/repairRoute 改 StopSpec[] → finalize 转成 Stop[]StopSpec 不导出；Request.alreadyPicked/inStash 决定本次要不要生成取货动作
Stop一次停靠的动作集 + 时刻 + 在车量：deliveries[]{orderId, late, penaltyMin} / pickups[] / offloads[] / reclaims[] / phase / rawArrivalMin/waitMin/arrivalMin / late/penaltyMin（聚合）/ remainingLoadKg动作集是真源：GUI 的 onAdvanceStop 完全按它做状态转移，不再有「趟」可反查；逐单窗口要求每张送达单带自己的 late/penalty；停靠零耗时 ⇒ 没有「离开时间」字段定长 O(动作数)；停靠内先卸后装，峰值取「卸后/装后」较大者；remainingLoadKg = 到达在车 − 送达 − 降载 + 取货 + 取回界面与汇总各自重算等待/罚时（口径必漂）；或维护「订单→停靠」反查表finalize 生成 → RoutePlan::stops（真源）→ 停靠明细 / 超时订单面板 / RouteMetricslate/penaltyMin 是停靠级聚合，别拿它代替逐单（逐单真源是 deliveries[] 与 metrics.orders）
RouteMetrics + OrderMetric摘要与验收口径：S / A / 逐单 penalty 与准时 / 取货准时率 / 送达准时率（总·紧急·普通）/ 平均在车 / 利用率 / 峰值--plan-summary 的四行与 13 字段要落到可断言的结构上，而不是在渲染处现算；取货准时判据 t_pick + 最短耗时(A→B)×timeFactor ≤ we 必须与规划同口径O(订单数)；平均在车 = Σ(段在车量 × 段时长) / 总运行时长（含首末空驶段）各处渲染时各算一遍，口径必然分叉（G4 的「取货准时率 ≥ 送达准时率」也守不住）finalize 汇总 → RouteMetrics → --plan-summary / 路线信息面板 / 黄金值断言分母 0 的率打印 —（不是 0%）；峰值载重不进构造键，只作指标
RoutePlan（+ PlanStatus）一次规划的完整结果：stops（真源）+ offloads（custody）+ metrics + 由 stops 一次展平的 nodes/nodeArrivalMin/nodeIsStop + 汇总（距离/耗时/成本/penalty/回程时刻）真源只有一份（stops），扁平字段是兼容视图且只在一处生成 ⇒ 两套数据不会各自走样；界面按下标推进，扁平序列比「在结构里找第几个节点」直接空间 O(节点数 + 停靠数)；展平 O(节点数 + 停靠数)；失败用 PlanStatus{Ok, OrderExceedsCapacity, Unreachable} + reason调用方自己维护「路线」与「整条节点序列」两份数据并保持同步replan/planRoute/insertOrder/replanIncremental 产出 → GUI 推进与高亮 / sliceRemainder 切剩余plan.nodes 为空时 nodeIndexAtTime 返回 0（调用方判空）；totalTimeMin 用未取整的 elapsed 算
finalize（展平点）把 stops 展平成 nodes/nodeArrivalMin/nodeIsStop，并汇总指标与 custody唯一生成点：任何出口都只在这里生成视图，忘一处就拿到旧视图；同一节点可能多次出现（途经 / 强制重访 / 回站），nodeIsStop 只标记「作为停靠的那一次」O(节点数 + 停靠数)；在所有规划出口各调一次每个消费者各自展平一遍，视图立刻与 stops 走样RoutePlan::stops → finalize → 扁平字段 → GUI 推进 / isEdgeOnRoute / sliceRemaindernodeIsStop 与 nodes 必须等长；sliceRemainder 切剩余时停靠按 nodeIsStop 下标对齐取
OnboardItem车辆此刻已在车上的货（nodeId, kg, orderId）重规划若不知道「车非空」，规划器会假设货都在起点 ⇒ 每次重算都先跑回基地（P17 实测）；按订单记账是因为同节点多单下按 nodeId 扣货会把别的单一起扣掉（issue #5）O(在途单数)重规划出来的每一段都可能先回基地，与车的物理事实脱节GUI 从当前 RoutePlan 推出在途货 → replan/insertOrder/replanIncremental → Ctx.onboard → replay 初始在车量必须与 StashState 一起传；漏传会让在车货被当成「还没取」而重复生成取货动作
OffloadLeg · StashState降载 custody 记录（站 / 单 / 送达点 / kg / 卸下时刻 / 取回时刻）与跨重规划暂存（站 + OnboardItem[]）「同车卸、同车取」必须有账可审：暂存守恒（Σ卸入 − Σ取回）、期末 0、取回先于该单送达，全靠它；与转运分型——判据就是「卸入车 == 取走车 ⇒ 降载」OffloadLeg O(降载单数)；选站对每座中转站构造一次降载版路线，一经选定即锁站单堆；StashState 透传 O(暂存单数)从行程序列反推「哪张单在哪卸、还要回哪取」，守恒无从断言、界面也画不出「当前暂存货(kg)」insertOffloadStop/insertReclaimStop → Stop.offloads/reclaims + RoutePlan.offloads → 面板与守恒断言；GUI 把 StashState 透传 replanIncremental不主动为「更优」进站；只卸整张普通单、绝不卸紧急货、不卸 A/B 目的地的货；锁站不可达 ⇒ 全量兜底，仍不行 ⇒ 拒绝该单
