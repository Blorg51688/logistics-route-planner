# 项目速懂（图版）

> 一眼看懂整个项目怎么跑。**深度内容不在这里**——完整版（562 行，含追问答法、D23 细节）见
> [`项目速懂-详解.md`](../../docs/项目速懂-详解.md)。想看门面与常用命令 → 根目录 `README.md`；全部文档地图 → [`docs/文档导航.md`](../../docs/文档导航.md)。

**一句话**：城市物流网络建成**有向带权图**（30 节点 / 106 有向边 / 25 订单），用手写二叉堆 + Dijkstra 求三种权重下的最短路，
再用手写贪心串成配送路线；配送过程由**软件内时间**驱动四类事件，事件可触发**增量式重规划**。

---

## ① 一张图：数据怎么流

```
config/default.ini                           ← 30 节点 / 106 有向边 / 25 订单，车 200kg、08:00 发车
   │  IniFile::parse（手写解析，带行号报错）
   ▼
ConfigLoader::load  →  Config{ graph, vehicles, orders, general }
   │
   ▼
RoutePlanner::planRoute       ← 单趟贪心 / 多趟分批（总需求 740kg > 200kg ⇒ 6 趟）
   │      └─ 每选一站就调一次 Dijkstra::shortestPath（整趟约 O(k²) 次）
   ▼
RoutePlan
   ├─ trips[]          ← **真源**（趟的列表）
   └─ nodes/stops/...  ← 由 flatten() 一处展平出来的视图，不各自维护
   │
   ▼
GUI 推进：onAdvanceStop / onAdvanceMoment（逐节点，不许跳站）
   │
   ├─ 移动后必调 settleEventsUpTo(now)   ← 事件结算挂在"软件时间前进"上
   │      └─ SimEvent::nextEventTimeMin（每 15 分钟一个刻）+ pickEvent（权重 10:3:1:1）
   │
   ▼ 四类事件
   ├─ 路况    Traffic::simulateTrafficChange → needsReplan？→ replanIncremental
   ├─ 紧急单  RoutePlanner::insertUrgentOrder（两版取优，penalty 更差则否决）
   ├─ 新客户  GraphEdit::addRandomCustomer
   └─ 封路    GraphEdit::closeRandomRoad（不封桥）
   │
   ▼
syncScene()  →  路径高亮 / 拥堵标记 / 车辆位置重绘
```

**旁路**（不走 GUI、不需显示器）：`--dump-graph`、`--plan-summary`、`--self-check-actions`、`--render-window`。

## ② 一张图：路况怎么触发重规划

```
软件内时间前进（推进一站 或 推进一刻）
        │
        ▼
  过了事件刻？──否──▶ 无事发生
        │是
        ▼
  pickEvent 抽一个（路况 : 紧急单 : 新客 : 封路 = 10 : 3 : 1 : 1）
        │
        ▼ 抽到路况
  simulateTrafficChange：round(0.1 × 106) = 11 条边
     畅通 → timeMin 恢复 baseTimeMin      （增幅 0，不触发）
     拥堵 → timeMin = baseTimeMin ×(1+20%~50%)   ← baseTimeMin 永不改，是判定基准
        │
        ▼
  needsReplan：这条边在**当前路线的相邻两站之间**且增幅 ≥ 20% ？
        │                                    │否
        │是                                  └──▶ 不重算
        ▼
  replanIncremental
     把路线按停靠点切成 leg → 只重算**受影响**的 leg
     其余 leg 原样复用、停靠顺序不变
        │
        └─ 某 leg 重算失败 → 整体退回全量重算
```

## ④ 一页表：结构 → 承载什么 → 复杂度

前提：**n** = 节点数（30）、**m** = 有向边数（106）、**deg** = 某点出度、**k** = 停靠候选数（25）、**s** = 堆内条目数。

| 结构 | 承载什么 | 关键操作与复杂度 | 替代了谁 |
|---|---|---|---|
| `LogisticsGraph` | 节点表 + 邻接表 `vector<vector<Edge>> out_` | `indexOf` **O(n)**（线性扫描，无映射表）；`addNode` O(n)；`removeNode` **O(n+m)**（入边分散，要扫全部表） | 存储用容器允许；查找/遍历手写 |
| `MinHeap` | Dijkstra 取最小 | `push`/`popMin` **O(log s)**；空堆 `popMin` 返回 false 且不改出参 | `std::priority_queue` |
| `Dijkstra` | 三权重最短路 + 前驱数组复原 | `dist`/`previous` 各 O(n)；**惰性删除**使总时间 **O(m·n + m·log m)** | 松弛与堆逻辑手写 |
| `weave`（贪心串联） | 每轮选"最短路权重最小"的下一站 | 每轮 O(k) 次 Dijkstra ⇒ 整趟 **O(k²) 次**（k=25 ≈ 325 次） | `std::min_element` |
| `RoutePlan::flatten` | 把 `trips` 展平成 `nodes/stops` 视图 | O(总节点数 + 停靠数)，**只此一处生成** | — |
| `IniFile` | 手写 INI 解析，报错带行号 | 解析 O(L·S)；`findValue` O(r) | 第三方 INI 库 |

**为什么不用邻接矩阵**：n=30、m=106 是稀疏图（无向道路对仅 56），矩阵 900 格绝大多数为空，且每格要放 3 个权重。
**没有 decrease-key 怎么绕过**：松弛成功就压新条目、旧条目留着，弹出时 `currentDist > dist[current]` 就丢掉（堆条目 ≤ m）。

## ⑤ 三策略差在哪

同一份 `shortestPath`，**只在 `pickWeight` 处换维度**，没有三套算法。
数据生成时 `cost` 按**道路等级**差异化（主干道快而贵、支线慢而便宜），不是 `cost = dist × 常数`——否则"最低成本"会恒等于"最短距离"。

| 策略 | 距离 | 成本 | penalty | 趟数 |
|---|---|---|---|---|
| distance | **178.200** km | 244.200 元 | 166 | 6 |
| cost | 186.300 km | **235.900** 元 | 207 | 6 |
| time | 183.200 km | 255.200 元 | 201 | 6 |

各自在自身目标上最优，三策略都只有 D05 一个超时点。取法：`./build/app --plan-summary distance|cost|time`。
