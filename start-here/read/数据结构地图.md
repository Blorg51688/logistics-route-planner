# 数据结构地图 —— 为什么是这些结构，它们怎么连起来

> 这份文档回答四件事：**每个结构为什么用它、它的特点（含复杂度前提）、没有它得自己写什么、它跟谁连**。
> 表以「结构」为主语，不是功能清单。要看得更顺（上色的流通图）→ 同目录 [`数据结构总览.html`](数据结构总览.html)（浏览器双击打开，自包含）。
> 一句话看不懂整体怎么跑 → 先看 [`项目速懂.md`](项目速懂.md)；要完整推导与追问答法 → [`项目速懂-详解.md`](项目速懂-详解.md)。

## 0. 全文统一的前提（不写清前提的复杂度等于没写）

**n** = 节点数（当前数据 **30**）、**m** = 有向边数（**106**）、**deg** = 某节点的出度、
**k** = 停靠点候选数（≤ **25**）、**s** = 堆内条目数、**count** = 一次路况改动的边数（默认 **11**）、
**L** = 配置文本总行数、**r** = 某节的记录行数。

当前数据口径：`config/default.ini` = 2 仓库 + 3 中转站 + 25 配送点 = 30 节点；106 有向边 = 50 个双向道路对（100 条）+ **6 条单向边**；25 张订单、总需求 740kg；车 200kg、08:00 发车。

**事实来源**：`src/`（本次文档提交未改动任何源码，源码基线 = 提交 `4a23236`）+ 现有文档。文中一律用「`文件:符号名`」，不用行号（行号会漂）。

## 2. 表 1 · 存储与配置层（结构本体 + 承载它的记录）

| 结构 | 是什么 | 为什么是它（排除谁 / 依据） | 特点与复杂度（前提） | 没有它得自己写什么 | 连接：谁喂它 → 它 → 谁消费 | 代价与坑 |
|---|---|---|---|---|---|---|
| `IniFile`·`IniSection`·`IniRecord` | INI 文本 → 带行号的记录序列（节 → 记录） | 解析错误必须报行号 ⇒ 记录自带 `lineNo`，而且 `findValue` 返回**记录本体**而非值（报错时才带得上行号）；节数与记录数都很小（`[general]` 8 行）⇒ 顺序 `vector` 足够，不必建键索引 | `parse` O(L)（L = 总行数）；`findSection` O(节数)；`findValue` O(r)（r = 该节记录数） | 逐行扫描 + 手维护一张「值 → 行号」旁表 | `config/default.ini` → `IniFile::parse` → `IniSection`/`IniRecord` → `ConfigLoader::load` | 只认 `#` 注释；重复节名直接失败；不做语义校验（语义都在 `ConfigLoader`） |
| `Config` | 一次加载的完整结果：图 + 车辆 + 订单 + 全局参数 | 把「文件里的四类数据」收成一个值对象，规划器与界面只依赖它、不依赖 INI 形状；事件权重与间隔集中在 `GeneralConfig`，改配置不用改代码 | O(n + m + 订单数) 空间；纯数据、无方法 | `ConfigLoader` 要回传 4 个出参，或每个调用点自己再解析一遍 | `ConfigLoader::load` → `Config` → `RoutePlanner::planRoute` / `MainWindow` | 事件参数只剩 `event_interval_min`（旧的真实秒级字段已删除）；`Config::graph` 是**值**，不是引用 |
| `LogisticsGraph` | 有向带权图：`nodes_` 顺序表 + `out_` 邻接表，两者下标严格对齐 | 图是稀疏的（30 节点 / 106 有向边）⇒ 邻接矩阵 900 格绝大多数为空、而每格还要塞 3 个权重；下标对齐让「节点 i 的出边」是 O(1)，Dijkstra 不必每步筛边 | n、m、deg：`indexOf` **O(n)**（线性扫，无 ID→索引映射）；`findEdge` O(deg)；`addNode` O(n)；`removeNode` **O(n+m)**（入边散落在别人的出边表里）；空间 O(n+m) | Dijkstra 每轮自己从边表里筛边（每次 O(m)），或另建一份邻接结构 | `ConfigLoader` 装配 → `Dijkstra` 只读 `adjacency()`、io 输出邻接表/邻接矩阵 → `Traffic`/`GraphEdit` 就地改 → GUI 只读遍历 | 没有反向邻接表 ⇒ 删点 O(n+m)；`indexOf` 是 O(n)（源码注明「节点数很小（30 量级），不为它引入索引结构」）；**不提供可写 `Edge*`**，防调用方改坏 `fromId` 等不变量 |
| `Node`·`Edge`（记录） | 图的两条记录类型；`Edge` 携带三权重（距离/耗时/成本）+ `baseTimeMin` + `congested` | 三权重并存才能「同一张图、三套策略」（`pickWeight` 只换维度）；`baseTimeMin` 单列出来，是因为路况判定要「相对基准的增幅」，而 `timeMin` 会被就地改写 ⇒ 没有基准就无法判断「畅通」 | 定长 O(1)；`findEdge(from,to)` O(deg) | 想把耗时还原成「畅通」就得另存一张初始耗时表，并与图永远保持同步 | `ConfigLoader` 构造 → `LogisticsGraph::out_` → `Dijkstra` 松弛 / `Traffic::simulateTrafficChange` 改 `timeMin` / GUI 画箭头 | `updateEdgeTime` 只改 `timeMin`，`congested` 由「是否高于 `baseTimeMin`」自动维护；`Node::x/y` 只供 GUI 布局，不参与权重计算 |

## 3. 表 2 · 手写算法层（「手写算法、不手写轮子」的落点）

| 结构 | 是什么 | 为什么是它（排除谁 / 依据） | 特点与复杂度（前提） | 没有它得自己写什么 | 连接：谁喂它 → 它 → 谁消费 | 代价与坑 |
|---|---|---|---|---|---|---|
| `MinHeap` | 手写二叉最小堆，元素固定为 `Entry{key:double, value:int}`（底层 `std::vector`） | 课程硬性要求堆自写（禁 `std::priority_queue`·`make_heap`）；**不做成模板**，是因为全项目只有 Dijkstra 一处用、元素类型固定为（权重, 节点下标），模板只会加噪音 | s = 堆内条目数：`push`/`popMin` 各 O(log s)；`siftUp`/`siftDown`/`swapEntries` 全自写（不引 `<algorithm>`）；空堆 `popMin` 返回 false 且不改出参 | Dijkstra 每轮取最小扫一遍 `dist[]`（O(n)）——n=30 时同阶，所以这里的收益是**考点**，不是运行时提速 | `Dijkstra::shortestPath` → `push`（松弛成功）/ `popMin`（取当前最近） | **没有 decrease-key** ⇒ 同一节点会留下过期条目（堆条目 ≤ m），靠弹出时 `currentDist > dist[current]` 惰性删除（源码注明：去掉该守卫结果不变，属性能优化） |
| `Dijkstra::shortestPath` + `dist[]`·`previous[]` | 单源单目标最短路：距离数组 + 前驱数组 + 惰性删除堆 | 三种策略**共用这一份实现**，只在 `pickWeight(Distance/Time/Cost)` 换权重来源 ⇒ 不是三套算法；用前驱数组复原路径，而不是让堆条目携带整条路径 | n、m、s：`dist`/`previous` 各 O(n)；时间 **O(m·n + m·log m)**（每条边一次松弛，松弛内层的 `graph.indexOf` 是 O(n)）；路径复原 O(路径节点数)；起点=终点返回单元素路径、权重 0 | 把前驱数组换成「堆里带路径」会让每次松弛多 O(n)；三套策略要写三遍 | `LogisticsGraph::adjacency()` → `shortestPath` → `PathResult{nodes, totalWeight}` → 三个调用点：`appendLeg`（沿路走一段）、`weave`（选下一站）、`replanOneTrip`（重算受影响 leg） | 不可达时 `found=false` 且 `nodes` 为空；`kInfinity=1e100` 只是哨兵；**无 decrease-key 是设计，不是缺陷** |
| `weave`（贪心串联）+ `appendLeg` | 每轮在未服务候选里选「当前位置到它最短路权重最小」者，选完沿最短路走一段并记账 | §5.2 贪心串联；**紧急优先必须内嵌在每轮选择内部**（每轮重扫 pool 判断 `hasUrgent`），不能靠事后排序——否则多趟与插单下会丢掉「紧急先送」；并列时按节点 ID 字典序取，保证同一输入必得同一条路线 | k = 候选数：一轮对 pool 里每个候选各调一次最短路 ⇒ 单趟约 k(k+1)/2 = **O(k²) 次最短路调用**（k=25 时约 **325 次**），是整个规划的主开销；`appendLeg` 把**全部途经节点**写进 `Trip::nodes` | 自己写「每步选最近」的比较、时间窗推进、紧急优先与 tie-break | `Candidate[]` + 图 → `weave` → `Stop`/`Trip`；被 `multiTripPlanImpl` / `replan` / `replanOneTrip` 复用 | 贪心不保证最优（报告必须照写）；时间推进恒用**耗时**维度 `edge->timeMin`，与本次策略无关；停靠点的到达时刻要用「等过窗口」的 `arrivalMin` 覆盖 `appendLeg` 记下的原始到达时刻 |
| `multiTripPlan`（多趟分批） | 总需求 > 载重时进入：紧急候选先独立成趟 → 在途货一趟 → 其余按簇分批，每批一趟从仓库直达后返回 | D21 把「载重不足」从不可行改成多趟往返；分簇用数据里的 `sub_network_id`（行政归属，可核对），不每次重算最近枢纽；簇按总货量降序、平局按 hub 名升序 ⇒ 输出确定。中转站**不参与排线**（实测经站 198.2km/13 趟 vs 直达 178.2km/6 趟） | 批内「能装就装」线性装箱 O(簇内候选数)；簇序用**手写选择排序** O(簇数²)（禁 `std::sort`）；整体 ≈ Σ 各趟的 O(k_t²) 次最短路 | 超载场景直接判不可行（旧 D14 行为），或自己写分簇 + 分批 + 趟序列 | `Candidate[]` + `OnboardItem` + `initialStock` → `multiTripPlan` → `Trip[]` → `flatten` | 批的起点必须是车的**真实位置** `current` 而不是最初的 `startPos`（否则排出的趟首尾不接）；只有「从仓库装货出发」的趟才计缓冲货，别的趟凭空计会重复计数 |
| `GraphEdit`（`addRandomCustomer`·`closeRandomRoad`·`makeSyntheticEdge`） | 动态增删：随机位置插新客户、随机封一条路（双向删边）、手工加边的权重估算 | 坐标 → 权重的换算**从图自身既有边推算**平均比值（`estimateScale`），不硬编码「坐标单位 → 公里」⇒ 不与数据集尺度脱钩；封路前用 BFS 检查「封了以后还连不通」，**不封桥** ⇒ 不会把一片区域变成孤岛 | `estimateScale` O(m)；`reachesSkipping` 手写 BFS，队列用 `vector` + 游标、`seen` 线性查找 ⇒ O(n·(n+m)) 量级；`addRandomCustomer` 找最近既有节点 O(n) | 自己写「最近点 + 双向连边 + 权重估算 + 连通性检查」 | 事件分派 → `GraphEdit` → `LogisticsGraph::addNode`/`addEdge`/`removeEdge` → 图变了，后续规划在新图上跑 | `seen` 是线性查找而不是 `set`（节点量小）；封路是**双向**删边，在含单向边的图里反向边本就可能不存在；`makeSyntheticEdge` 在坐标重合时返回 false；`addRandomCustomer` 建边失败会回滚删点 |
| `SimEvent`（`nextEventTimeMin`·`pickEvent`·`EventWeights`）+ `Rng` | 软件内时间的事件模型：每 `intervalMin` 一个事件刻、每刻恰抽 1 个事件，四类权重 10:3:1:1 | **两个独立理由，别混**：①用软件内时钟而不是真实定时器／推进计数，是为了「推进粒度不影响事件串」（D24）；②手写 `xorshift32` 而不是 `<random>`，是**可复现性**选择（同种子必得同序列，测试能逐值断言不 flaky），**不是**因为 STL 被禁 | `pickEvent` 单次 O(4) 前缀扫描（不预先算总和再赌一次）；`nextEventTimeMin` O(1) 且严格大于 now；`Rng` 每步 3 次移位异或 O(1) | 自己写加权抽签、全零权重的兜底、事件刻对齐 | `GeneralConfig`（权重 + 间隔）→ `nextEventTimeMin` + `pickEvent` → GUI 事件分派 → `Traffic` / `insertUrgentOrder` / `GraphEdit` | 权重 ≤ 0 的种类**永不被抽中**（写 0 再问「为什么不出现」是误用）；全零时保底 `Traffic` 且**仍消耗一次随机数**（契约：一次抽签 = 一次 rng 消耗，否则两条路径的事件串会错位）；`intervalMin <= 0` 返回 `nowMin + 1` |
| `simulateTrafficChange`·`TrafficChange`·`TrafficReport`·`needsReplan` | 一次路况变化中被改动的边清单（增幅 + 畅通/拥堵），以及「要不要重算」的判定 | 把「这次改了什么」落成**可审的数据**——因为触发判定要问「受影响的边是否恰在当前路线的相邻两站之间」；增幅每次**重设**为 `baseTimeMin×(1+ratio)` 而不是在原值上叠加 ⇒ 耗时不会逐次失控增长，`baseTimeMin` 永远是基准 | count = 改动边数（默认 `round(0.1×106)` = **11**）：选边用**部分 Fisher-Yates** O(count)（只需前 count 个位置被打乱，全排列是浪费）；`needsReplan` O(count × 路线长度) | 分不清「改了但不在我路上」和「改在我必经段上」，只能每次事件都全量重算 | `simulateTrafficChange` → `LogisticsGraph::updateEdgeTime`（就地改 `timeMin`）→ `TrafficReport` → `needsReplan` / `replanIncremental(report)` | 只有「增幅 ≥ 阈值 **且**恰在路线相邻两站」才触发（畅通变更 `increaseRatio=0`，永不触发）；`needsReplan` 与 GUI 高亮共用 `isEdgeOnRoute` 同一条逻辑 |

## 4. 表 3 · 调度状态层（被算法承载、被界面消费的记录）

| 结构 | 是什么 | 为什么是它（排除谁 / 依据） | 特点与复杂度（前提） | 没有它得自己写什么 | 连接：谁喂它 → 它 → 谁消费 | 代价与坑 |
|---|---|---|---|---|---|---|
| `Candidate`（`RoutePlanner.cpp` 内部） | 把 `Order` 折叠成「停靠点候选」：同点订单合并（需求求和、窗口取并集、任一紧急则该点紧急） | §4.4 停靠点合并规则：一个节点只应停一次——否则同点多单会被贪心反复选中、来回奔波 | `buildCandidates` O(k × 订单数)（对每个订单线性扫已有候选，无映射表）；k ≤ 25 | `weave` 会把订单当候选 ⇒ 停靠次数与订单数同阶，而不是与配送点数同阶 | `Order[]` → `buildCandidates` → `Candidate[]` → `weave` 的 pool / `replanOneTrip` 的 `findCandidate` | 合并靠线性扫（订单量大才需要映射表）；`weave` 的 pool 按**值**传递，每次调用复制一份（25 项，换来「调用方保留自己副本」的清晰语义） |
| `Stop` | 一次停靠的时间-载重结算：`rawArrivalMin`/`waitMin`/`arrivalMin`/`late`/`penaltyMin`/`remainingLoadKg` | §4.3 推进递归要求 raw → wait → arrival → penalty **成组落地**；否则界面与测试各自重算，口径必然漂（D13：规划、重规划、插单必须同一口径） | 定长 O(1)；一次停靠一个 | 每个消费者（界面、汇总、测试）都要重算等待与罚时 | `weave` / `makeStop` 生成 → `Trip::stops` → `flatten` 汇总到 `RoutePlan::stops` 与 `totalPenaltyMin` → GUI 停靠明细 | `remainingLoadKg` 是「**离开该站时**本趟剩余」，只统计订单货；缓冲货走 `Trip::bufferKg`，两者绝不混用 |
| `Trip` | 一趟行程：`nodes`/`nodeArrivalMin`/`nodeIsStop` 三条平行数组 + `stops` + `loadKg`/`bufferKg` + 汇总 | 多趟（D20/D21）的单位是「趟」：界面要显示第 N 趟、增量重规划要逐趟重建、缓冲库存要按趟记账；用平行数组是因为下游推进是**按下标**的（`nodeIndexAtTime` 的语义就建立在下标对齐上） | O(本趟节点数)；三条数组必须等长；不变量 `loadKg + bufferKg ≤ capacityKg` 且 `bufferKg ≥ 0` | 得自己从扁平序列里反推「趟边界」 | `weave` 填充 → `RoutePlan::trips`（**真源**）→ `flatten` 展平 / `sliceRemainder` 切剩余 / `replanOneTrip` 重建 | `replanOneTrip` 先用「`nodes.size() < 2` 或 `nodeIsStop` 与 `nodes` 不等长」判不可增量；`loadedFromDepot` 与 `supplyInPlace` 两个标记专门区分「出仓趟／就地满足趟／接着送趟」，否则导出证据会把合法的 `bufferKg=0` 误报成缺陷 |
| `RoutePlan`（+ `PlanStatus`） | 一次规划的完整结果：`trips`（**真源**）+ 由它展平的 `nodes`/`nodeArrivalMin`/`nodeIsStop`/`nodeTripIndex`/`stops` + 汇总 + 库存字段 | `trips` 是真源、扁平字段是「兼容视图」，且**只在一处（`flatten`）生成** ⇒ 两套数据不会各自维护走样；界面按下标推进，扁平序列比「在 trips 里找第几个节点」直接 | 空间 O(总节点数 + 停靠数)；`flatten` O(总节点数 + 停靠数)；失败用 `PlanStatus{Ok, OrderExceedsCapacity, Unreachable}` + `reason` 返回 | 调用方自己维护「趟列表」与「整条序列」两份数据并保持同步 | `multiTripPlan`/`replan`/`replanIncremental` 产出 → GUI 推进与 `isEdgeOnRoute` 高亮 / `sliceRemainder` 切剩余 → 再喂 `replanIncremental(previous)` | `plan.nodes` 为空时 `nodeIndexAtTime` 返回 0（**调用方需自行判空**）；`totalTimeMin` 用**未取整**的 elapsed 算（改用 `returnArrivalMin` 反推会引入 0.1min 级精度回归） |
| `flatten`（展平点，core 里产出视图消费的字段） | 把 `trips` 展平成 `nodes`/`nodeArrivalMin`/`nodeIsStop`/`nodeTripIndex`/`stops` 并汇总总量 | **唯一生成点**；后续趟要跳过起点（否则展平后出现「原地一步」） | O(总节点数 + 停靠数)；在三个规划出口各调一次（`multiTripPlanImpl` / `replan` / `replanIncremental`） | 每个消费者各自展平一遍，视图立刻与趟结构走样 | `RoutePlan::trips` → `flatten` → 扁平字段 → GUI 推进 / `isEdgeOnRoute` / `sliceRemainder` | 三个出口都要调，忘一个就拿不到新视图；`sliceRemainder` 切出的 `remainder` 只填了 `trips`/`nodes`/`nodeIsStop` 与库存快照，**没有** `nodeArrivalMin`/`nodeTripIndex`（它只喂 `replanIncremental(previous)`，那边只读 `trips`/`nodes`/`status`） |
| `OnboardItem` | 车辆**此刻已在车上**的货（`nodeId`, `kg`） | 重规划时若不知道「车非空」，规划器会假设货都在仓库 ⇒ 每次重算都先跑回仓库（P17 实测「车在仓库与客户间反复跳跃」）；只留两个字段，因为规划只需要「哪一点、多少货」 | O(在途点数)；`multiTripPlanImpl` 里按节点线性去重（同点多单只插一次） | 重规划出来的每一段都可能先回仓库，与车的物理事实脱节 | GUI 从当前 `RoutePlan` 推出在途货 → `replan` / `insertUrgentOrder` / `replanIncremental` → `multiTripPlanImpl` 的「在途货批」（排在紧急批之后） | 必须从**剩余池**取候选（从全量取会把已送过的点再送一遍）；批的起点用 `current`（车的真实位置），不是 `startPos` |
| `TransitOp`·`TransitStock` | 站内一次装卸的记账单元（`nodeId`/`kgDelta`/`atMin`）与站库存快照（期初/期末） | 缓冲库存（D23，**仅服务紧急单**）要能核对守恒 ⇒ 用「操作序列 + 期初/期末」表达：期末 = 期初 + Σ`kgDelta`；`kgDelta` 带符号（>0 入库、<0 出库）比两套字段少一个状态 | `transitOps` O(操作数)、`transitStock` O(站点数)；按时刻排序用**手写插入排序** `sortTransitOpsByTime`（禁 `std::sort`）；期末重算 O(操作数 × 站点数) | 库存变成隐式状态，守恒守恒断言无从落笔 | `Trip::bankOps`（返程顺路寄存，至多一条）→ `RoutePlan::transitOps` → 界面显示 + 守恒断言；`initialStock`（**当前时刻**快照）→ 规划器 | `initialStock` 的语义是「当前时刻快照」而不是「规划期初」，且**不回传**（期末只从 `RoutePlan::transitStock` 读）；`replanIncremental` 必须把库存快照**带走**，否则路况重规划后库存凭空归零；「顺路」意味着该站本来就在最短路的节点序列里 ⇒ 寄存**不新增节点、不改时刻、不改里程** |

## 6. 基础记录速查（没有算法、只有字段，故不占上面七栏）

| 类型 | 字段要点 | 一句话 |
|---|---|---|
| `Node` | `id` / `type` / `x,y` / `subNetworkId` | 当前数据：2 仓库 + 3 中转站 + 25 配送点；`subNetworkId` 是分簇依据（行政归属，不是算出来的最近枢纽） |
| `Edge` | `fromId`/`toId` / 三权重 / `baseTimeMin` / `congested` | 有向；同一对 `(from,to)` 至多一条；`baseTimeMin` 由 `addEdge` 在未指定时固化为当前 `timeMin` |
| `Order` | `nodeId` / `demandKg` / `windowStartMin` / `windowEndMin` / `urgent` / `served` | 窗口统一是「相对当日 00:00 的分钟数」；被 `buildCandidates` 折叠成 `Candidate` |
| `Vehicle` | `startNodeId` / `capacityKg` / `departTimeMin` | 当前单车辆（200kg、08:00）；约束的是**单趟在车货量**，不是总需求 |
| `PathResult` | `found` / `nodes` / `totalWeight` | `Dijkstra` 的唯一出口；`found=false` 时 `nodes` 为空 |
| `TrafficChange` | `fromId`/`toId` / `increaseRatio` / `congested` | 一次改动的账目；`increaseRatio` 就是本次施加的增幅（**不叠加**） |
| `EventWeights` | 路况/紧急/新客/封路 = 10/3/1/1 | 抽签的扫描顺序即枚举顺序，决定了并列时的确定性 |
| `PlanStatus` | `Ok` / `OrderExceedsCapacity` / `Unreachable` | 只有「单个订单就超载」或「存在不可达点」才不可行；**总需求超载走多趟** |
